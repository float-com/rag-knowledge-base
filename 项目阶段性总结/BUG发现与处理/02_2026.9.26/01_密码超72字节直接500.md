# 01_密码超72字节直接500

> 发现日期：2026.09.26
> 发现阶段：**Day11 · 第 7 章「用户与角色管理」**（写 `POST /api/users` 时核对密码校验规则）
> 状态：**⚠️ 已知未修 · 暂时保留**
> 修复计划：等 Day13 全部学完后再统一处理（用户决定）

---

## 一、问题一句话

**密码的 `max_length=128` 限制的是字符数，而 bcrypt 拒绝的是超过 72 字节的明文 —— 中文只要 25 个字、emoji 只要 19 个，就会让创建/修改用户接口返回 500。**

---

## 二、复现证据（实测，非推测）

### 2.1 纯函数层：`hash_password` 的真实边界

| 输入 | 字符数 | UTF-8 字节数 | 结果 |
| --- | --- | --- | --- |
| `"a" * 71` | 71 | 71 | ✅ OK |
| `"a" * 72` | 72 | 72 | ✅ OK |
| `"a" * 73` | 73 | 73 | ❌ **抛 `ValueError`** |
| `"密" * 24` | 24 | **72** | ✅ OK |
| `"密" * 25` | 25 | **75** | ❌ **抛 `ValueError`** |
| `"😀" * 18` | 18 | **72** | ✅ OK |

**规律：边界是 72 字节，不是 72 或 128 个字符。**

### 2.2 HTTP 层：`POST /api/users` 的实际响应

| 请求密码 | 字节数 | 实际响应 |
| --- | --- | --- |
| `"a" * 71` | 71 | **201**（正常创建） |
| `"a" * 73` | 73 | **500** `{'code': 'internal_error', 'message': '服务内部错误'}` |
| `"密" * 24` | 72 | **201** |
| `"密" * 25` | 75 | **500** `{'code': 'internal_error', 'message': '服务内部错误'}` |

> 复现方式：真库 + `httpx.ASGITransport(app=app, raise_app_exceptions=False)`
> （必须传 `raise_app_exceptions=False`，否则异常会被 httpx 直接抛回测试脚本，看不到 500 响应体）。
> 同一现象也会出现在 `PATCH /api/users/{user_id}` 改密码时（同一个 `hash_password` 调用点）。

---

## 三、根因链

```
UserCreate.password 声明的是  max_length=128     ← 限制【字符数】
        ↓
bcrypt 5.x 对超过 72 【字节】的明文直接抛 ValueError
（4.x 之前是静默截断，5.x 起改为报错）
        ↓
UserService.create_user / update_user 直接调 hash_password，中间没有任何按字节的校验
        ↓
ValueError 冒泡到全局异常处理器
        ↓
被当作"未预期的系统崩溃"转成 500 internal_error
        ↓
用户看到"服务内部错误"，日志里是一句 bcrypt 的英文原始报错
```

**为什么 `max_length=128` 看起来"够严格"却漏了**：

| 输入类型 | UTF-8 编码宽度 | 达到 72 字节需要几个字符 |
| --- | --- | --- |
| 纯 ASCII（英文/数字/符号） | 1 字节 | **72 个** |
| 中文 / 日文 / 韩文 | 3 字节 | **24 个**（第 25 个就超） |
| emoji | 4 字节 | **18 个**（第 19 个就超） |

也就是说：**`max_length=128` 只在纯 ASCII 输入下"恰好"比 72 宽松一点点；一旦用户用中文设密码，128 这个上限完全不起作用。**

## 四、影响面

| 维度 | 评估 |
| --- | --- |
| **触发条件** | 用户在创建用户 / 改密码时，输入的密码 **UTF-8 编码超过 72 字节** |
| **实际概率** | **中低** —— 需要"中文密码"或"超长密码"这种不常见但完全合理的输入 |
| **后果** | 接口返回 **500**，用户看到"服务内部错误"，无法自助解决（不知道要缩短密码） |
| **是否是安全问题** | ❌ **不是**（安全性反而是正确的）。理由见下 |
| **数据是否受损** | ❌ 不受损。异常发生在写库之前，用户不会被创建、密码也不会被改 |
| **受影响的接口** | `POST /api/users`（创建用户）、`PATCH /api/users/{user_id}`（改密码） |
| **不受影响的接口** | 登录（`/api/auth/login`）—— `verify_password` 已经兜住了 `ValueError`，超长密码只是"登录失败"而不是 500（见下） |

### 4.1 为什么这**不是**安全问题 —— 一个值得记的反直觉点

容易被误判成"安全漏洞"，但**恰恰相反，它的成因说明安全设计是对的**：

```
如果代码用"静默截断"的方式兼容超长密码：
    用户设了 100 字节的密码 → 实际只存了前 72 字节的哈希
        ↓
    用户用完整 100 字节登录 → 也被截断成 72 字节 → 校验通过
        ↓
    密码的有效长度被悄悄缩短了，用户【以为自己设了一个更长的密码】
        ↓
    这是真实存在的安全弱点（攻击者只需要猜前 72 字节）

bcrypt 5.x 选择【直接报错】而不是静默截断，正是为了暴露这个上限，
而不是制造一个"看起来更长其实更弱"的密码。
```

**所以正确处理方式是"在入口按字节拦住并告诉用户"（422），而不是"想办法容忍它"。**

### 4.2 登录路径为什么没事

`app/core/security.py` 的 `verify_password` 里有：

```python
try:
    return bcrypt.checkpw(plain.encode("utf-8"), hashed.encode("utf-8"))
except ValueError:
    # 明文的 72 字节上限、以及非法 hash 串，都会走到这里，
    # 统一按"密码不对"处理即可，绝不向上抛
    return False
```

因此用超长密码去登录，得到的是**正常的登录失败**（401），不是 500。
**这道兜底是第 3 步写 `security.py` 时就已经做对的**，缺的只有 `hash_password` 那一侧。

## 五、修复方案（已设计好，待执行）

### 5.1 主防线：`backend/app/api/schemas/users.py`

选择这一层的三条理由：

| # | 理由 |
| --- | --- |
| 1 | **两个有风险的入口都在它之后** —— 全项目 `hash_password` 只有 3 个调用点：`user_service.py:113`（创建）、`user_service.py:166`（更新）、`seed.py:120`（种子，值来自可信配置，无风险）。拦住这两个 schema 字段就覆盖了全部不可信输入 |
| 2 | **这一层能给出正确的状态码** —— 用户输入不合法应返回 **422**（框架级参数校验）。若只在 `hash_password` 里抛，会变成 **500** |
| 3 | **与现有风格一致** —— 这一层已经在用 `min_length` / `max_length` 做长度校验，加一条"按字节"的规则是同层同类的事 |

**具体改法**（抽成模块级函数，供两个类共用，避免复制两份将来漏改一处）：

```python
from pydantic import field_validator

# bcrypt 的上限是按【字节】算的，不是字符
_BCRYPT_MAX_BYTES = 72


def _validate_bcrypt_length(v: str | None) -> str | None:
    """按字节校验密码长度，防止超长明文直接把 bcrypt 打崩。"""
    if v is None:
        return v
    if len(v.encode("utf-8")) > _BCRYPT_MAX_BYTES:
        raise ValueError(
            f"密码的 UTF-8 字节长度不能超过 {_BCRYPT_MAX_BYTES} 位"
            f"（中文等非 ASCII 字符会占用多个字节）"
        )
    return v


class UserCreate(BaseModel):
    ...
    password: str = Field(min_length=4, max_length=128)

    _check_password_bytes = field_validator("password")(_validate_bcrypt_length)


class UserUpdate(BaseModel):
    ...
    password: str | None = Field(default=None, min_length=4, max_length=128)

    _check_password_bytes = field_validator("password")(_validate_bcrypt_length)
```

### 5.2 安全网：`backend/app/core/security.py` 的 `hash_password`

只改 schema 有一个缺口：**Service 层也可能被非 HTTP 路径调用**（脚本、将来的批量导入）。
所以建议在 `hash_password` 里也拦一道 —— 不是为了现在，而是为了**将来**：

```python
def hash_password(plain: str) -> str:
    # 安全网：HTTP 入口已在 schemas/users.py 按字节校验过；这里再拦一道，
    # 让"绕过 HTTP 直接调 Service"的调用方也能得到一句能看懂的报错。
    if len(plain.encode("utf-8")) > 72:
        raise ValidationError("密码的 UTF-8 字节长度不能超过 72 位")
    return bcrypt.hashpw(plain.encode("utf-8"), bcrypt.gensalt()).decode("utf-8")
```

> ⚠️ 两点说明：
> 1. `security.py` **已经** import 了 `app.core.exceptions`（用的是 `UnauthorizedError`），
>    所以加 `ValidationError` 不引入新的依赖方向。
> 2. 这样改之后，万一 schema 校验被绕过，返回的是 **400** 而不是 500 —— 比现在好，
>    但仍不如 422 准确。**主力防线依然是 schema 层。**

### 5.3 推荐同时考虑：把密码长度上限写成"两个约束"

```python
password: str = Field(min_length=4, max_length=128)   # 字符上限（保留，防超长请求体）
# 再加按字节的 validator（真正的 bcrypt 边界）
```

两条约束并存的理由：`max_length=128` 挡的是"超大请求体"（10MB 的密码字符串也能触发它），
按字节的 validator 挡的是"bcrypt 的真实上限"。两者防的不是同一件事。

## 八、相关但独立的两条发现（同一天发现，一并留档）

本次复现过程中还撞到两个独立问题，**不属于本 BUG**，但都在这里记一笔，避免以后重复踩：

### 8.1 `seed` 的守卫一存在"半初始化状态"盲区（Day11 第 6 章发现）

```
现象：为了复现本 BUG，我先清空了 users / roles 三张表，
     但脚本随后只补建了用户、没有补建角色 ——
     结果 roles=0，admin 用户失去了 admin 角色，
     所有管理接口返回 403，而 seed 的守卫一（count_all() > 0）
     因为"库里有用户"直接跳过，内置角色永远建不出来。
```

**结论**：`count_all() > 0` 这个幂等守卫假设"库里有用户" ⇔ "初始化完成"。
理论上存在半初始化状态会被永久跳过。
**后果不严重**（有用户能登录，只是缺内置角色），但排查时很有迷惑性 —— 权限问题会以 403 的形式出现，而病因在 seed 的守卫上。

### 8.2 `httpx.ASGITransport` 默认会把服务端异常再抛出来（测试技巧）

```
默认行为：raise_app_exceptions=True
    → 未捕获异常被 httpx 直接抛回测试脚本，你【看不到 500 响应体】，
      只会看到一句 pydantic/Starlette 的 traceback

正确写法：httpx.ASGITransport(app=app, raise_app_exceptions=False)
    → 让 FastAPI 的全局异常处理器接管，把异常转成 500 响应，
      才能断言到 {'code': 'internal_error', 'message': '服务内部错误'}
```

**这条是以后写"验证 500 行为"的测试时必踩的坑**，记在这里省一次排查。
