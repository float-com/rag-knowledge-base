## 一、问题一句话

**上传链路从"文件经过服务器"改成"浏览器直传 COS"之后，一条上传被拆成三段（init / complete / abort），但第 11 期的鉴权清单还停在旧协议上 —— 三个新端点一个都没挂鉴权；同时 `UploadSession` 上暂存的权限标签，始终没有被搬到最终的 `Document` 上，导致直传落地的文档一律是"空标签 = 公开"。**

---

## 二、两个问题分别是什么

### 问题 1 🔴 三个端点完全没有鉴权

```
backend/app/api/routes/document_uploads.py
    POST   /api/documents/uploads/init                ← 无 CurrentUser、无 CurrentAdmin
    POST   /api/documents/uploads/{upload_id}/complete
    DELETE /api/documents/uploads/{upload_id}
```

三扇门各自能干什么：

| 端点 | 未登录的人能做什么 |
| --- | --- |
| `init` | 拿到一枚**有效的 COS 预签名 PUT 凭证**（300 秒内可往桶里写对象） |
| `complete` | 让服务端去校验对象并**建出 Document 记录**、触发解析流水线 |
| `abort` | **删掉 COS 上的对象**（只要知道 upload_id） |

### 问题 2 🔴 直传落地的文档丢权限标签

```python
# backend/app/db/models.py  L206-207（UploadSession.permission_tags 的注释）
# 业务说明：直传生命周期内暂存的细粒度数据权限与可见性标签集合；
#           待落库 Document 时按需向下沉淀        ← 计划写在这里
```

```python
# backend/app/services/document_upload_service.py  L287-297（finalize_upload 建 Document）
document = Document(
    name=upload_session.original_name,
    file_hash=file_hash,
    mime_type=upload_session.mime_type,
    size=upload_session.expected_size,
    storage_provider="cos",
    cos_bucket=service.file_service.bucket,
    cos_object_key=upload_session.object_key,
    cos_region=service.file_service.region,
    status=DocumentStatus.UPLOADING,
)          # ← 没有 permission_tags，也没有 created_by
```

而 `Document.permission_tags` 的空数组语义是**公开**：

```
permission_tags 缺省 = []
        ↓
按第 11 期约定：空数组 = 公开，任何登录用户都能看
        ↓
所以走直传上传的文档，无论管理员当初"打算"设什么标签，一律【全员可见】
```

### 问题 2 的附带项：`created_by` 也无从落库

`created_by`（"谁传的"，审计用途）在直传链路上**根本没有数据来源**：

```
旧链路：文件经过 8000，请求上下文里有当前用户 → 可以顺手记 created_by
        ↓
新链路：finalize 是【后台任务】，用独立的 AsyncSessionLocal，
        请求上下文早已结束 → 拿不到当前用户
        ↓
而 upload_sessions 表【没有上传人字段】可以中转
        ↓
结论：要让 created_by 在直传链路上可用，必须先给 upload_sessions 加一列
```

## 三、为什么会这样：两处根因（都指向 Day3 那次改造）

### 3.1 证据链（git 追踪，非推测）

```
655c131  2026-09-14  [feat(upload): 打通预签名直传链路并修复 Docling 模型加载]
          ← document_uploads.py 这个文件在该提交里【首次出现】
          ← upload_sessions 表也在这次改造中建立

19c7f2c  2026-09-26  [feat(auth): 给文档与会话挂上用户态与权限过滤]
          ← backend/app/api/routes/documents.py 里【第一次】出现 permission_tags
          ← 即：9-26 之前，前端上传表单里的"权限标签"输入框，填了也白填（后端直接忽略）
```

`Day3_文本向量化链路优化/上传链路架构对比.md` 里对这次改造的定性：

> - **旧链路（multipart 代理上传）**：仍在代码中，前端已不再调用，作为灰度回滚与旧客户端兼容保留。
> - **新链路（预签名直传）**：当前前端实际使用的链路。

### 3.2 根因一：按"文件"对照，而不是按"协议端点"对照

```
旧链路（传输方式 A）：文件必须经过 8000 端口
    → 服务端要读全文算哈希 → 只能有一个端点 → 权限只挂一处
        ↓
第 8 章把 CurrentAdmin 正确加在 POST /api/documents 上 ✅
        但前端从 9-14 起就不调它了，它只是回滚用的遗迹
        ↓
新链路（传输方式 B）：文件不经过 8000 端口
    → 一条上传拆成三段（init / complete / abort）
    → 就是【三扇新的门】，而"门锁清单"还停在旧协议上
        ↓
我第 8 章按文件逐个 grep（grep 范围是 routes/documents.py），
document_uploads.py 没进清单 → 三扇门全漏
```

> 📌 **一个现成的"应查清单"其实就在手边**：
> `Day3_文本向量化链路优化/上传链路架构对比.md` 里已经列出了这三个端点
> （`initDocumentUpload` / `completeDocumentUpload` / `abortDocumentUpload`）。
> 第 8 章核对时**没有去比对这份文档**，这是本次漏检的直接原因。

### 3.3 根因二：搬迁动作被记录了下来，但没人执行

```
直传链路建立时（9-14）：Document 上还没有 permission_tags 列
        ↓ 所以"搬到 Document"这件事当时做不了
UploadSession.permission_tags 的注释写了计划："待落库 Document 时按需向下沉淀"
        ↓
第 11 期给 Document 加了列（19c7f2c）
        ↓
但没有人回头把 finalize_upload 里那一段搬运补上
        ↓
桥两头都搭好了，就差最后一根线
```

### 3.4 一个容易忽略的技术细节：两边类型不一样

```
UploadSession.permission_tags   →  JSONB
Document.permission_tags        →  varchar[]（ARRAY(String())）
        ↓
搬运时不能直接赋值，需要类型转换 + 清洗，
否则会出现"看起来存进去了，检索时 && 永远不命中"的静默失效
```

### 3.5 还发现一处"注释与实现不一致"

```python
# backend/app/api/routes/document_uploads.py  L76
#   特性：注入当前请求的异步数据库会话，由领域服务执行【鉴权】、入库与签名计算
```

`init_upload` 的实现里**没有任何鉴权动作** —— 只做了大小校验、后缀解析、建会话、签 URL。
**这句注释会让下一个人以为鉴权已经做了**，从而不去检查。属于"错误的注释比没有注释更危险"。

### 3.6 还有一处：init 阶段没有对标签做标准化

```
init_upload 把 payload.permission_tags 原样存进 UploadSession（L135）
        ↓
没有经过 _normalize_tags（去空白 / 丢空串 / 去重）
        ↓
若前端传 ["hr ", "hr"]，库里会存成"看起来像 hr 但实际不相等"的字符串
        ↓
将来搬到 Document 后，检索时 && 永远不命中
        ↓
表现为"权限明明配了却不生效"，极难排查
```

## 四、当前影响评估

### 4.1 数据核查（2026-09-26 实测）

```
upload_sessions 共 32 条，permission_tags 非空的 = 0 条
documents       共  8 篇，permission_tags 非空的 = 0 篇
```

**所以当前不是"设了标签但丢了"，而是"标签根本没进来过"——暂时没有数据受损。**

原因：现有 8 篇文档在直传链路上传时，要么没填标签，要么填了也被后端忽略（后端 9-26 才真正开始处理这个字段）。

### 4.2 但有三个隐患，按严重程度排列

| # | 隐患 | 说明 |
| --- | --- | --- |
| 1 | **默认放开的权限缺口** | 就算 4.1 现在没损失，只要修好问题 2 之前有人用直传链路传带标签的文档，**每一次都会静默变成公开** |
| 2 | **未登录可写入** | 任何人都能 init 拿预签名 URL → 占 COS 存储 → complete 建 Document → 触发解析（烧 CPU 与向量化配额） |
| 3 | **未登录可删除** | 只要知道 upload_id，就能 `abort` 删掉 COS 上的临时对象 |

> ⚠️ **隐患 1 的危险性在于它的"静默"**：
> 管理员在界面上填了 `["hr"]`、点了确定、看到上传成功，
> **没有任何报错**，但结果是全员可见。
> 这类"看起来生效了、实际没生效"的权限问题，比明确报错危险得多。

## 五、修复方案（Day13 之后执行）

### 5.1 改动 ① 三个端点各补一个依赖（零风险，可随时做）

```python
# backend/app/api/routes/document_uploads.py
from app.api.deps import CurrentAdmin, DbSession

async def init_upload(
    _: CurrentAdmin,          # ← 新增
    payload: InitUploadRequest,
    session: DbSession,
) -> InitUploadResponse:
```

`complete_upload` / `abort_upload` 同样各加一个 `_: CurrentAdmin`。

**顺带要修的**：
- `init_upload` docstring 里那句"由领域服务执行鉴权"（L76）必须改掉；
- 或改成在 `router` 上挂 `dependencies=[Depends(get_current_admin)]`
  （第 8 章评测模块就是这么做的，声明一次整组生效）。

### 5.2 改动 ② 把标签搬到 Document（一行的事）

```python
# backend/app/services/document_upload_service.py  finalize_upload 建 Document 时
document = Document(
    ...
    status=DocumentStatus.UPLOADING,
    # 【新增】把 init 阶段暂存的标签沉淀到正式文档上。
    #   ① JSONB → varchar[] 的类型转换由 SQLAlchemy 按列类型完成；
    #   ② 清洗复用 document_service 里已有的 _normalize_tags，保证口径与旧链路一致
    permission_tags=_normalize_tags(upload_session.permission_tags or []),
)
```

> 📌 注意 `_normalize_tags` 目前在 `document_service.py` 里是**模块级私有函数**（下划线开头）。
> 直传服务要用它，有两个选择：
> - 直接 import（破坏"私有"约定，但项目内已有先例）；
> - 提升为公开函数或上收到某个共享位置（更干净，但要动两处）。
> **推荐后者**，顺便把第 8 章归档里记的"三个 service 各留一份副本"这件事一并收敛。

### 5.3 改动 ③ `created_by` 需要一张小迁移

```
① upload_sessions 加一列 created_by（UUID，可空，外键 users.id，ON DELETE SET NULL）
② init_upload 时从【当前用户】写入（这里因为加了 CurrentAdmin，请求上下文里有用户）
③ finalize_upload 时搬到 Document.created_by
```

> 这一步依赖改动 ①（没有鉴权就没有"当前用户"可写）。

### 5.4 改动 ④ 顺手把 init 阶段的标签也清洗一遍

```python
permission_tags=_normalize_tags(payload.permission_tags or []),
```

**为什么 init 和 finalize 两处都要清洗**：
init 清洗是为了"暂存的就是干净的"（否则迁移时还得回头洗历史数据）；
finalize 清洗是最后一道防线（防止有人绕过 init 直接写库）。

## 六、验收方法（修完之后怎么证明修好了）

### 6.1 鉴权（改动 ①）

```
未登录 POST /api/documents/uploads/init              → 401
普通用户 POST /api/documents/uploads/init            → 403
普通用户 POST /api/documents/uploads/{id}/complete   → 403
普通用户 DELETE /api/documents/uploads/{id}          → 403
管理员 四个动作                                       → 正常
```

### 6.2 标签沉淀（改动 ②）

```
管理员传带标签的文档 → 上传完成 → 查 documents.permission_tags
    ├─ 必须等于 init 时声明的标签（经清洗后）
    └─ ★ 反向验证：无该标签的用户【检索不到】该文档的分块
       （这正是第 9 章刚补上的那条检索 SQL 过滤）
```

> ⚠️ **反向验证是关键**：只看"标签存进去了"不够，
> 必须用第 9 章的检索链路证明"**没权限的人真的搜不到**"，
> 才算闭环。否则又会出现"存了但 && 不命中"的静默失效。

### 6.3 兼容性（不能打破旧链路）

```
旧链路 POST /api/documents（multipart）仍能正常上传并带标签
    ← 两条链路必须共用同一套 _normalize_tags 口径
```

## 七、给复盘留的一条教训

```
引入新的【传输协议】时，安全 / 权限这类【横切关注点】必须按
"协议端点清单"逐个打钩，不能按"文件清单"打钩。
```

**推理过程**：

```
认证 / 鉴权字典是挂在【信任边界】上的
        ↓
而换协议往往会改变信任边界的【数量】和【位置】
        ↓
旧链路 1 个端点 = 1 扇门 → 翻文件很容易翻全
新链路 3 个端点 = 3 扇门 → 翻文件不一定翻得到
        ↓
所以要翻的是"这次改造新增/改动过哪些端点"（协议视角），
而不是"这次改造动了哪些文件"（文件视角）
```

> 📌 **落到操作上**：每次做权限类改造时，
> 直接打开 `docs` / `/openapi.json` 数**端点**，
> 而不是在代码目录里 grep **文件**。
> 这次如果从 OpenAPI 的 28 条路径出发逐条打钩，
> `document_uploads` 那三条一眼就会暴露出来。
