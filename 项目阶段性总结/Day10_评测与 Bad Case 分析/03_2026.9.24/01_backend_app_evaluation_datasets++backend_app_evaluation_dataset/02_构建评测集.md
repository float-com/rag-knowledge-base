## 三、2.1 jsonl 字段约定

### 3.1 文件放置位置

```
backend/app/evaluation/datasets/
├── __init__.py      ← 让 datasets 也成为一个普通包（教程只要求建外层，这是补强）
├── seed.jsonl       ← 50 条（21 KB）全场景评测集
└── smoke.jsonl      ←  5 条（2 KB）流程冒烟集
```

**格式**：**jsonl = 每行一条独立 JSON**。
好处是**新增 / 修改 case 直接改文件就行** —— 不用整体重新序列化，diff 也清晰。

| 评测集 | 条数 | 拒答类 | tags 种类 | 用途 |
| --- | --- | --- | --- | --- |
| **`smoke.jsonl`** | **5** | 1 | 8 种 | **流程测试用，快速跑一遍全链路** |
| **`seed.jsonl`** | **50** | 5 | 13 种 | 覆盖差旅 / 考勤 / 福利 / 产品规格 / 信息安全 / API / 越界拒答 |

### 3.2 七个字段的含义

| 字段 | 类型 | 含义 | 谁消费它 |
| --- | --- | --- | --- |
| **`id`** | `str` | 人类可读的 case 编号（如 `case_001`） | **Bad Case 对账**、跨批次追踪同一用例的指标波动 |
| **`question`** | `str` | 用户问题 | 送进 RAG 链路 |
| **`expected_answer`** | `str` | 期望的标准答案 | **喂给 RAGAS 当 `reference`** |
| **`expected_document_names`** | `list[str]` | 期望被引用的源文档名 | **引用命中判定** |
| **`expected_keywords`** | `list[str]` | 期望出现在引用片段里的关键词 | **文档名不命中时的退路** |
| **`should_refuse`** | `bool` | 期望模型拒答（问题超纲 / 没有相关文档） | **拒答正确率** |
| **`tags`** | `list[str]` | 场景标签 | **按类型筛 Bad Case** |

### 3.3 ⭐ 引用命中判定：**双重宽松匹配**

这是本节最需要在第 3 节之前理解的一条规则（写在 `EvaluationCase` 的 docstring 里，**L37-51**）：

```
实际引用 citations  →  与期望比对：
    ① 文档名命中：实际引用的来源文件名 命中 expected_document_names
    ② 关键词命中：实际引用片段（quote）的文本 命中 expected_keywords 里【任意一个】
    任一成立  →  视为【引用命中】
```

**为什么要"双重"且"宽松"**：

> **切片粒度不同会导致来源微小偏差** ——
> 同一份文档可能被切成不同粒度的片，**文档名可能带路径、可能只匹配一部分**；
> 而**关键词命中**提供了**第二条退路**：哪怕文档名对不上，**只要片段内容里出现了核心词，就认为证据链可信**。

### 3.4 两手实例

**正面用例**（`seed.jsonl` 第 1 条）：

```json
{"id": "case_001",
 "question": "出差住宿一线城市，经理级员工每晚住宿费用上限是多少？",
 "expected_answer": "根据差旅管理制度，经理级员工在一线城市（北京、上海、广州、深圳）的住宿费上限为每晚600元。",
 "expected_document_names": ["差旅管理制度.md"],
 "expected_keywords": ["600", "一线城市", "经理级"],
 "should_refuse": false,
 "tags": ["差旅", "事实问答"]}
```

**拒答用例**（`smoke.jsonl` 第 5 条）：

```json
{"id": "smoke_005",
 "question": "珠穆朗玛峰的海拔高度是多少米？",
 "expected_answer": "该问题超出知识库范围，应当拒答。",
 "expected_document_names": [],
 "expected_keywords": [],
 "should_refuse": true,
 "tags": ["拒答", "越界问题"]}
```

> 📌 **注意拒答用例的 `expected_document_names` 是【空列表】** —— 这是**正确的表达**：
> **该拒答的问题本来就不该引用任何文档**。
>
> 🎯 **第 3 节要与之对齐**：`citation_hit` 对这类用例**记 `NULL`**、
> **不参与命中率的分母**（否则"拒答正确"的样本反而会拉低引用命中率）。

### 3.5 覆盖核对（本节已实测）

| 检查项 | 结果 |
| --- | --- |
| `seed.jsonl` 逐行 JSON 可解析 | ✅ **50 / 50** |
| `smoke.jsonl` 逐行 JSON 可解析 | ✅ **5 / 5** |
| 七个字段是否齐全 | ✅ **55 / 55 全齐**（无多余、无缺失） |
| `id` 是否唯一 | ✅ 两份都唯一 |
| **引用的文档名是否都在知识库里** | ✅ **0 个缺失**（seed 8 个 / smoke 4 个，全部命中） |
| tags 覆盖教程七类场景 | ✅ 差旅 / 考勤 / 福利 / 产品规格 / 信息安全 / API / 越界拒答 **全部命中** |

## 四、2.2 评测集加载

### 4.1 模块清单

| 文件 | 行数 | 内容 |
| --- | --- | --- |
| `backend/app/evaluation/__init__.py` | 0（空） | **按教程要求建空文件** |
| `backend/app/evaluation/datasets/__init__.py` | 0（空） | **补强**：让 `datasets` 也成为普通包（见 §4.4） |
| **`backend/app/evaluation/dataset.py`** | **239** | ⭐ 核心：1 个 dataclass + 3 个函数 |

`dataset.py` 的四个出口：

| 对象 | 位置 | 作用 |
| --- | --- | --- |
| `DATASETS_DIR` | **L33** | 评测集目录基准路径 |
| `EvaluationCase` | **L36-65** | `@dataclass(frozen=True)`，七个字段的**只读契约** |
| `list_datasets()` | **L68-107** | 扫目录列清单（**廉价**） |
| `load_dataset(name)` | **L110-181** | 按名加载并逐行校验（**昂贵**） |
| `_parse_case(...)` | **L186-239** | 单行映射为强类型（**私有纯函数**） |

### 4.2 ⭐ 设计要点一：**"廉价问条数"与"昂贵真解析"分成两个函数**

这两件事看似重复（都要读文件），但**成本与用途完全不同**：

| | **`list_datasets()`** L68 | **`load_dataset(name)`** L110 |
| --- | --- | --- |
| 目的 | 便宜地问"有多少条" | 昂贵地**真解析**成对象 |
| 读文件方式 | 逐行读**但不解析** | 逐行读**且每行 `json.loads`** |
| 闸门数 | 1 个（目录是否存在） | **3 个**（文件存在 / 空行跳过 / JSON 合法） |
| 失败出口 | **0 个** | **2 个** |
| 成本 | **与行数无关的量级**（纯文本行扫描） | **与行数成正比** |
| 谁用 | 前端**下拉选单** + 固化 `dataset_size` | 第 6 步**执行器** |
| 定位 | **L87** `sorted(DATASETS_DIR.glob("*.jsonl"))` | **L127** `DATASETS_DIR / f"{name}.jsonl"` |
| 计数/解析 | **L99** `sum(1 for line in f if line.strip())` | **L159** `json.loads(line)` |

**教程原话**：若每次查进度都重新数一遍文件，
一旦评测集在跑的过程中被改动，进度条就会算错（甚至出现大于 100% 的情况）。

> ⭐ **本节最值得记住的对照**：**同样是逐行读文件，一个只数行、一个逐行解析。**
> 图二与图三并排看，就能一眼明白"为什么要有两个函数"。

### 4.3 设计要点二：`list_datasets()` 的两处防御

| # | 防御 | 位置 | 为什么 |
| --- | --- | --- | --- |
| **1** | **目录不存在 → 返回 `[]`** | **L81-82** | 服务冷启动 / 本地未配置评测集目录时，**不该直接崩** |
| **2** | **`sorted(...)` 遍历** | **L87** | **不同操作系统的文件系统遍历顺序不同** → 不排序会让**前端下拉列表顺序漂移** |

**顺带一处细节**：只数**非空行**（**L99** `if line.strip()`）——
**容忍人工排版留白**，否则进度条分母会偏大。

### 4.4 设计要点三：包结构（含一处**补强**）

```
app/evaluation/__init__.py            ← 空文件（教程要求）
app/evaluation/datasets/__init__.py   ← 空文件（教程未要求，本项目补强）
```

**补强 `datasets/__init__.py` 的理由与代价**：

| | 说明 |
| --- | --- |
| **收益** | `datasets` 从"隐式命名空间包（PEP 420）"变成**普通包** —— 对打包、IDE 索引、`importlib.resources` 都更可靠 |
| **代价** | 与项目既有风格略有出入（`app/ingestion/` 至今**没有** `__init__.py`，用的就是命名空间包机制） |
| **结论** | 无害且更好，**保持现状** |

**路径定位方式**（**L33**）：

```python
DATASETS_DIR = Path(__file__).resolve().parent / "datasets"
```

**为什么这里可以放心用 `__file__`**：
`dataset.py` 是**普通模块**（不是命名空间包），**普通模块一定有 `__file__`**。
（曾担心过"命名空间包没有 `__file__`"，但那只针对**包本身**，对包内模块不成立。）

### 4.5 🔴 设计要点四：**三层错误归一化**（本节设计价值最高的一处）

评测集是**人工维护**的 jsonl —— **手写必然出错**（漏逗号、括号没闭合、键名敲错）。
若只抛一个笼统的"格式错误"，**面对几百行的文件只能靠二分法逐行排查**。

**所以本模块建立了"精确到行号 + 精确到字段名"的错误感知体系**：

| 层 | 出错情形 | 抛出 | 位置 | 报错带的定位信息 |
| --- | --- | --- | --- | --- |
| **第 1 层 · 文件层** | 评测集文件不存在 | `NotFoundError` | `load_dataset` **L131** | **评测集名** |
| **第 2 层 · 行级语法层** | 某行 JSON 语法非法 | `ValidationError` | `load_dataset` **L171** | **第 N 行** + 原始错误 |
| **第 3 层 · 字段契约层** | 必填字段缺失 | `ValidationError` | `_parse_case` **L237** | **第 N 行** + **缺失的键名** |

**报错样例（实测）**：

```
NotFoundError:    评测集不存在: no_such_dataset
ValidationError:  评测集 bad_json 第 2 行 JSON 非法: Expecting value
ValidationError:  评测集 missing_field 第 1 行缺失字段: id
```

> ### 🎯 **"第几行 + 哪个键"这两个信息，把"二分法排查"变成"一眼定位"。**
> 这是本节最值得带走的工程实践。

**异常最终怎么变成 HTTP 响应**（**跨层，不是顺序执行**）：

```
函数内 raise  →  沿调用栈【弹出】  →  app/api/error_handlers.py 捕获 AppException
                                    →  翻译为对应 HTTP 响应
```

> ✅ **口径已统一（本节实施时修正）**：`load_dataset` 的 docstring 与注释原来写
> "对外返回 **HTTP 422**"（**照抄教程原文**），与本项目实际不符 ——
> **本项目 `ValidationError.http_status = 400`**（见 `app/core/exceptions.py` **L77 / L81**）。
> **已把 3 处 422 改为 400**（`dataset.py` **L117 / L122 / L169**）。
>
> **为什么会有这个偏差**：教程把"**Pydantic 参数校验返回 422**"与
> "**业务 `ValidationError` 返回什么**"混在一处写了。**两者不是同一件事**：
>
> | 路径 | 状态码 | 谁来产生 |
> | --- | --- | --- |
> | **我们的业务异常**（`AppException` 体系） | `ValidationError` → **400** / `NotFoundError` → **404** | `app/api/error_handlers.py` |
> | **FastAPI 的请求参数校验**（Pydantic） | **422** | 框架内建，**进函数之前**就返回 |
>
> ⚠️ **所以仓库里那些 422 是对的、不要一起改**：
> `app/api/routes/chat.py` **L173 / L188**（`Query(ge=1)` 越界）描述的就是**框架行为**；
> Day04 / Day08 归档里记的 `page=0 → 422` 也是**实测过的框架事实**。

### 4.6 设计要点五：`_parse_case` 的**字段策略**

| 字段 | 策略 | 位置 | 为什么 |
| --- | --- | --- | --- |
| **`id` / `question`** | **直接索引 `data["id"]`** —— **Fail-Fast** | **L212-213** | 缺了这条样本就**失去执行主体与标识**，立即 `KeyError` 阻断 |
| `expected_answer` | `get(..., "")` | **L217** | 拒答类样本**本来就没有详细标准答案** |
| 三个列表字段 | **`get(...) or []`** 双重防御 | **L223-224 / L229** | ⭐ **不只防"键缺失"，还防手写 `"tags": null`** |
| `should_refuse` | `get(..., False)` + `bool(...)` | **L228** | 绝大多数样本都是"应该回答"；`bool()` 保证结果一定是 `True`/`False` |
| 全部字段 | **`str(...)` / `list(...)` 类型强制** | 各处 | 防止 JSON 里写了数字 ID（如 `"id": 1001`）导致后续比较逻辑出错 |

**⭐ `or []` 那个双重防御值得单独记**：

```python
data.get("tags", [])        # ❌ 挡不住显式 null → 拿到 None → list(None) 抛 TypeError
data.get("tags") or []      # ✅ None 与缺失都变成 []
```

**`frozen=True` 的意义**（**L36**）：

```
评测执行过程中【任何人都改不了它】 → 保证实验可复现、基线纯洁
    ↓
试图修改会抛 FrozenInstanceError（已实测）
```
