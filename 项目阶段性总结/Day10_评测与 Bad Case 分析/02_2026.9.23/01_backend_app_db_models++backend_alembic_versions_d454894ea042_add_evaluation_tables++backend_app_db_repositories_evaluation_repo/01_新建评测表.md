**用一次班级考试打比方**：

| 表 | 一行代表 | 存什么 |
| --- | --- | --- |
| `evaluation_runs` | **一场考试** | 考什么卷子、多少人、跑到第几个了、班级平均分 |
| `evaluation_items` | **一个学生的答卷** | 题目、标准答案、**他实际写的答案**、得分、错在哪一类 |

## 四、4 个值得记住的设计决策

### 决策 1 · 为什么明细表要**复制**题目与标准答案？

`expected_*` / `question` 原本在评测集文件（jsonl）里，**入库时抄一份**：

```
若只存"评测集文件名 + 第几行"的引用：
    评测集改版（换标准答案 / 删掉一条）
        ↓
    老 run 的成绩单就对不上了 —— 当时它凭什么是 60 分？说不清
```

- **代价**：一点冗余存储
- **收益**：**每一轮评测永远可复现**，评测集怎么改都不影响历史对比

> 代码里写的是【快照设计原则】：**"确保每一次评测历史都是闭环且完全可重现的静态沙盒。"**
>
> 🔁 **本项目同源先例**：第 6 期引用落库时也快照了 `document_name` / `quote`
> （原文被删后引用仍可展示）。**同一原则：跨时间对比的数据，必须把"当时的样子"存下来。**

### 决策 2 · 为什么仓储**只 `flush` 不 `commit`**？

这是**整个评测能不能看到进度条**的关键：

```
后台任务跑 100 条 case
    ↓
若等全部跑完才一次性 commit：
    前端每 5 秒轮询 → 进度永远是 0/100 → 最后突然跳到 100/100
    ↓
若每条跑完就 commit 一次：
    轮询能看到 1/100、2/100 … 进度条真的在动
```

**所以"提交时机"必须由执行器掌握，仓储不能自己抢先提交。**

> `flush` vs `commit` 的区别（仓储注释里解释得很清楚）：
> - **`flush()`**：把内存变更转成 SQL 发给数据库，拿到回填的主键与默认值，**但不结束事务**
> - **`commit()`**：真正落盘并关闭事务 —— **仓储擅自 commit 会破坏外层的长链事务原子性**
>
> 🔑 **一句话**：**"能看进度"不是自然有的，是设计出来的。**

### 决策 3 · 删 run 时那些明细怎么办？

```
删掉一场考试 → 它的 100 份答卷应自动消失
```

**双重保障**：

| 层 | 机制 | 作用 |
| --- | --- | --- |
| **数据库** | 外键 `ondelete="CASCADE"` | PostgreSQL 用外键索引高效级联抹除子行 |
| **ORM** | `cascade="all, delete-orphan"` + **`passive_deletes=True`** | 指示 SQLAlchemy **信任数据库端**，别把成百上千条子项先 SELECT 进内存再逐条 DELETE |

> **没有 `passive_deletes=True` 的后果**：ORM 会先把子行全部加载进内存 ——
> 100 条没事，10 万条就是内存暴涨 + 性能骤降。

### 决策 4 · 为什么排序要 `created_at` **加** `id`？

```python
.order_by(EvaluationRun.created_at.desc(), EvaluationRun.id.desc())
```

**单用 `created_at` 不够安全**：同一事务/高并发批量创建时，
**完全可能产生相同的时间戳**（PostgreSQL 的 `now()` 返回**事务开始时刻**）。
排序列不具备唯一性 → **翻页时出现"漏看"或"重复看到"的幽灵分页**。

> ⚠️ **本项目实测过的真实现象**：同一事务 `bulk_add` 3 条，`created_at` 全部相同，
> 此时排序退化为按随机 UUID 的 `id`。
> **生产路径（每条 case 单独提交）不受影响** —— 每条拿到独立时间戳。
> 但若将来改成"一次性批量插入"，这里的排序稳定性就会成为问题。

| `downgrade()` | L120 | 反向删除（先删索引 → 子表 → 父表） |

### 5.2 🔴 差点删掉两个索引的坑

初次 `autogenerate` 生成的迁移里，**除了本期两张表，还多了两条**：

```python
op.drop_index('ix_document_chunks_content_tsv')      ← 全文检索 GIN 索引
op.drop_index('ix_document_chunks_embedding_hnsw')   ← 向量近邻 HNSW 索引
```

**这两个索引在数据库里真实存在**（实测 `pg_indexes`）：
```
ix_document_chunks_content_tsv      CREATE INDEX ... USING gin (content_tsv)
ix_document_chunks_embedding_hnsw   CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)
```

**为什么 autogenerate 说它们该删**：
**Alembic 的自动比对"看不见"GIN / HNSW 这类特殊索引方法与表达式索引** ——
模型侧从来没声明过它们，比对器就以为"数据库里有、模型里没有 → 应该删"。

> ### ⚠️ 若照抄执行：**全文检索索引与向量近邻索引被真的删掉** ——
> **混合检索当场退化成全表扫描，而且不报错、不崩溃，只是变慢变差。**

### 5.3 修法：**治本，而不是每次手工删那两行**

**教程给的方案**：在 `DocumentChunk` 里补 `__table_args__`，把两个索引**显式声明**出来。

```python
class DocumentChunk(Base):
    __tablename__ = "document_chunks"

    __table_args__ = (
        Index(
            "ix_document_chunks_embedding_hnsw",
            "embedding",
            postgresql_using="hnsw",
            postgresql_ops={"embedding": "vector_cosine_ops"},
        ),
        Index(
            "ix_document_chunks_content_tsv",
            "content_tsv",
            postgresql_using="gin",
        ),
    )
```

**效果实测**：

| 漂移项 | 声明前 | **声明后** |
| --- | --- | --- |
| `remove_index ix_document_chunks_content_tsv` | 🔴 有 | ✅ **消失** |
| `remove_index ix_document_chunks_embedding_hnsw` | 🔴 有 | ✅ **消失** |
| `modify_nullable/comment content_tsv` | 有 | 顺带对齐 |
| `modify_comment answer_citations.retrieval_meta` | 有 | 顺带对齐 |

**最终**：
```
alembic check  →  No new upgrade operations detected.
```

> 🎯 **我原来的做法是"每次手工裁掉那两行"（治标）；
> 教程的做法是"让模型认识这两个索引"（治本）—— 以后任何人跑 autogenerate 都不会再踩。**
>
> **这是本节最有价值的产出，而且它修的是跨期历史隐患（第 6 期的索引），不是本期功能。**

### 5.4 顺带对齐的两处**长期漂移**（都不是本期功能）

| # | 改了什么 | 为什么安全 |
| --- | --- | --- |
| 1 | `document_chunks.content_tsv` → **NOT NULL** + 补列注释 | 该列是数据库自动维护的**生成列**；**实测 259 行无 NULL**，改约束不重算数据 |
| 2 | `answer_citations.retrieval_meta` 的**列注释文案**对齐 | 纯文字，零风险 |

> ⚠️ 第 1 条**动之前先查了** `WHERE content_tsv IS NULL` 的行数 = **0**，
> 否则 `ALTER ... SET NOT NULL` 会直接失败。

### 6.3 ⭐ 两条贯穿仓储的设计约定

#### ① 读写口径分治（Batch vs Page）

| 方法 | 消费者 | 要求 |
| --- | --- | --- |
| `list_by_run()` | **自动化评估器**（喂 RAGAS） | **样本绝对完整**、顺序严格一致 → **严禁分页** |
| `list_page()` | **前端控制台**（排查坏例） | 低延迟、小吞吐、分页稳定 → **支持多维过滤** |

> **为什么不合并成一个方法**：批量评估要"拿全"，页面展示要"拿一页"，
> 混在一起容易两头不讨好。（代码注释原话："No Pagination by Design"）

#### ② 参数强制钳制（Parameter Clamping）

```python
page = max(page, 1)
page_size = max(min(page_size, 100), 1)
```

**即使上层 Schema 已校验，仓储也要自主设防** ——
因为它可能被**数据修复脚本、离线 Worker** 直接调用。
`page=0` 会产生负 offset 让 SQL 崩溃；`page_size=10000` 会拖垮连接池。

#### ③ `filters` 必须被数据查询与总数统计**共享**

```python
filters = [EvaluationItem.run_id == run_id]
if bad_case_only:  filters.append(...)
if category:       filters.append(...)

stmt       = select(...).where(*filters)   # 数据
total_stmt = select(count).where(*filters) # 总数 ← 同一套 filters
```

> **若总数漏掉了 `category` 条件**：前端算出的总页数偏大 →
> **用户翻到末尾页会看到大面积空白。**

## 八、本节的"额外收获"

修 `__table_args__` 时**顺带拆掉了一个定时炸弹**：

> **原来每次 `alembic revision --autogenerate` 都会生成两条 `op.drop_index(...)`**，
> 分别指向**全文检索 GIN 索引**与**向量近邻 HNSW 索引**。
> **照抄执行会把它们真的删掉，而且不报错。**
>
> 现在模型里显式声明了这两个索引，**`alembic check` 输出零漂移** ——
> **以后任何人跑 autogenerate 都不会再踩这个坑。**

**同时给 `models.py` 的模块注释做了一次大修**：

| | 修改前 | 修改后 |
| --- | --- | --- |
| 覆盖的类 | **3 个** | **12 个**（全部） |
| 覆盖的表 | 2 张 | **8 张**（全部） |
| 架构特性 | 3 条 | **6 条**（新增：输入快照 / 调试卷随行 / **索引显式声明**） |

> 修改前那段注释从第 2 期起就已失准（漏了 UploadSession / Conversation / Message /
> AnswerCitation 等 5 张表）。**已按"业务域分组"重写，12 个类全部列出。**
>
> 💡 **可固化的习惯**：**凡是给 `models.py` 加表，同步更新模块注释的职责清单。**
