## 一、本章在整条链路里的位置

> **第 11 章的鉴权只解决了"谁能调"，没解决"能调多少次"。**
> **这一节补的正是后面这一维。**

```

                                ↓

                                ↓
本节 滑动窗口限流          →  每个用户每分钟最多 N 次，超了 429
```

### 1.1 为什么"重"接口必须自己限流

```
/chat             一次调用 = 1 次 embedding + 2 次检索 + 1 次 rerank + 1 次 LLM 生成
                            每一项都在真金白银地花钱（token 按量计费）
/upload           一次调用 = 落 COS + Docling 解析 + 上百次 embedding + 落库
                            算力密集，且会长时间占用后台任务
        ↓
它们不能只靠"登录鉴权"保护 —— 合法用户的误操作或恶意刷接口，
都能在几分钟内把额度与算力吃光。
```

## 二、算法：Redis Sorted Set 滑动窗口

### 2.1 为什么用 Sorted Set（而不是计数器）

```
固定窗口计数器（你想省事时最可能写的版本）：
    每个 key 记一个整数，每次 +1，60 秒后清零
        ↓
    问题：临界点双倍放行
        用户在 00:59 发 60 次（窗口边界前）
        在 01:00 再发 60 次（新窗口开始）
        → 2 秒内实际放行 120 次，而"每分钟 60 次"的本意被绕过

滑动窗口（Sorted Set）：
    把【每次请求的时间戳】都记下来
    每次请求先清掉"60 秒之前"的记录，再数剩下的
        ↓
    任意时刻看到的都是"过去 60 秒"的真实次数 → 没有临界点漏洞
```

> ⭐ **一句话**：**计数器只记"次数"，Sorted Set 记"每次是什么时候"** ——
> 后者才能在任意时刻回答"最近 60 秒内到底有多少次"。

### 2.2 四条命令，一个 pipeline

```python
async with self._redis.pipeline(transaction=True) as pipe:
    await pipe.zremrangebyscore(key, 0, now - _WINDOW_SECONDS)   # ① 清窗口外
    await pipe.zcard(key)                                        # ② 数窗口内
    await pipe.zadd(key, {str(uuid4()): now})                    # ③ 记本次
    await pipe.expire(key, _WINDOW_SECONDS)                      # ④ 续 TTL
    _, count, _, _ = await pipe.execute()
```

| # | 命令 | 职责 | 少了它会怎样 |
| --- | --- | --- | --- |
| ① | `zremrangebyscore key 0 now-60` | 清掉 60 秒前的成员 | 集合无限增长，`zcard` 永远超限 → **第 61 次之后永久被拒** |
| ② | `zcard key` | 数窗口内当前请求数 | 无从判断是否超限 |
| ③ | `zadd key {uuid: now}` | 把本次请求记进去 | 限流永远放行 |
| ④ | `expire key 60` | 给 key 续 60 秒 TTL | **每个来访过的用户都会在 Redis 里留下一个永不过期的 key** |

### 2.3 ⚠️ 三个容易看错的细节

**细节一：为什么 `expire` 是"每次都要续"，而不是"只在第一次设"**

```
限流 key 是临时数据：
    活跃用户每次请求都续上 60 秒 → 窗口始终有效
    冷用户停止请求 60 秒后 key 自动过期消失 → Redis 里不留垃圾
        ↓
若不续（或只在第一次设）：用户 60 秒后 key 就没了，
    他下次请求时窗口被重置 —— 相当于"每 60 秒白送一个满额窗口"，
    只要卡着这个节奏就能绕过限流
```

**细节二：为什么 `zcard` 必须排在 `zadd` 之前**

```
zcard 拿到的是【本次请求加入之前】的数量
        ↓
所以判定条件写成  count >= limit  （而不是 > limit）
        ↓
若顺序反了（先 zadd 再 zcard），拿到的是"含本次"的数量，
判定就该写 > limit —— 两个地方必须配套改，改漏一处就少限一次或多限一次
```

**细节三：为什么 member 用 `uuid4()` 而不是时间戳**

```
Sorted Set 的 member 必须唯一
        ↓
若用 str(now) 当 member：同一微秒内的两次并发请求会被当成【同一个成员】，
    zadd 只保留一条 → 计数偏小 → 【限流放水】
        ↓
uuid 保证每次插入都是新成员；score 仍用 now，排序与范围清理靠它
```

### 2.4 为什么必须 `pipeline(transaction=True)`

```
这四条命令是"读—改—写"的组合：先数、再写、还要设过期
        ↓
若逐条单独发送：
    两个并发请求可能同时读到 count=59，然后各自都判定"没超限"
        → 双双放行
        → 限流在最需要它的时候（突发并发）恰好失效
        ↓
pipeline(transaction=True) 底层走 MULTI / EXEC：
    四条命令打包成【一次网络往返】、【服务端原子执行】，
    中间不会被其它客户端插队
```

> 📌 顺带一个性能收益：**一次网络往返**而非四次 ——
> 限流要在每个重接口前执行，往返次数直接影响每请求的额外延迟。

## 四、挂在哪些接口上（教程明确划分）

| 类别 | 接口 | 挂限流？ | 理由 |
| --- | --- | --- | --- |
| **写 / 重操作** | `POST /conversations/{id}/chat` | ✅ 挂 | 烧 token（embedding + rerank + LLM） |
| | `POST /documents`（**旧** multipart 上传） | ✅ 挂 | 烧算力（解析 + 上百次 embedding） |
| | ★ `POST /documents/uploads/init`（**直传**） | ✅ 挂 | 会签出一枚有效的 COS 预签名 URL（300 秒内可往桶里写对象） |
| | ★ `POST /documents/uploads/{id}/complete`（**直传**） | ✅ 挂 | 建档 + 触发解析流水线 |
| | ★ `DELETE /documents/uploads/{id}`（**直传**） | ⚠️ **只鉴权，不限流** | 低频操作（取消上传才触发），不是"烧钱"的重操作 |
| | `reindex`（第 6 节做） | ✅ 挂 | 与上传同属重操作 |
| **读接口** | `list_documents` / `get_document` / `list_conversations` … | ❌ **不挂** | 前端文档列表有 **3 秒轮询**，给读接口限流会**误伤正常用户**（光靠轮询就把自己限住） |
| **匿名 / API Key** | 将来的 MCP 入口 | ⏭ 留给第 13 章 | 没有 user_id，需要另一套维度 |

> 🔴 **"读接口不挂"这条是本节最容易做错的地方**：
> 直觉上"限流当然是越全越好"，但**轮询会让正常用户触发限流** ——
> 那是最糟的误伤：用户什么都没做错，只是开着页面。

```
    浏览器直传 COS，文件不经过服务器

```

## 五、代码结构（三个文件）

### 5.1 `core/rate_limiter.py`（新增）

```
_WINDOW_SECONDS = 60                    窗口固定 60 秒
class RateLimiter
    ├── __init__   取 get_redis()（复用第 2 章的应用侧客户端，连 db0）
    └── check(identity)   四步 pipeline + 判定，超限抛 RateLimitError
get_rate_limiter()  lru_cache 单例
```

**窗口长度为什么不做成可配置**：

```
RATE_LIMIT_PER_MINUTE 这个名字里就写着 "PER MINUTE"
        ↓
若窗口可配（比如 30 秒），这个名字就名不副实了
    —— 30 秒窗口下它实际是"每半分钟 N 次"
        ↓
要调频率就调 N，不要调窗口
```

**为什么按 identity（user_id）而不是按 IP**：

```
本项目所有业务接口都要求登录（第 11 期 CurrentUser），用户身份可靠
        ↓
而 IP 在 NAT / 代理 / 移动网络下会被大量用户共享 → 按 IP 限流容易误伤
        ↓
匿名入口（将来的 MCP / API Key）没有 user_id，那类限流留给后续章节
```

### 5.2 `api/deps.py`（修改）

```python
async def enforce_rate_limit(
    user: Annotated[User, Depends(get_current_user)],
) -> None:
    if not settings.rate_limit_enabled:
        return
    await get_rate_limiter().check(f"user:{user.id}")

RateLimited = Annotated[None, Depends(enforce_rate_limit)]
```

**为什么依赖里要 `Depends(get_current_user)`**：

| 好处 | 说明 |
| --- | --- |
| **顺序天然正确** | FastAPI 先解析当前用户、再执行本函数，所以走到限流时 `user` 一定就绪 |
| **匿名请求不占配额** | 未登录在 `get_current_user` 那步就 401 了，**根本进不到限流逻辑** |

> 📌 **同一请求不会解析两次令牌**：FastAPI 的依赖缓存让 `get_current_user`
> 在一次请求内只执行一次 —— 路由里再声明 `CurrentUser` 也是复用同一结果
> （实测确认：未登录请求返回 **401 而不是 429**）。

### 5.3 两个路由（修改）

```python
async def stream_chat(
    conversation_id: UUID,
    user: CurrentUser,
    _rate_limit: RateLimited,        # ← 新增
    payload: ChatRequest,
    session: DbSession,
) -> AsyncIterable[ServerSentEvent]:
```

**下划线前缀的含义**：约定"函数体里不用这个值"。
**但它绝不影响依赖执行** —— 超限时照样在**进入函数体之前**抛 429。

## 六、⚠️ 一个要知道的行为特性：被拒绝的请求也会被计数

**这是我在验证时实测出来的**，不是 bug，而是这个写法的自然结果：

```
四步 pipeline 里，zadd 排在判定【之前】就已经执行了
        ↓
所以【被拒绝的那次请求也被记进了窗口】
        ↓
含义：一旦触发限流，持续重试会让窗口内始终保持超限状态，
      必须等到最早的记录滑出 60 秒窗口才会恢复
```

**为什么保留这个行为**：

| 视角 | 评价 |
| --- | --- |
| 对恶意高频请求 | ✅ **正是想要的** —— 越刷越被挡，不会因为"重试"而获得额外额度 |
| 对用户手抖连点 | ⚠️ 他停手后仍会最多再等一个窗口才恢复 |

**若要改成"拒绝时不计数"**：

```
需要把 zadd 挪到判定之后
        ↓
但那样就不能在同一个 pipeline 里完成了
    （必须"先读、判定、再写"两次往返）
        ↓
代价是失去原子性 —— 并发时又回到"双双读到 59、双双放行"的漏洞
        ↓
本项目按教程保留当前写法
```

> ⭐ **这个取舍值得记住**：**原子性 与 "拒绝不计数" 在当前算法下不可兼得**。
> 选了原子性，就接受了"拒绝也计数"。

## 七、验证结果（18 项全通过）

> 方式：真机 + 真实 Redis。算法层用**临时短窗口（2 秒）+ 临时低阈值（3）**
> 来快速验证，否则每个用例都要等 60 秒。

### 7.1 算法层（12/12）

```
阈值 3 时：
  ★ 前 3 次全部放行
  ★ 第 4 次被拒，code=rate_limited、HTTP 429、提示里带阈值
  ★ 限流 key 有 TTL（实测 ttl=2）—— 冷用户不会永驻 Redis
  ★ 不同 identity 互不影响（限流按 user 维度隔离）
  ★ 等待 2.1 秒窗口滑出后自动恢复放行
  ★ 总开关关闭时 enforce_rate_limit 直接放行
  ★ 开关打开时超限会真正抛 429
```

### 7.2 HTTP 层（6/6）

```
★ 未塞满窗口时返回 200（不是 429）
★ 把窗口塞到 61（阈值 60）后返回 429
   响应体：{"code":"rate_limited","message":"请求过于频繁，每分钟最多 60 次，请稍后再试"}
★ 响应 code 与 message 都正确
★ 未登录时是 401 而不是 429（认证先于限流）
★ 清空窗口后立刻恢复 200
```

### 7.3 回归（契约零变化）

| 项 | 结果 |
| --- | --- |
| OpenAPI 路径数 | **28**（不变） |
| operationId | **39 个且唯一**（不变） |
| `_rate_limit` 是否变成请求参数 | ❌ **没有** —— chat 的 parameters 仍只有 `conversation_id` 与 `Authorization` |
| upload 的 multipart 参数 | ✅ 仍是 `file` + `permission_tags` |
| 限流挂载点 | ✅ `chat.py` / `documents.py` / **`document_uploads.py`**（其中 `abort` 只鉴权不限流）；读接口未挂 |

### 7.4 直传链路补漏的验证（13/13）

> 发现过程与根因见 §4.1 与 `BUG发现与处理/02_2026.9.26/02_直传链路漏掉鉴权与权限标签.md` §十。

```
三种身份 × 三个端点：
    init      未登录 401 / 普通用户 403 / 管理员 200（前端带 token 所以不受影响）
    complete  未登录 401 / 普通用户 403
    abort     未登录 401 / 普通用户 403 / 管理员 204（清理成功）
★ 限流真的生效：塞满窗口后 init 与 complete 都返回 429
   响应体 {"code":"rate_limited","message":"请求过于频繁，每分钟最多 60 次，请稍后再试"}
契约：
    路径数仍 28、operationId 仍 39 且唯一
    ★ init 的 parameters 现在声明了 Authorization
```
