三、四条命令各自的职责

· zremrangebyscore key 0 now-60：清掉窗口外的旧时间戳，留下的就是过去 60 秒内的请求
  少了它：集合无限增长，zcard 永远超限，第 61 次之后永久被拒
· zcard key：数窗口内当前请求数；★ 它排在 zadd 之前，所以拿到的是本次加入之前的数量
· zadd key {uuid now}：记下本次请求
  member 用 uuid 而不是时间戳：同微秒并发会被当成同一成员而去重，导致计数偏小、限流放水
· expire key 60：每次请求都续 TTL
  少了它或只在第一次设：活跃用户 key 不再续期，他下次请求时窗口被重置，
  相当于每 60 秒白送一个满额窗口，卡着节奏就能绕过限流

四、为什么必须 pipeline(transaction=True)

· 四条命令是"读—改—写"组合：先数、再写、还要设过期
· 逐条单独发送时，两个并发请求可能同时读到 count=59、各自判定没超限 → 双双放行
  限流在最需要它的突发并发场景恰好失效
· MULTI / EXEC 把它们打包成一次网络往返、服务端原子执行，中间不会被插队
· 顺带收益：一次往返而非四次，降低每请求的额外延迟

五、为什么不用 slowapi / fastapi-limiter

· 现成装饰器是黑盒：限流 key 怎么拼、窗口怎么算、超限返回什么体都藏在库里
· 而滑动窗口算法本身是本节要展示的核心知识，自己写三十行逻辑完全透明
· 与第 11 期选 PyJWT、本节选 redisvl 的判断方向相反，但理由一致：
  看当下是在学原理还是用工具 —— 这里是在学原理

六、deps.py 的挂载方式

· enforce_rate_limit 依赖 get_current_user，两个好处：
  · 顺序天然正确：FastAPI 先解析用户再执行限流，所以能拿到稳定的 user_id 做维度
  · 匿名请求不占配额：未登录在 get_current_user 那步就 401，根本进不到限流逻辑
· RateLimited = Annotated[None, Depends(enforce_rate_limit)]
· 路由里写成 _rate_limit: RateLimited，下划线只表示函数体不用它的值，
  不影响 FastAPI 执行依赖 —— 超限时照样在进入函数体之前就抛 429

七、接口划分（教程明确要求）

· 挂：chat（烧 token）、upload（烧算力）、reindex（第 6 节做，同样烧算力）
· 不挂：list / get 等读接口
  原因是前端文档列表有 3 秒轮询，给读接口限流会误伤正常用户
  这是本节最容易做错的一处：直觉上"限流越全越好"，但轮询会让用户什么都没做错就被限住
· 匿名与 API Key 入口的限流留给第 13 章 MCP

八、一个行为特性（实测发现，非 bug）

· 四步 pipeline 里 zadd 排在判定之前就已执行，所以【被拒绝的请求也被记进窗口】
· 含义：一旦触发限流，持续重试会让窗口内始终超限，必须等最早记录滑出 60 秒才恢复
· 对恶意高频请求正是想要的效果（越刷越被挡）；对用户手抖连点则需多等一个窗口
· 若要改成"拒绝不计数"，就得把 zadd 挪到判定之后、拆成两次往返，牺牲原子性
  本项目按教程保留当前写法：原子性与"拒绝不计数"在当前算法下不可兼得

九、验证结果（18 项全通过）

· 算法层 12 项（用临时短窗口 2 秒 + 临时低阈值 3 快速验证，否则每例要等 60 秒）
  · 前 3 次放行、第 4 次被拒，code 与 429 与提示文案都正确
  · 限流 key 有 TTL、不同 identity 互不影响、窗口滑出后自动恢复
  · 总开关关闭时直接放行，打开时真正限流
· HTTP 层 6 项
  · 未塞满时返回 200；塞到 61 后返回 429，响应体是 rate_limited 与提示文案
  · 未登录返回 401 而不是 429（认证先于限流）
  · 清空窗口后立刻恢复 200
· 回归：OpenAPI 路径 28 与 operationId 39 均不变
  _rate_limit 没有变成请求参数，upload 的 multipart 参数仍为 file 与 permission_tags

十、补漏：直传链路的三个端点（用户提问时被连带发现）

· 触发：用户问「Day3 做的直传优化跟 Day12 的 Celery 有没有冲突」，
  核对两条上传链路时发现：限流只挂了旧 multipart 链路，漏了直传链路
· 为什么漏：教程说"挂在 upload 接口"，而 documents.py 里那个函数恰好就叫 upload_document，
  看起来完全对得上 —— 但前端实际上传走的是直传链路（directDocumentUpload.ts 调
  /uploads/init 与 /complete）。结果限流只保护了"前端不用的那条链路"
· ★ 这不是第一次：Day11 加鉴权时也漏了同一个模块（已归档在 BUG-02）
  根因相同：按【文件】对照，而不是按【协议端点】对照
· 修法
  · init 与 complete 补 CurrentAdmin + RateLimited
  · abort 只补 CurrentAdmin（低频操作，不是重操作，不挂限流）
  · 顺带更正 init_upload 下方一句错误注释：原写"由领域服务执行鉴权"，
    但服务层拿不到请求上下文、从来不做鉴权 —— 这句会让人以为鉴权已经做过了
· 验证 13 项全通过
  · init 401 / 403 / 200；complete 401 / 403；abort 401 / 403 / 204
  · 塞满窗口后 init 与 complete 都返回 429，响应体正确
  · 契约：路径 28 与 operationId 39 不变；init 的 parameters 现在声明了 Authorization
· 前端零改动：它一直带着 Bearer 令牌（requestJson 内部注入了 authHeaders），
  只是后端原先不验 —— 这也解释了"无鉴权"为什么一直没暴露
· 一条流程教训（比这个漏本身更重要）：
  做权限 / 限流这类横切改造时，从 OpenAPI 的端点清单逐个打钩，不要按文件排查
