四、为什么要有 ingestion_tasks 这张表

· documents.status 回答「这份文档现在什么状态」，只有一份，会被覆盖
· ingestion_tasks 回答「这一次尝试什么结果」，每次尝试一条，可累积
· 于是才能回答 documents.status 答不了的问题：失败过几次、排队了多久、上次错在哪
· progress_total / progress_done 是给前端进度条用的：
  向量化最慢，只暴露"运行中"会让进度条长时间僵住，用户分不清在跑还是卡死

五、★ 教程在这里埋了一个坑

· 教程让在迁移里补复合索引 ix_ingestion_tasks_document_created，
  但没有说要在 models.py 里同步声明它
· 而 Alembic autogenerate 只比对"模型推导结构"与"数据库实际结构"，
  迁移里建的、模型里没声明的索引会被当成"多出来的东西"，下次自动生成 drop_index 删掉
· 这正是教程自己在 4.2 开头解释 ix_documents_permission_tags 时讲的道理，却在几行后又犯一次
· 实测：不声明时 autogenerate 确实生成 drop_index；补上 __table_args__ 后重跑为 pass（零操作）

六、★ 实测撞到的 BUG（详见 BUG发现与处理/03_2026.9.27/03）

· 现象：按教程写法（每任务 asyncio.run）启动 worker，第 2 个任务必崩
  RuntimeError: Event loop is closed
  AttributeError: 'NoneType' object has no attribute 'send'
  结果 ingestion_tasks 永远 pending、documents.status 永远 uploading、一个 chunk 都没有
· 根因：两种生命周期长度对不齐
  · 事件循环的生命周期 = 一个任务（asyncio.run 跑完就关循环）
  · 被缓存资源的生命周期 = 整个 worker 进程（连接池、embedder 单例里的 httpx 池）
  · loop A 里建的连接被缓存，loop A 关闭，loop B 复用它 → 底层 socket 绑在已关闭的循环上
· 为什么难查：它不在第一次任务时出现；本次还额外伪装成过网络错误
  （openai.APIConnectionError: Connection error.），差点被误判成"代理抽风"
· 修法：app/db/session.py 新增 run_worker_coro，用【常驻事件循环】跑所有任务
  与其逐个清理被缓存的 I/O 资源（漏一个就复发），不如让循环常驻，
  资源与循环的绑定关系就永远成立
· 并发前提：常驻循环只对"单任务串行"成立 → worker 必须用 --pool=solo
  （Windows 上本来也用不了 prefork；真要 --pool=threads --concurrency=N 还得配 NullPool）

七、直传链路改造的两个技术点

· bound method 跨不过进程边界：self.finalize_upload 带着 self，
  broker 序列化不了；就算能序列化，worker 里也没有那个 self
  → 降级成模块级同步入口 run_finalize_upload_sync
· 循环依赖：document_upload_service 顶层 import tasks 拿 ingest_document_task，
  而 finalize_upload_task 需要 service → 把 service 的 import 放进任务函数体内
· 顺带修掉一个隐患：finalize_upload 原先挂在 BackgroundTasks 上，
  一次 uvicorn --reload 就会让它消失、会话永远卡在 FINALIZING；搬到 worker 后不再受影响

八、验证结果（全部真实数据）

· 直传链路（前端实际用的那条）2/2 通过，且故意连跑两份验证"第 2 个任务不再崩"

  任务台账从 1 行变成 2 行（首次 + 重试各一条，都是 success 5/5）—— 验证"流水式记录而非覆盖"

· 迁移与契约

  · documents.version 加列成功，12 行存量全部回填为 1

九、worker 启动命令（Windows）

· python -m celery -A app.celery_app worker -l info --pool=solo
  · Windows 用不了默认的 prefork 池，必须显式指定 solo
  · --pool=solo 同时也是"常驻事件循环"这个修法的前提条件
· ★ 本机需要先摘掉系统代理：$env:NO_PROXY="*"; $env:no_proxy="*"
  · 本机开着系统代理（127.0.0.1:7897），而 ProxyOverride 里没有百炼域名
  · 教程的启动命令里也带了 no_proxy="*"，就是为这种情况准备的
  · 不摘的话 embedding 请求会先走代理，代理侧一抖动就报 APIConnectionError，
    而那个报错样子很像代码 BUG，本次排查就被它误导过一次
· 教训：从这一节起，后端 API 启动但 worker 没启动时，上传会很快返回成功，
  但文档会一直停在 uploading / pending —— 任务不会真正解析、切分、向量化
  排查顺序：先看 worker 有没有起来，再看 ingestion_tasks 那一行的 status 卡在哪
