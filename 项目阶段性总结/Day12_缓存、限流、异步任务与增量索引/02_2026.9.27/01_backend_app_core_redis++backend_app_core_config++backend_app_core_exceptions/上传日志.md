三、配置（三组，共 11 个键）

· Redis 连接
  · REDIS_URL 走 db 0（应用侧：语义缓存与限流）
  · CELERY_BROKER_URL 走 db 1（待执行任务）
  · CELERY_RESULT_BACKEND 走 db 2（任务执行结果）
  · 分成三个逻辑库的理由：三者生命周期与清理策略完全不同
    缓存要清理时 FLUSHDB 会连带丢掉所有待执行任务
· 语义缓存：ENABLED / TTL_SECONDS / MIN_SIMILARITY
· 滑动窗口限流：ENABLED / PER_MINUTE

四、代码改动（3 个文件）

· backend/app/core/redis.py（新增）
  · get_redis() 用 lru_cache 保证进程内单例
  · 为什么单例：from_url 每次调用都新建连接池，多处各建会出现连接数翻倍、
    空闲连接分散、关闭时机不统一
  · decode_responses=True：读写自动以 str 处理，省掉全部手工编解码
  · 只连 db 0，Celery 的 broker 与 result backend 由 Celery 自己直连

· backend/app/core/config.py：新增 8 个字段
· backend/app/core/exceptions.py：新增 RateLimitError
  · 为什么不复用 PermissionDeniedError：403 是身份不够、重试无用；
    429 是频率超了、等一会重试有效。混在一起会让调用方误判而放弃重试

五、环境问题（已修复并单独归档）

· 症状：连通性验证时 MODULE 命令报 unknown command，redis_version 显示 3.0.504
· 根因：Windows 上装过原生 Redis 3.0.504，注册成服务且开机自启，一直占着 6379
  Docker 的 rag-kb-redis 端口映射登记成功却绑不上
· 误导点：容器一直 Up (healthy)，docker port 也显示正常，都不报错
  只有版本号与命令能力对不上这一条线索
· 修复：提权后 Stop-Service Redis 并 Set-Service -StartupType Disabled
  必须设 Disabled 而不只是 Stop，否则下次开机会再次抢走端口
· 修复后：redis_version=7.4.0，模块含 search / ReJSON / bf / timeseries / redisgears_2
· 归档：项目阶段性总结/BUG发现与处理/02_2026.9.26/03_Windows原生Redis抢占6379导致语义缓存不可用.md
