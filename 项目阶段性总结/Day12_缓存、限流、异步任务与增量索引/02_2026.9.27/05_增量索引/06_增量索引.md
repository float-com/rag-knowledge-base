## 〇、三分钟速览（先读这一节）

```
本节要解决的一件事：
        文档内容被替换了，怎么只重算【变了的那部分】的向量，而不是整篇重来？

本节用的唯一工具：
        chunk_hash —— 每个切片的内容指纹，当作切片的"身份证"

本节的核心算法（三句话）：
        旧有新没有 → DELETE
        新旧都有   → UPDATE（只改位置字段，不动 embedding）
        新有旧没有 → INSERT（只有它需要重算 embedding）

本节的实测收益（真实数据）：
        末尾追加一点内容   → 6 个切片只有 1 个需要重算（省 83%）
        文档中部大改       → 6 个切片有 5 个需要重算（几乎没省）
        ★ 所以增量的收益完全取决于"改动有多局部"，不是无条件的

本节最该记住的两句坑话：
        教程说"覆盖到同一个 object_key" → 本项目是内容寻址，key 会变，旧对象成了孤儿
        教程的 await 写法 → 优先级写反，必崩（潜伏了一整节才被发现）
```

## 一、本章在整条链路里的位置

### 1.1 第 4 节与第 5 节的分工

```
第 4 节（Celery）      文档第一次进来        → ingest_document   全量
第 5 节（增量索引）    文档内容被人替换了    → reindex_document  增量
```

一句话：**第 4 节管"从无到有"，这一节管"从有到新"。**

### 1.2 新增的两个入口，对应两个阶段

```
POST /api/documents                 上传【新文档】 → 新建 Document 记录

```

两个入口别混淆 —— 它们的 multipart 请求体长得几乎一样（都只有一个 `file` 字段），
区别只在"落到哪个资源上"。

## 二、`chunk_hash`：本节唯一用到的工具

### 2.1 它在哪产生

```
parser.parse()    →  Docling 解析出纯文本
splitter.split()  →  切分，并给每个切片注入两个元数据：
                        chunk_index  该切片在文档中的序号（0,1,2...）
                        chunk_hash   该切片【正文】的指纹
```

`chunk_hash` 就是切片正文的哈希。**正文一样，hash 就一样；正文变一个字，hash 全变。**

### 2.2 为什么它能当"身份证"

因为我们真正关心的不是"这段文字在第几段"，而是"**这段文字我算过向量没有**"。
向量只取决于正文内容：

```
正文相同 → 向量必然相同 → 可以直接复用旧向量，不必再调一次收费的 embedding 接口
```

于是"内容有没有变"这个问题，就被 `chunk_hash` 精确回答了。

### 2.3 ⚠️ 它的边界：hash 相同 ≠ 位置相同

这是最容易踩的一处认知偏差：

```
hash 相同   →  正文没变，向量可以复用
hash 相同   ✗→  位置也没变
```

**完全可能出现**：文档改了一小段，导致后面某段被挪到了别的章节、页码也变了，
但那段的文字一字未改 —— 它的 hash 不变，**可它的 `chunk_index` / `page_no` /
`section_path` 变了**。

这三个字段是检索结果回显"这段出自第几页、哪一章"的**唯一依据**。
不更新的话，用户点开引用会跳到错误的章节 —— **内容对、位置错**，
比直接报错更难被发现。这就是下一节"UPDATE 分支"存在的全部理由。

## 三、对齐算法（本节核心）

### 3.1 三分类规则

```
old 里有、new 里没有的 hash   →  DELETE    这段内容被删了
new 里有、old 里也有的 hash   →  UPDATE    内容没变，只更新位置与元数据
new 里有、old 里没有的 hash   →  INSERT    新增内容，需要算 embedding
```

### 3.2 代码逐段讲解（`_run_incremental`）

```python
async def _run_incremental(
    document_id: UUID, task_id: UUID,
    old_chunks: list[DocumentChunk],       # 从数据库拉出来的旧切片
    new_chunks: list[LangChainDocument],   # 刚解析切分出来的新切片
) -> None:
    # ---------- 第一步：把两边都变成"按 hash 索引"的结构 ----------
    old_by_hash: dict[str, DocumentChunk] = {c.chunk_hash: c for c in old_chunks}
    new_hashes: set[str] = {c.metadata["chunk_hash"] for c in new_chunks}
    #    old_by_hash 是【字典】：既用来判断"命中没有"，也用来拿到"命中的那条旧记录"
    #    new_hashes  是【集合】：只用来判断"某个旧 hash 还在不在新集合里"

    # ---------- 第二步：算出要删的 ----------
    to_delete_ids: list[UUID] = [
        c.id for c in old_chunks if c.chunk_hash not in new_hashes
    ]

    # ---------- 第三步：把新切片分成"要插入"和"要更新"两堆 ----------
    to_insert: list[LangChainDocument] = []
    to_update: list[tuple[DocumentChunk, LangChainDocument]] = []
    for nc in new_chunks:
        h = nc.metadata["chunk_hash"]
        existing = old_by_hash.get(h)
        if existing is None:
            to_insert.append(nc)          # 没见过 → 新增，要算 embedding
        else:
            to_update.append((existing, nc))   # 见过 → 命中，只更新位置

    # ---------- 第四步：只对"新增"的那批算 embedding ----------
    await _set_task_total(task_id, len(to_insert))     # ★ 进度分母 = 新增数
    new_embeddings = await _embed_with_progress(
        [c.page_content for c in to_insert], task_id
    )

    # ---------- 第五步：删 / 改 / 插，同一个事务一次提交 ----------
    async with AsyncSessionLocal() as session:
        chunk_repo = DocumentChunkRepository(session)
        await chunk_repo.delete_by_ids(to_delete_ids)

        for old, nc in to_update:          # 只改位置/段落元数据，不碰 embedding 列
            old.chunk_index = nc.metadata["chunk_index"]
            old.page_no = nc.metadata.get("page_no")
            old.section_path = nc.metadata.get("section_path")
            old.extra_metadata = nc.metadata

        await chunk_repo.bulk_add(         # 新增的这批带上刚算好的向量
            [_make_chunk(document_id, c, vec)
             for c, vec in zip(to_insert, new_embeddings, strict=True)]
        )
        await session.commit()
```

几个容易忽略的点：

| 细节 | 为什么 |
| --- | --- |
| `old_by_hash` 用字典、`new_hashes` 用集合 | 前者要"取出旧对象"，后者只判断存在性。用集合去重更快，但取不到对象 |
| `zip(..., strict=True)` | 不加的话长度不等会**静默截断**，少写切片且不报错 |
| 三个操作同一个 `session` / 一次 `commit` | 中途失败要整体回滚，否则留下"旧的删了新的没写"的空档 |
| 更新时**不动** `embedding` 列 | 内容没变 → 向量必然有效，重算纯属浪费钱 |

### 3.3 ★ 手算实例（真实数据）

**实例 A：末尾追加一点内容（增量的最佳情况）**

```
v1（5 片，全量入库，台账 progress=5/5）
    idx=0  ee84147e
    idx=1  3bfec216
    idx=2  644f0405
    idx=3  3bf6a6df
    idx=4  d6362800

v2（在 v1 末尾追加 1 段）
    idx=0  ee84147e   命中      ← 原有内容一段没动
    idx=1  3bfec216   命中
    idx=2  644f0405   命中
    idx=3  3bf6a6df   命中
    idx=4  d6362800   命中
    idx=5  <新 hash>  INSERT

    分类：DELETE=0   UPDATE=5   INSERT=1
    台账 progress_total = 1        ← 只为这 1 个切片付了 embedding 的钱
    chunks：5 + 1 = 6   ✅
```

**这一次的收益：6 个切片里只重算 1 个 —— 省下 83% 的 embedding 成本。**

---

**实例 B：文档中部大改（增量几乎无效的情况）**

真实采集数据（脚本让新版本同时"删掉中间若干行"+"追加新段落"）：

```
v1（5 片）
    idx=0  ee84147e
    idx=1  3bfec216
    idx=2  644f0405
    idx=3  3bf6a6df
    idx=4  d6362800

v2（删掉中部 8 行 + 追加 2 段）
    idx=0  ee84147e   命中       ← 只有标题那一片活了下来
    idx=1  9a1391c8   INSERT
    idx=2  50654bd8   INSERT
    idx=3  f5e665ca   INSERT
    idx=4  271cb499   INSERT
    idx=5  dd62aaa4   INSERT

    分类：DELETE=4   UPDATE=1   INSERT=5
    台账 progress_total = 5        ← 几乎等于全量重算
    净变化检查：5 - 4 + 5 = 6  = 实际 6   ✅

v3（再删中部 6 行 + 追加 2 段）
    idx=0  ee84147e   命中       ← 又是只有标题活下来
    idx=1  03fcf1ed   INSERT
    idx=2  da25cfba   INSERT
    idx=3  837f79d6   INSERT
    idx=4  bede9dc6   INSERT

    分类：DELETE=5   UPDATE=1   INSERT=4
    台账 progress_total = 4
    净变化检查：6 - 5 + 4 = 5  = 实际 5   ✅
```

**★ 这一组数据揭示了一件比算法本身更重要的事：**

> **增量的收益完全取决于"改动有多局部"。**
> 末尾追加 → 省 83%；文档中部大幅增删 → 几乎为 0（6 片里重算 5 片）。

原因是**切分是链式的**：在文档中部删掉几行，会导致其后的所有切片边界发生偏移，
每片的正文都跟着变，于是 hash 全变 —— 明明"只删了几行"，却要重算一大半。

**这不是实现的缺陷，而是"按内容哈希对齐"这个方案的固有特性。**
真正能改善它的是更细的分块粒度，或者对切片内容做归一化 ——
那属于另一条技术路线（本节不涉及）。

**结论怎么用**：增量索引最适合"追加型"的改动（补一段制度、加一条说明）；
对"中部大改文档"，它退化得跟全量差不多，但**功能上仍然正确**。

### 3.4 进度分母为什么不是切片总数

```python
await _set_task_total(task_id, len(to_insert))     # ← 不是 len(new_chunks)
```

前端进度条上的"已完成 / 总数"反映的是 **embedding 的计算进度**。
命中的切片只是改几个字段、几乎不耗时，把它们算进分母会让进度条显得很慢，
与真实耗时完全不成比例。

实例 A 里台账是 `progress=1/1`，而文档实际有 6 个切片 —— 这个"1"就是本节全部努力的意义。

### 3.5 ⚠️ 必须预检 hash 重复

```python
if _has_duplicate_hash(new_chunks):
    await _run_full_rebuild(...)        # 退化成全删全插
else:
    await _run_incremental(...)
```

**为什么**：上面的对齐逻辑建立在"hash 可以当唯一键"这个前提上。
如果**同一批新切片内部**就有两个 hash 相同（文档里有完全重复的段落、
或者极短文档被切成若干相同的小片），后果是：

```
· new_hashes 是 set → 重复值被【静默去重】
  → "本该插入 2 条"变成"只插入 1 条"，切片表数量对不上
· 配对时"哪个新切片对应哪条旧记录"出现歧义
```

这时候增量对齐的语义已经不成立。**宁可多花一次 embedding 的钱，
也不要写出一份数量对不上的切片表** —— 这就是 `_run_full_rebuild` 存在的理由。

### 3.6 ★ 一个可观测性缺口（复习时容易忽略）

回看实例 A/B 的实测：台账里的 `progress_total` **只等于 `len(to_insert)`**。

```
to_insert  →  有记录（就是 progress_total / progress_done）
to_update  →  没有任何记录
to_delete  →  没有任何记录
```

也就是说：**只看台账，你无法知道这次到底是"删了 4 片"还是"什么都没删"。**
想验证删除与更新是否正确，只能前后对比切片表的 hash 集合（本次归档的数据就是这么采到的）。

如果将来要增强可观测性，最小改动是给 `ingestion_tasks` 加两列
（`deleted_chunks` / `updated_chunks`），或者把这些数字打进日志。
**目前没有做**，先记在这里。

## 四、仓储层补的两个方法（5.1）

### 4.1 `delete_by_ids`

```python
async def delete_by_ids(self, chunk_ids: Sequence[UUID]) -> None:
    if not chunk_ids:
        return                       # ← IN () 是非法 SQL，必须先判空
    stmt = delete(DocumentChunk).where(DocumentChunk.id.in_(list(chunk_ids)))
    await self.session.execute(stmt)
```

判空为什么放在方法里、而不是让调用方自己防：
**增量索引里最常见的场景恰恰是"没有任何切片要删"**（只改内容不改段落结构时）。
把这个判断收进方法，调用方就不必每次都写一遍，也不会漏。

### 4.2 `list_all_by_document`

```python
async def list_all_by_document(self, document_id: UUID) -> list[DocumentChunk]:
    stmt = (select(DocumentChunk)
            .where(DocumentChunk.document_id == document_id)
            .order_by(DocumentChunk.chunk_index.asc()))
    return list((await self.session.execute(stmt)).scalars().all())
```

**为什么敢一次性全加载进内存**：单文档的切片数量有天然上限 ——
splitter 控制每片约 600 字，即便 50MB 的超大文档也只有几百到几千条切片，量级可控。
哈希对齐需要"新旧逐条配对比较"，全部加载进内存用字典查找是这里最直接的写法。

**为什么不无脑优化成流式**：那会把"哈希对齐"变成多趟扫描，
复杂度上升而收益为零 —— 在切片数量到那个量级之前不值得。

> ⚠️ 注意这行是 `list((await ...).scalars().all())`，**带括号**。
> 这个括号在第八节会被证明是"生死攸关"的。

## 五、`_run_reindex` 主流程（5.2）

### 5.1 与 `_run_ingest` 的差异对照

```
                 _run_ingest（首次入库）        _run_reindex（增量重建）
阶段 1  查文档            相同                          相同（找不到就标 failed）
阶段 2  下载 + 解析       相同                          相同
阶段 3  切分              相同                          相同
阶段 4  定分母/向量化     全量：len(chunks)             分叉：
                          _embed_with_progress              hash 有重复 → 全删全插
                                                           否则        → 增量对齐
阶段 5  写库              bulk_add                      delete_by_ids + 改位置 + bulk_add
阶段 6  收尾              状态 → READY                  ★ 多一步：doc.version += 1
                              台账 → success                 状态 → READY / 台账 → success
失败路径                  两张表都写 failed             相同
```

### 5.2 ★ 版本号为什么在 worker 里加，而不是在 Service 里加

```python
# Service.reindex        →  只是"提交任务"，此时文档还没重建
# worker _run_reindex    →  重建真正成功后，才 doc.version += 1
```

如果放在 Service 里加，一旦 worker 失败，前端列表就会出现
「**版本号已经变成 v2 了、内容却还是旧的**」这种假象。
放在成功路径的末尾，语义才准确：

> **版本号 = 内容已经成功换过几版。**

实测印证：`POST /reindex` 的响应里 `version` 仍是 **1**（因为任务刚投递、还没跑完），
等 worker 跑完再查详情，才是 **2**。

### 5.3 兜底路径 `_run_full_rebuild`

```python
await _set_task_total(task_id, len(new_chunks))
embeddings = await _embed_with_progress([c.page_content for c in new_chunks], task_id)
async with AsyncSessionLocal() as session:
    chunk_repo = DocumentChunkRepository(session)
    await chunk_repo.delete_by_document(document_id)     # ← 与 _run_ingest 的唯一区别
    await chunk_repo.bulk_add([...])
    await session.commit()
```

它和 `_run_ingest` 的写库阶段长得几乎一样，**为什么还要单独一个函数**：

- 两者的**语义**不同，将来会分头演化；
- 它【必须】显式 `delete_by_document` 清掉旧数据 ——
  这一步正是它存在的理由，**也是让 reindex 任务幂等的关键**
  （同一任务跑第二遍不会写出两套切片）；
- 分开写之后，将来谁往这里加逻辑，都不会波及首次入库那条路径。

### 5.4 幂等性的连带结论（与第 4 节的呼应）

第 4 节留下过一个问号：「等 `_run_ingest` 变成幂等之后，`task_acks_late` 要不要改成 True？」
本节的复查结论是 —— **仍然不要改**：

```
reindex_document 任务  →  已经幂等（_run_incremental / _run_full_rebuild 都是先删后插）
ingest_document  任务  →  【仍然不幂等】（pipeline 阶段 6 依旧只 bulk_add，不先清空）
task_acks_late         →  是【应用级】配置，不能只对某几个任务开
结论                    →  维持 False
```

这个结论已经回写进了 `celery_app.py` 与 `pipeline.py` 的注释里，
两处互相指路，避免下次忘记。

## 六、`DocumentService.reindex`（5.3）

### 6.1 教程给的三道防线

| 防线 | 检查内容 | 不放会怎样 |
| --- | --- | --- |
| 状态检查 | 只允许 `READY` / `FAILED` 触发 | 与正在进行的 ingest 抢同一份文档，两个任务同时写 chunks 互相踩踏 |
| 文件类型 | 新版本 MIME 必须与原文档一致 | "PDF 被 Markdown 覆盖"——预览/下载按 MIME 走、扩展名还是 pdf，链路状态混乱 |
| 内容去重 | 新文件 SHA-256 与原文件一致就拒绝 | 白跑一次 embedding（纯浪费算力，用户没有任何收益） |

### 6.2 ★ 与教程不同之一：教程那句注释是错的

教程注释写的是「**新文件覆盖到 COS 的同一个 `object_key`**」。
但本项目的 `FileService` 是**内容寻址（CAS）**的：

```python
def build_object_key(self, file_hash: str, suffix: str) -> str:
    return f"documents/{file_hash}{suffix}"
```

**key 里嵌了 hash，所以 hash 一变、key 必然变。** 新版本会落到一个全新的对象上，
旧对象根本不会被覆盖。本次实测：

```
旧 COS key = document-uploads/2c72dce2-fa38-4e64-8a9b-a0f6b9106420/celery验证_reindex_de2dc3.md
新 COS key = documents/f49308b4da1fbb701bde83d8a2339e26dd446c64fae03660b2089dbc5e5aad53.md
                                     ↑ 与旧 key 完全不同
```

这个差异带来两个必须自己补的防护。

### 6.3 ★ 与教程不同之二：跨文档的哈希唯一性检查

`documents.file_hash` 上有 **UNIQUE 约束**。如果新版本的内容恰好与
**库里另一份文档**完全相同，那么 `doc.file_hash = new_hash` 提交时会直接抛
`IntegrityError` → 用户看到 500；而且此时新对象**已经传上 COS 了**，白白留下一个孤儿。

**为什么只有 reindex 会撞上这条约束**：

```
直传 finalize / 旧链路 upload  →  写库【之前】先 get_by_hash 做秒传去重，
                                  发现重复就复用已有记录，根本不会写一个重复的 hash
reindex                        →  【把已有文档的 hash 改掉】，
                                  这是唯一能撞上唯一约束的路径
```

所以补了一层上传**之前**的检查（放在上传前，连孤儿对象都不要产生）：

```python
other = await self.repo.get_by_hash(new_hash)
if other is not None:
    raise ValidationError(
        f"新版本内容与库中已有文档《{other.name}》完全一致。"
        "若想更新那一份，请直接对它执行重新索引"
    )
```

> **本节最值得带走的一条思路**：
> `file_hash` 的唯一约束一直都在，是"新引入的能力"（reindex 可以绕过秒传直接改写 hash）
> 让它从"安全"变成了"可被触发"。
> **给系统加新能力时，要回头检查既有的约束与假设还成不成立** ——
> 这类问题往往不会在开发时报错，只会在某个少见的输入组合下 500。

### 6.4 ★ 与教程不同之三：清理上一版遗留的 COS 对象

因为 key 是内容寻址的，每次 reindex 都会产生一个**全新的对象**，
旧对象再没有任何数据库记录指向它。不清理的话：

```
每重新索引一次  →  就往桶里堆一份永远没人读的垃圾
而且不会自愈     →  这不是偶发失败，是【必然发生】
```

清理动作有三个顺序上的讲究：

```
① 放在 commit 【之后】
      万一提交失败，数据库还指着旧 key，先删就指向不存在的对象了
② 放在 delay  【之后】
      任务已经投出去了，清理失败不影响重建
③ 整段包在 try 里只记警告
      清理是"尽力而为"的收尾动作，绝不能让它把整个请求变成 500
```

**取舍说明**：删除旧对象 = 不保留历史版本。
这与教程的设计一致（它本来就把 `doc.file_hash` / `cos_object_key` 直接改掉了，
旧版本在逻辑上已经不存在），所以删除只是把"逻辑上没了"变成"物理上也没了"。
**若将来要做版本回溯，这里就得改成保留 + 单独的历史表。**

### 6.5 完整的执行顺序（一次 reindex）

```
1. API 进程：POST /{id}/reindex
   ├─ 状态检查（READY/FAILED）           ─┐
   ├─ MIME 一致检查                       ├─ 任一不过 → 400，什么都没发生
   ├─ 空文件 / 大小检查                   │
   ├─ 与自身 hash 相同 → 400              │
   └─ 与其它文档 hash 相同 → 400         ─┘
2. 上传新文件到 COS（得到【新 key】）
3. 改 Document 字段：file_hash / size / cos_object_key / status=PARSING / name
4. 落一条 ingestion_tasks（task_type=reindex, status=pending）
5. commit                                ← 文档与台账同一次提交
6. delay 投递 reindex_document           ← 必须在 commit 之后
7. 清理旧 COS 对象（try/except，只记警告）
8. 返回 200（此时 version 仍是旧值！）
───────────────────────────────────────────────
9. worker：_run_reindex
   ├─ 台账 → running
   ├─ 文档 → PARSING / INDEXING
   ├─ 下载新文件 → 解析 → 切分
   ├─ 拉旧切片 → hash 对齐 → 判分叉
   ├─ 增量或全量重建（只有 INSERT 那批付费算 embedding）
   ├─ doc.version += 1                    ← 只有成功才 +1
   └─ 文档 → READY、台账 → success
```

## 七、路由与契约（5.4 / 5.5）

### 7.1 `_to_document_read`：为什么不能直接 `model_validate(orm)`

```python
async def _to_document_read(document: Document, service: DocumentService) -> DocumentRead:
    latest = await service.get_latest_task(document.id)
    return DocumentRead.model_validate({
        **{c.name: getattr(document, c.name) for c in document.__table__.columns},
        "latest_task": IngestionTaskRead.model_validate(latest) if latest is not None else None,
    })
```

**为什么必须先摊平成字典**：`latest_task` **不是 `documents` 表上的列**，
ORM 实体上根本没有这个属性，直接 `model_validate(orm)` 拿不到它。

**摊平会不会泄露物理存储字段？** 不会：

```
字典里确实带上了 cos_bucket / cos_object_key / cos_region
但 DocumentRead 没有声明它们
Pydantic v2 默认 extra='ignore'  →  多出来的键被忽略
=> 响应体里出现什么字段，仍然只由 DocumentRead 这个白名单决定，脱敏边界没有被打开
```

> ⚠️ 反过来提醒：如果哪天给 `DocumentRead` 设了 `extra='forbid'`，
> 这里就必须改成显式取字段。

### 7.2 五个端点同时被改

`_to_document_read` 一进来，**所有返回 `DocumentRead` 的端点都要跟着改**：

```
POST   /documents                        upload_document
GET    /documents                        list_documents          （列表，逐条 await）
GET    /documents/{id}                   get_document
POST   /documents/{id}/retry             retry_document
PATCH  /documents/{id}/permission-tags   update_document_permission_tags
POST   /documents/{id}/reindex           reindex_document        （本节新增）
```

**这是一次典型的"一处改动、多处生效"** ——
所以验证时必须逐个端点打钩，不能只测新加的那个。
（第八节的 BUG 恰好就藏在这条被扩散出去的读取路径上。）

### 7.3 `reindex` 路由

```python
@router.post("/{document_id}/reindex", response_model=DocumentRead,
             operation_id="reindexDocument")
async def reindex_document(
    _: CurrentAdmin,
    _rate_limit: RateLimited,
    document_id: UUID,
    session: DbSession,
    file: UploadFile = File(..., description="新版本文件（MIME 必须与原文档一致）"),
) -> DocumentRead:
    service = DocumentService(session)
    document = await service.reindex(document_id, file)
    return await _to_document_read(document, service)
```

- **必须是 multipart 而不是 JSON**：它要承载真实文件字节流。
  前端契约里因此是 `BodyReindexDocument = { file: Blob | File }`。
- **必须挂限流 + 要求管理员**：同 `upload_document` ——
  要落 COS、要投递 Celery 任务、可能烧掉上百次 embedding。
- **没有 `status_code=201`**：它不是"新建资源"，返回 200。

### 7.4 ⚠️ 列表页的 N+1（教程也点出来了）

```
本页 20 篇文档  →  1 次文档列表查询 + 20 次 latest_task 查询 = 21 次 SQL
而前端文档列表是【每 3 秒轮询一次】
```

单就本项目的数据量（十几篇）完全无感，但文档量上千之后这里会成为主要瓶颈。

真要优化，PostgreSQL 的 `DISTINCT ON` 可以一次取回全部文档的最新任务：

```sql
SELECT DISTINCT ON (document_id) *
FROM ingestion_tasks
WHERE document_id = ANY(:ids)
ORDER BY document_id, created_at DESC
```

它**恰好能走 `ix_ingestion_tasks_document_created` 这个复合索引** ——
索引的列顺序 `(document_id, created_at DESC)` 与这条 SQL 的 `WHERE + ORDER BY` 完全对齐。

> 顺带一提：模型里那个复合索引到本节才终于有了第二个使用者，
> 第一个是仓储层的 `get_latest_by_document`。

**本节按教程保留"逐条查询"的写法，优化留到真的需要时再做。**

### 7.5 前端是「成品代码」，本节只做校验

本节前端（`DocumentDetailPage` 的「上传新版本」按钮 + `IngestionTaskCard` +
`DocumentsPage` 的版本号列）在仓库里**已经写好了**，而且**类型契约在前**：


## 八、★ 实测撞到的 BUG：教程原文的 `await` 优先级写错

### 8.1 现象

本节第一次调用 `latest_task` 读取路径时：

```
POST /api/documents/{id}/reindex   →   500  {"code":"internal_error"}
```

**但同一时刻，数据库里那份文档的 `version` 已经从 1 变成了 2。**

也就是说：**业务副作用全都成功了，只是组装响应体时炸了。**
这个"半成功"现象立刻把排查范围从"整条 reindex 链路"缩小到
"**服务方法返回之后的响应组装环节**"。

### 8.2 出错的代码（教程原文）

```python
# 教程原文（错的）
return await self.session.execute(stmt).scalar_one_or_none()
```

**Python 里 `.` 的优先级高于 `await`**，所以它实际等价于：

```python
await ( self.session.execute(stmt).scalar_one_or_none() )
#      └──────────── 先算这一段 ────────────┘
```

而 `AsyncSession.execute()` 是**协程函数**，调用它得到的只是一个**协程对象** ——
协程上根本没有 `scalar_one_or_none` 方法。于是**在 `await` 生效之前**，
属性访问就已经先抛 `AttributeError` 了。

日志末尾那句是这类错误的典型指纹：

```
RuntimeWarning: coroutine 'AsyncSession.execute' was never awaited
```

**只要看到它，第一反应就该去查 `await` 与 `.` 的优先级。**

### 8.3 为什么它能潜伏整整一节

```
第 4 节  写下 get_latest_by_document()     ← 但它【没有任何调用方】
第 4 节  验证：任务能跑通、台账状态会变    ← 全程没有一条断言碰到过这个方法
第 5 节  第一次调用                        → 立刻必崩
```

**这段代码在写下之后的整整一节时间里，从未被执行过一次。**

第 4 节的验证清单看起来很完整（任务注册、迁移、端到端上传、重试、进度推进……），
但恰恰漏掉了"台账的**读取**路径"—— 因为当时那条路径根本还不存在。

> 一句话：**没有调用方的代码 = 未验证的代码。**

### 8.4 修法

```python
# 写法一（本项目采用）：拆成两步
result = await self.session.execute(stmt)
return result.scalar_one_or_none()

# 写法二：保留单表达式，但主动加括号
return (await self.session.execute(stmt)).scalar_one_or_none()
```

### 8.5 全局排查结果

对全后端做模式扫描（匹配 `await ...execute(...).<访问器>`）：

```
chunk_repo.py            7 处   全部带括号，正确
document_repo.py         4 处   正确
conversation_repo.py     6 处   正确
evaluation_repo.py       5 处   正确
role_repo.py             3 处   正确
user_repo.py             4 处   正确
citation_repo.py         2 处   正确
ingestion_task_repo.py   1 处   ★ 错误 ← 就是它，已修
```

**31 处正确写法全都带了括号，只有这一处没带** ——
说明项目既有的书写习惯是对的，是第 4 节照抄教程时把那一处错误一起抄了进来。

完整记录见 `BUG发现与处理/03_2026.9.27/04_await优先级写错：任务台账查询必崩.md`。
