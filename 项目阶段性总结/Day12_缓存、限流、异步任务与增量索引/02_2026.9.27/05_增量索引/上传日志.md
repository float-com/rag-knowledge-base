二、这一节的核心：用 chunk_hash 当切片的"身份证"

· 文档改了一小段，全量重建要把【每一个切片】都重算 embedding，而 embedding 按量计费
· 增量索引的三分类规则：
    旧有新没有 → DELETE
    新旧都有   → UPDATE（只改 chunk_index / page_no / section_path，不动 embedding）
    新有旧没有 → INSERT（只有它需要重算 embedding）
· 进度分母是 len(to_insert)，不是 len(new_chunks)：
  前端进度条反映的是"embedding 的计算进度"，命中的切片几乎不耗时，算进分母会让进度条失真

三、★ 实测出的一个反直觉结论：增量的收益取决于"改动有多局部"

· 末尾追加一点内容：6 个切片里只有 1 个需要重算（省 83%）
· 文档中部大幅增删：  6 个切片里有 5 个需要重算（几乎没省）
    v1→v2 : DELETE=4 UPDATE=1 INSERT=5   净变化 5-4+5=6 ✅  台账 progress_total=5
    v2→v3 : DELETE=5 UPDATE=1 INSERT=4   净变化 6-5+4=5 ✅  台账 progress_total=4
· 原因：切分是链式的 —— 在中部删掉几行会让其后所有切片的边界偏移，每片正文都变、hash 全变
  明明"只删了几行"，却要重算一大半。这不是实现缺陷，是"按内容哈希对齐"方案的固有特性
· 所以增量索引最适合"追加型"改动；对"中部大改"会退化成接近全量，但功能仍然正确

五、chunk_repo 的两个新方法

· delete_by_ids 必须先判空：IN () 是非法 SQL，而"没有任何切片要删"恰恰是最常见的场景
· list_all_by_document 敢一次性全加载：单文档切片受 splitter 控制（每片约 600 字），
  50MB 文档也只有几百到几千条，量级可控；哈希对齐需要逐条配对，内存字典查找最直接

六、★ 与教程不同的第一处：教程那句注释是错的

· 教程写"新文件覆盖到 COS 的同一个 object_key"
· 但本项目 FileService 是【内容寻址】的：build_object_key = f"documents/{file_hash}{suffix}"
  key 里嵌了 hash → hash 一变 key 必然变 → 新版本落到全新对象上，旧对象根本没被覆盖
· 实测：旧 key 是 document-uploads/<uuid>/xxx.md，新 key 是 documents/<新hash>.md
· 这个差异带来两个必须自己补的防护（下面两条）

七、★ 与教程不同的第二处：跨文档哈希唯一性检查

· documents.file_hash 上有 UNIQUE 约束
· 若新版本内容恰好与【库里另一份文档】相同 → 提交时 IntegrityError → 500，
  而且此时新对象已经传上 COS 了，白白留一个孤儿
· 为什么只有 reindex 会撞上：
    直传 finalize / 旧链路 upload 在写库【之前】先 get_by_hash 做秒传去重，不会写重复 hash；
    reindex 是"把已有文档的 hash 改掉"，是唯一能撞上这条约束的路径
· 修法：上传【之前】先 get_by_hash 查一次，命中就 400 并告知是哪份文档
· 这条的思路值得记住：新引入的能力（reindex 可以绕过秒传改写 hash）
  会让既有的约束从"安全"变成"可被触发" —— 加新能力时要回头检查旧假设还成不成立

八、★ 与教程不同的第三处：清理上一版遗留的 COS 对象

· 因为 key 是内容寻址的，每次 reindex 都会产生全新对象，旧对象再没有任何记录指向它
· 不清理的话：每重新索引一次就往桶里堆一份垃圾，而且【不会自愈】（是必然发生，不是偶发失败）
· 三个顺序讲究：
    ① 放在 commit 之后 —— 万一提交失败，数据库还指着旧 key，先删就指向不存在的对象了
    ② 放在 delay 之后 —— 任务已经投出去了，清理失败不影响重建
    ③ 整段 try/except 只记警告 —— 清理是"尽力而为"的收尾，不能让它把整个请求变成 500
· 取舍：删除旧对象 = 不保留历史版本。这与教程设计一致（它本来就直接改掉了 file_hash），
  将来要做版本回溯的话，这里得改成保留 + 单独的历史表

九、路由与契约

· 新增 _to_document_read：因为 latest_task 不是 documents 表上的列，
  必须先把 ORM 的列摊平成字典再塞进去
· 摊平不会泄露 cos_bucket / cos_object_key —— DocumentRead 没声明它们，
  而 Pydantic v2 默认 extra='ignore'
· 五个端点同时被改（list / get / upload / retry / permission-tags），
  这是一次典型的"一处改动、多处生效"，验证时必须逐个打钩
· ⚠️ 列表页是 N+1：本页 20 篇 → 21 次 SQL，而前端每 3 秒轮询一次
  优化方案是 PostgreSQL 的 DISTINCT ON，恰好能走 ix_ingestion_tasks_document_created
  本节按教程保留逐条查询，优化留到需要时再做
· 前端契约在前：types.gen.ts 里 BodyReindexDocument / IngestionTaskRead / version / latest_task
  早就写好了，后端是"照着契约兑现"

十、★ 实测撞到的 BUG：教程原文的 await 优先级写错

· 现象：POST /reindex 返回 500，但同一时刻文档的 version 已经从 1 变成了 2
  → 业务副作用全成功了，只是组装响应时炸了。这个"半成功"现象是定位的关键线索
· 出错代码（教程原文）：
      return await self.session.execute(stmt).scalar_one_or_none()
  Python 里 `.` 的优先级高于 await，它实际等价于
      await ( self.session.execute(stmt).scalar_one_or_none() )
  而 execute() 返回的是【协程对象】，协程上没有 scalar_one_or_none → AttributeError
· 指纹：日志里的 RuntimeWarning: coroutine 'AsyncSession.execute' was never awaited
· 为什么潜伏整整一节：这个方法第 4 节就写了，但全项目唯一的调用方是第 5 节的 _to_document_read
  第 4 节的验证清单很完整，却恰恰碰不到这条"还不存在的读取路径"
  → 一句话：没有调用方的代码 = 未验证的代码
· 全局排查：32 处 execute 链式访问，31 处都带括号（正确），只有这一处没带
  说明是照抄教程时把那一处错误一起抄了进来
· 修法：拆成两步 result = await ...; return result.scalar_one_or_none()

十二、验证过程中踩的两个测试自身的坑（记下来免得再犯）

· 第一次跑守卫测试时，"内容与当前版本一致"这项 FAIL、而"内容与另一份文档一致"这项假通过
  原因是测试顺序写错了：
    ① 第一项测试用 ".md 文件名 + text/html 声明" 去触发 MIME 不一致，
       但 _resolve_mime_and_suffix 是【后缀优先】的 —— 后缀是 .md 就被判成合法 markdown，
       这一次调用真的执行了一次 reindex，把"当前版本"换掉了
    ② 于是后面"内容一致"的基准失效；而"跨文档一致"那项返回 400 其实是因为
       文档当时正处于处理中，被状态守卫拦下的，不是被哈希守卫拦下的
  修法：内容类守卫必须先测、每次先 ensure_ready、MIME 测试必须用真正不同的后缀
· 教训：守卫类测试里，任何一次"意外成功"的写操作都会污染后续用例的基准；
  测试顺序本身就是测试设计的一部分
