三、权限隔离的设计（本章最关键的一处）

· 为什么不能直接用标签数组做 Tag 匹配
  RedisSearch 的 Tag 过滤是"有交集即命中"，而这里需要"集合完全一致"
  若用交集匹配：张三有 public 与 hr，其答案会命中李四（只有 public）→ 越权
· 本项目的做法：排序后拼接再哈希
  同集合不同顺序 → 哈希相同 → 命中
  子集、超集、无交集、不同集合 → 哈希不同 → 不命中
  实测 7 组用例全部符合预期
· 代价是"权限是子集时也不命中"，命中率低一些
  但这是刻意的保守：不命中只多花一次 LLM，误命中会让用户看到无权内容

四、ChatService 的改造

· stream_answer
  · load_context 之后、图执行之前插入缓存查询
  · 命中则走 _stream_cache_hit 并 return，避免白花一次 LLM 调用
  · 落库助手消息之后、收尾事件之前写缓存，只在"非拒答且校验通过"时写
· 新增四个内部方法
  · _safe_uuid：缓存里的字符串 UUID 解析回 UUID，失败返回 None 而不是抛异常
  · _try_cache_lookup：查缓存并把 embedding 一起带出，供保存阶段复用
  · _stream_cache_hit：命中路径。落库与事件一件不少，只是不跑图、不调 LLM
  · _persist_cached_assistant_message：落库时 metadata 写 cache_hit=True
· _persist_assistant_message 补 cache_hit=False，让该键在所有助手消息上都存在
· citation_repo 新增 existing_chunk_ids / existing_document_ids（见第六节）

五、后端 schema

· schemas/chat.py
  · MessageRead 新增 cache_hit 字段，默认 False
  · 新增 _parse_cache_hit：默认值刻意用 False 而非 None

六、实测撞到并修掉的三处坑（已单独归档）

· 坑一：缓存命中路径漏写 state["answer"]
  症状是前端正常收到答案与引用，但刷新后这条消息消失
  根因是落库读 state["answer"] 而我只 yield 没回写，抛 KeyError 导致事务回滚
  这个 bug 特别隐蔽：发结果在落库之前、异常被流式兜住、用户只有刷新才发现
· 坑二：lookup 的 return_fields 漏了 vector_distance
  导致相似度拿到 None，那段判定被整段跳过，任何召回结果都算命中
  阈值静默失效，表现为"缓存命中率特别高"，看起来像好事
  修法除了补字段，还把"拿不到距离"改成保守判未命中并打 warning
· 坑三：缓存引用指向已删除的 chunk 会导致外键失败、回滚整条消息
  两个外键虽是 ON DELETE SET NULL，但插入时仍会校验 id 是否存在
  修法是落库前批量校验一次存在性，不存在的置 None（快照字段仍可展示引用卡片）

七、相似度阈值必须实测定标（教程的 0.92 在本项目命中不了）

· 实测 text-embedding-v3 在中文问答上的分布
  相近（换说法）      0.7589 ~ 0.8819
  相关但不同问点      0.8381
  无关               0.4154 ~ 0.5161
· 可行区间是 (0.5161, 0.7589]，0.92 高到任何换说法都不命中
· 已把 .env / .env.example / config.py 的默认值改为 0.75，并在注释里附上实测依据
· 提醒：换 embedding 模型后必须重新定标，这个数只对当前模型有意义

十、后期修正（验证与讲解过程中发现并改掉的）

· 注释修正 7 处
  · semantic_cache_service.py 共 5 处
    · _stub_embed 里写 distance_threshold=1.0，实际是 2.0（改代码时漏改注释）
    · CachedAnswer.citations 的示例字段写成 doc_id / content，不是本项目结构；
      真实为 ordinal / document_id / chunk_id / document_name / page_no /
      section_path / score / quote / retrieval_meta 共 9 个
    · hexdigest 举例的哈希注明它正是空字符串的 SHA-256（即 _scope_key([]) 的结果）
    · hits[0] 处补充 num_results=1 所以只有一条（排序是 Redis 的活，不是这里做的）
    · lru_cache 的 maxsize 表述精确化为"最近 1 个参数组合"
  · chat_service.py 共 2 处
    · _try_cache_lookup 的标题写"均返回 (None, None)"，与第 3 点"返回 (None, embedding)"
      自相矛盾 —— 已改为明确区分：前两种返回 (None, None)，第三种是唯一带回向量的
    · _persist_cached_assistant_message 把"置 None 能避免插入报错"归因于
      ON DELETE SET NULL，因果写反 —— 正确的是外键列允许为空（nullable）；
      ON DELETE SET NULL 只管"删除父行时"，插入时照样校验 id 是否存在

· ★ 新发现一个编码陷阱（decode_responses）
  · 用 core/redis.py 的 get_redis()（decode_responses=True）去 hgetall 缓存键，
    会抛 UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe2
  · 原因：Hash 里的 prompt_vector 是 1024 维 float32 的二进制数据，不是文本。
    这也解释了为什么在 IDE 里看该字段显示为乱码 —— 它本来就是二进制
  · 影响面：当前代码只读单个字段（metadata / prompt），没触发；
    但将来若做"缓存管理接口"要列出整条 Hash，必须先改成 decode_responses=False
    并逐字段决定怎么解

· 两处配套改动的取舍（正文有详述）
  · citation_repo 的 existing_chunk_ids / existing_document_ids：
    缓存引用是跨生命周期的快照（最长 1 小时），期间文档可能被删，落库前必须校验；
    用 WHERE id IN (...) 批量查一次，不是逐条查
  · schemas/chat.py 的 cache_hit 默认 False 而非 None：
    与 _parse_trace_id 的默认 None 刻意相反 —— trace_id 需要"没有"的表达来隐藏面板，
    而 cache_hit 是布尔判断，收敛成 bool 前端只写 if (cache_hit)
