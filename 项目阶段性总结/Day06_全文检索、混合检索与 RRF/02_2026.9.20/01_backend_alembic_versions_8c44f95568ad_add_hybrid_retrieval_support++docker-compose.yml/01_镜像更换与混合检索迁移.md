## 一、本期实现的三步与取舍

教程原本三步：

```
1. 自定义 PostgreSQL 镜像（写 postgres.Dockerfile：多阶段构建 SCWS + zhparser）
2. docker-compose 切到 build 模式
3. 迁移
```

**实际采用方案：前两步跳过，只做第 3 步。**

| 教程步骤 | 实际做法 | 原因 |
| --- | --- | --- |
| 1. 自建镜像 | ❌ **不做** | 改用预构建镜像，镜像内已含 SCWS + zhparser |
| 2. 切 build 模式 | ❌ **不做** | 直接写 `image:` 拉取，无需 `build:` |
| 3. 迁移 | ✅ **必做** | 见第三节：镜像只是"提供文件"，扩展装载只能靠迁移 |

### 为什么放弃自建镜像

自建方案有 3 处高风险点，**实测确认预构建镜像可以完全绕开**：

```
① SCWS 1.2.3（2011 年项目）用现代 autotools 重建常失败（acconfig.h 等问题）
② 构建期必须联网到 github.com / xunsearch.com / deb.debian.org，国内常超时
③ Dockerfile 里 4 个 COPY 路径写得很具体，任一路径不符即构建中断
```

## 三、⭐ 为什么迁移省不掉（**实测证据**）

**这是整节最值得记住的一点：镜像里"有扩展文件" ≠ 数据库里"扩展已装载"。**

```
镜像提供的是文件:  zhparser.so / zhparser.control / zhparser--2.4.sql
                  → 它们在【镜像文件系统】里
数据库集群在:      pgdata 数据卷里
→ 数据卷已存在 → 官方镜像的初始化钩子不会重跑
→ 扩展【未装载】
```

### 实测：纯净容器里的三层报错

起一个全新容器（未执行任何 CREATE EXTENSION）：

```
① 已装扩展只有 plpgsql
     → pg_available_extensions 能看到 zhparser（文件在位）
     → pg_extension 里没有 zhparser（未装载）

② 直接用 chinese_zh 分词
     ERROR: text search configuration "chinese_zh" does not exist

③ 尝试建配置 CREATE TEXT SEARCH CONFIGURATION zz (PARSER = zhparser)
     ERROR: text search parser "zhparser" does not exist        ← ★ 决定性
```

**执行 `CREATE EXTENSION zhparser` 之后全部成功**：

```
CREATE EXTENSION                    → 成功
CREATE TEXT SEARCH CONFIGURATION    → 成功
to_tsvector('chinese_zh', '按照报错信息')
  → '按照':1  '报':2  '错':3  '信息':4      ← 分词工作 ✓
```

### 附带确认：新镜像不自带中文配置

```
pg_ts_config 里 chinese_zh 数量: 0
default_text_search_config:      pg_catalog.english
→ 换镜像不会自动创建中文配置，必须靠迁移
```

## 四、迁移文件的四个组成部分

文件：`backend/alembic/versions/8c44f95568ad_add_hybrid_retrieval_support.py`（126 行）

```
revision      = '8c44f95568ad'          # L23
down_revision = '960400bbd4f4'          # L24（聊天表 + HNSW 索引那条）
```

### ① 装载扩展（L42）

```python
op.execute("CREATE EXTENSION IF NOT EXISTS zhparser")
```

### ② 创建中文检索配置（L44-73）

```sql
-- 用 DO $$ ... EXCEPTION 包一层实现幂等
DO $$ BEGIN
    CREATE TEXT SEARCH CONFIGURATION chinese_zh (PARSER = zhparser);
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;

DO $$ BEGIN
    ALTER TEXT SEARCH CONFIGURATION chinese_zh
        ADD MAPPING FOR n,v,a,i,e,l WITH simple;
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;
```

**⚠️ 幂等加固是教程没有的，但很必要**：

```
PostgreSQL 的 CREATE TEXT SEARCH CONFIGURATION 【没有 IF NOT EXISTS】
→ 重复执行报 duplicate_object → 中断整个迁移
→ 换镜像后重试、或回滚再升级时都会踩到
→ 用异常捕获包一层即可安全重跑
```

**`ADD MAPPING FOR n,v,a,i,e,l WITH simple` 的含义**：

```
zhparser 会给每个切出的词标注词性（名词 n / 动词 v / 形容词 a /
习用语 i / 叹词 e / 习用语 l 等），这里把六类词性映射到 simple 词典。
教程选择这种映射，理由是能让 tsquery 对中文关键词的匹配更稳定。
```

### ③ 全文检索向量列与 GIN 索引（L83、L90）

```sql
ALTER TABLE document_chunks
ADD COLUMN content_tsv tsvector
GENERATED ALWAYS AS (to_tsvector('chinese_zh', content)) STORED;

CREATE INDEX ix_document_chunks_content_tsv
ON document_chunks USING GIN (content_tsv);
```

**`GENERATED ALWAYS AS ... STORED` 的两个细节**：

```
① GENERATED ALWAYS：数据库自动维护的生成列
   → 应用【无需在 INSERT 时显式写入】
   → 从根上杜绝"新写入 chunk 时忘记维护 tsvector 列"导致的检索错乱
   → 且会自动【回填已有行】（实测 259 条全部生成，无需重跑入库）

② STORED：物化存储，占磁盘但不重复计算，查询更快
   （VIRTUAL 类型不存储、每次查询重算，且无法建 GIN 索引）
```

**GIN 索引原理**：倒排索引，把 tsvector 里的每个 token 反向映射到文档列表，
是全文检索的标准索引类型（类似书籍末尾的"索引页"）。

### ④ 检索调试元数据列（L99）

```python
op.add_column(
    "answer_citations",
    sa.Column("retrieval_meta", postgresql.JSONB(astext_type=sa.Text()),
              nullable=True, comment="混合检索调试元数据（sources / 各路排名与分数 / rrf_score）"),
)
```

### ⑤ downgrade（L110-126）—— 顺序与 upgrade 严格相反

```
3. op.drop_column("answer_citations", "retrieval_meta")
2. DROP INDEX IF EXISTS ix_document_chunks_content_tsv
   ALTER TABLE document_chunks DROP COLUMN IF EXISTS content_tsv
1. DROP TEXT SEARCH CONFIGURATION IF EXISTS chinese_zh
   DROP EXTENSION IF EXISTS zhparser
```

## 六、⚠️ zhparser 的已知行为：型号召回会漏

**这是分词器特性，不是迁移或配置问题**。用库内真实数据实测：

| 查询 | ILIKE 真实值 | tsquery 召回 | 差异 |
| --- | --- | --- | --- |
| 上传 | 3 | 3 | ✓ |
| 接口 | 16 | 16 | ✓ |
| 报错 | 1 | 1 | ✓ |
| 权限 | 19 | 19 | ✓ |
| 差旅 | 4 | **3** | 漏 1 |
| **B200** | **9** | **7** | **漏 2** |
| **A100** | **11** | **9** | **漏 2** |

### 根因

抽查漏掉的两条切片，其分词结果是：

```
'参数':3 '工作':5 '温度':6 '环境':1 '规格':2,4        ← B200 不在 token 列表里
'sku':3 '信息':2 '建议':5 '描述':4 '订货':1 '零售':6
```

而命中的 7 条里，B200 是这样出现的：

```
'edgeserver':5 'b200':6 ...        ← 有独立 token
```

**结论**：zhparser **会吞掉紧邻中文的字母数字串**（表格/紧凑排版里尤其明显）——
既没保留为独立 token，也没正确切分，于是整个型号从索引里消失。

### 影响与后续选项

```
本期按教程实现 → keyword_search 用 tsquery → 型号检索会漏（预期行为，不必惊慌）
若后续发现"型号查不全"是真实痛点 → 在同一 SQL 里补一个 ILIKE 分支即可：

    WHERE content_tsv @@ plainto_tsquery('chinese_zh', :q)
       OR content ILIKE '%' || :q || '%'          -- 精确子串兜底

两者实测互补：ILIKE 补型号漏召，zhparser 补词级模糊。
```

> 生成列自动回填了全部 259 条切片，无需重跑入库；
> 最后记录 zhparser 的固有行为——**会吞掉紧邻中文的字母数字串，导致型号召回漏 2 条**，后续如需补齐可在同一 SQL 加 ILIKE 分支。
