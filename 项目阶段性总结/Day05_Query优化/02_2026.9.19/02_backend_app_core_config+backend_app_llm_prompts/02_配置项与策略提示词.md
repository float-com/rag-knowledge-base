## 二、新增配置项

```python
# ===== Query 优化配置（第 5 期） =====
query_route_enabled: bool = True    # 策略路由总开关
multi_query_count: int = 3          # 多查询策略生成的子查询数量
```

### `query_route_enabled` —— 可回退性设计

注释里写明了它的用途：

> 关闭后整条链路退化成上一期的单路检索，是排查"优化是否真的有效"的第一手段。

**价值在于支持 A/B 对照实验：**

```
你怎么证明 Query 优化真的有用？
  → 同一批问题，开 / 关各跑一遍，对比 Top-1 分数分布与拒答率
  → 没有这个开关，只能靠改代码来切换，无法做对照
```

**与第 2 章"降级回 original"的关系：**

```
共同点：都保证「original 路径始终可用」
        降级 = 运行时自动回退，开关 = 开发时手动回退
        两者都依赖同一前提：单路检索这条基线没被破坏

不同点：触发时机与目的
        降级 → 异常时自动触发，保护「链路可用性」
        开关 → 人工主动切换，支持「效果度量」
```

> **第 2 章把"降级到 original"做成安全网时，顺带就获得了 A/B 测试能力**——因为 original 路径被完整保留了。

### `multi_query_count` —— 成本油门

```
multi_query_count = 3
  → 1 次 LLM 调用生成 3 条子查询
  → 3 次 embedding（第 12 章实测单次约 1 秒）
  → 3 次向量检索
```

**这个数字直接决定 `multi_query` 的成本与延迟。** 调大召回面更广，但延迟线性增长。注释里"绝大多数问题用够了"是经验默认值。

**建议**：实现完第 3 节后，用真实问题跑 `n=3` vs `n=5` 对比，验证召回质量是否真的提升。

## 三、四组策略 Prompt 的设计要点

### 3.1 路由 Prompt —— 给判据，而非只给标签

```
1. 问题清晰、表达完整、用词具体（含专有名词 / 编号 / 实体），直接检索即可。
2. 问题存在指代（"它"、"这个"、"那"）、省略、口语化或表达不完整，需要改写成独立完整的问题。
3. 抽象 / 开放式（"什么是..."、"为什么..."、"如何理解..."），关键词稀疏，直接检索容易召回不到。
4. 问题包含多个角度、多个并列子问题（如"对比 A 和 B"、"X 的优缺点"）。
```

**注意写法：给的是「判据」而不是「标签」：**

```
不带判据："判断问题属于哪种策略"  → 模型不知道边界在哪，随机性强
带判据  ："含专有名词/编号 → 直接检索；含'它/这个' → 改写"
                                → 模型有明确决策依据
```

> **这正是第 2 章"用 LLM 做路由"能成立的前提**——判据写清楚，模型才可能判对。
> **如果路由准确率不行，第一个该改的是这段 prompt，而不是急着换分类器。**

**末尾的格式约束也很硬：**

```
只输出一个小写的 route 名称，不要加任何解释、引号或标点。
```

**原因**：下游要做精确匹配。

```python
# 第 3 节 QueryRewriter 里会做的事
route = raw.strip().lower()
if route not in ("original", "rewrite", "hyde", "multi_query"):
    route = "original"      # 匹配不上就降级
```

若模型输出 `"The route is: rewrite"` 或 `Rewrite。`，就会匹配失败并降级 —— **既要在 prompt 里严令，又要在代码里防御**。

### 3.2 Rewrite Prompt —— "禁止回答"这条最关键

```
3. 不要扩写、不要解释、不要回答问题。
```

**为什么专门禁止"回答问题"？这是个真实且隐蔽的坑：**

```
用户问："它的学分是多少"（前文指 JavaEE 课程）
模型若越界作答："JavaEE 课程是 3 学分。"    ← 幻觉，它并不知道

→ query 变成 "JavaEE 课程是 3 学分"
→ 检索召回的片段全围绕"学分"这个词
→ 绕开了"JavaEE 课程"这个真正的上下文
→ Top-1 分数可能不低（如 0.65）→ 不熔断
→ 模型拿着"学分相关"的片段回答"学分是多少"
→ 用户看不出问题，但答案建立在编造的前提上
```

**⚠️ 危害的本质：改写节点污染的是「检索输入」，比污染答案更上游、更隐蔽。**

**注意这与"检索失败"的区别：**

```
检索失败 / 召回无关 → 分数低 → 熔断 → 拒答 → 用户看到"没有相关信息" → 失败可见
检索成功但方向错   → 分数可能很高 → 不熔断 → 基于错误前提作答 → 失败不可见
```

> 改写节点的职责是"把问题变完整"，**不是"回答问题"**。越界会引入幻觉。

### 3.3 HyDE Prompt —— 三个约束各有机制

```
1. 长度 80-200 字之间             → 太短缺信息量，太长会引入无关话题
2. 用陈述句，不要"我认为""可能"    → 陈述句形式最接近文档；不确定措辞会让向量偏移
3. 不要表达"无法回答"              → 否则生成"我无法回答"，与文档差距更远
```

**第 2 条是 HyDE 的核心机制**（第 2 章讲过形式匹配）：

```
问题（问句形式）  vs 文档（陈述形式）→ 形式错配
假设答案（陈述形式）vs 文档          → 形式一致 → 向量距离更近
```

**"不要用『我认为』『可能』"是为强化"陈述式"**——语气越笃定，生成文本越"像文档"。

**具体对照**：

```
问题形式：「向量检索会有什么问题？」
          ↑ 抽象、关键词稀疏（正是第 1 章"场景 3"的失效类型）

假设答案：「向量检索在实际应用中常见的问题包括：高维向量的近似
          最近邻搜索存在精度损失，索引构建成本随数据规模增长，
          以及在语义漂移场景下召回结果不稳定。」
          ↑ 陈述句 + 高术语密度（近似最近邻、索引构建、语义漂移）
```

**两个关键差异：形式（问句→陈述句）+ 术语密度。** embedding 在词与语义两个层面同时拉近距离。

**第 3 条防"退化"**：若模型说"我无法回答"，这段文本在向量空间里与任何真实文档都不像，HyDE 完全失效。

### 3.4 Multi-Query Prompt —— "角度不同"是效果分水岭

```
2. 各子查询之间角度不同，用词和视角要相互错开，不要只是同义词替换。
4. 输出 {n} 行，不多不少。
```

**第 2 条为什么重要**——多路召回的价值完全建立在"不同角度"上：

```
✓ 好的扩展（角度不同）：
    "HNSW 的查询性能特点"
    "IVFFlat 的索引构建成本"
    "HNSW 与 IVFFlat 的适用场景差异"
  → 三路覆盖不同文档片段

✗ 差的扩展（同义替换）：
    "HNSW 和 IVFFlat 的优缺点"
    "HNSW 与 IVFFlat 的优劣"
    "对比 HNSW 和 IVFFlat"
  → 三路召回同一批片段 → 白付 3 次 embedding → 质量零提升
```

**⚠️ 这个退化可检测（实操要点）：**

```
把生成的子查询打出来看一眼：
  ✗ 退化信号：三条读起来像同一句话的不同说法
  ✓ 好的信号：三条真的在问不同角度

可量化两个指标：
  ① 子查询两两之间的相似度（都很高 → 退化成同义替换）
  ② 多路结果的 chunk_id 重合率（很高 → 白付 N 次 embedding）
```

**另一个隐蔽之处**：

```
multi_query 会让 Top-1 分数变高（多路中总有一路能命中高分片段）
→ 所以：Top-1 分数上升 ≠ 策略有效
   可能只是"多路里有一路碰巧命中"，而非"多角度覆盖更全"
→ 必须同时看「召回片段的多样性」
```

> 多路召回需要比单路更细的度量。这是第 1 章"建立可度量失败判据"的延伸。

**第 4 条 `{n} 行，不多不少`** 是格式约束，`{n}` 来自配置：

```python
build_multi_query_messages(question, n=settings.multi_query_count)
```

**配置值最终会插进 prompt 文本**——改配置就改了 prompt 的硬约束。

## 四、四个装配函数：把模板细节关在 prompts.py 内部

```python
def build_route_messages(question: str) -> list[BaseMessage]:
    return list(ROUTE_QUERY_PROMPT.invoke({"question": question}).to_messages())
```

**看起来只是包了一层，但价值是信息隐藏：**

```
route_query 节点只写：
    messages = build_rewrite_messages(state["question"])

它完全不知道：
    模板对象叫什么（_REWRITE_SYSTEM / REWRITE_QUERY_PROMPT）
    变量怎么插值（invoke({"question": ...})）
    消息怎么构造（.to_messages()）

→ 以后优化 rewrite 的 prompt（如加"保留原问题中的数字"）
   只改 prompts.py 一处，节点零改动
```

**与 `build_answer_messages` 是同一模式**（第 10 章 `generate` 节点即如此调用）：

```python
# app/workflows/nodes/generate.py:40
messages = build_answer_messages(question=..., chunks=..., history=...)
```

> **「契约稳定性」思想在本期的第三次应用**：
>
> | 层次 | 隔离对象 |
> | --- | --- |
> | 第 9 章 `normalize_query` | 隔离"查询怎么来" |
> | 第 3 章第 1 节「覆盖 query」 | 隔离"策略有哪些" |
> | 第 3 章第 2 节 `build_*_messages` | 隔离"提示词怎么写" |

### 逐题批改

**第 1 题 —— 正确，但"共同点"那半句逻辑可更清**

正解见第二节的对照表。**最有价值的共同点**：两者都保证「original 路径始终可用」——**安全网顺带带来了 A/B 测试能力**。

**第 2 题 —— 关键因果说反**

```
❌ 作答："检索失败或检索到与原始问题毫不相干的 chunks"
✓ 实际："检索【成功】，召回一批与【编造前提】相关的片段"
```

**区别至关重要**：失败可见 vs 失败不可见（详见 3.2 节）。**危害的本质是污染了检索输入，比污染答案更隐蔽。**

**第 3 题 —— 正确**

补：形式与**术语密度**双重拉近距离（见 3.3 节的对照）。

**第 4 题 —— 基本正确，漏了最有价值的判断方法**

成本与效果的判断准确。**漏的是"这种退化可检测"**：

```
① 打出子查询肉眼检查
② 量化：子查询间相似度 + 多路结果 chunk_id 重合率
③ 注意：Top-1 上升 ≠ 策略有效，还要看召回片段多样性
```

**第 5 题 —— 正确**

即信息隐藏。这是"契约稳定性"思想的第三次应用（见第四节表格）。

## 七、一句话总结

> 本节为 Query 优化准备"素材"：新增**路由总开关**（提供 A/B 对照能力，是第 2 章安全网设计顺带带来的收益）与**子查询数量**（`multi_query` 的成本油门）；新增四组策略提示词——路由 prompt 给「判据」而非仅给标签并强制只输出策略名，rewrite prompt 明确**禁止回答问题**（防止改写越界污染检索输入），HyDE prompt 要求陈述句与笃定语气（形式匹配 + 术语密度双重拉近向量距离），multi-query prompt 强调**角度必须真正错开**（多路召回的价值完全建立于此，且该退化可检测）；四个 `build_*_messages` 函数把模板细节关在 prompts.py 内部，形成"契约稳定性"思想在本期的第三次应用。
