三、★ 关键技术验证：`!override` 到底有没有用（本次最有价值的实测）

· 背景：基础 docker-compose.yml 写的是 `"${POSTGRES_PORT:-5432}:5432"` ——
  **不写 IP = 绑定 0.0.0.0 = 公网可直连**。
  而 Compose 合并多个文件时，`ports` 这类列表默认是【追加】而非替换；
  于是"写了 override 但没生效"会变成两处都绑 —— 数据库照样裸奔，且**不报任何错**
· 实测（`docker compose config` 只读，不起容器、不影响正在跑的服务）：
      只基础文件                          → published: 5432 / 6379
      基础 + deploy/override（显式两文件）→ 127.0.0.1:55432 / 127.0.0.1:56379  ✅
· 结论：`!override` 在本机 Compose v5.4.0 上确实生效，**不是靠环境变量碰巧对上**
· 但仍保留脚本里的端口闸门：换个 Compose 版本（< 2.24）就可能失效，闸门是为那天准备的

四、★ deploy.sh 比手工敲多出来的两道闸门

**闸门 1：起完容器后强制校验端口**

```
若 docker compose ps 输出里出现 0.0.0.0:55432 / 0.0.0.0:5432 / 0.0.0.0:56379 / 0.0.0.0:6379
→ 直接报错退出，并提示"通常是 !override 未生效"
```

理由：这种失败**不会有任何报错**，只能靠主动查。

**闸门 2：`.env` 五项自检**（告警不阻断，因为部分项缺失只是功能降级）

| 检查项 | 为什么 |
| --- | --- |
| `ENVIRONMENT=production` | 没它 → config.py 的 JWT 硬校验不触发（教程清单里恰好没提这一项） |
| `JWT_SECRET` 长度 ≥ 32 **且不是模板值** | `.env.example` 里的 `change-me-please-use-a-strong-random-secret` 有 43 字符，**只查长度会误判为合规** |
| `DEFAULT_ADMIN_PASSWORD` | 占位符与 `admin` 都算没改 |
| `DATABASE_URL` / `REDIS_URL` / `CELERY_*` 端口 | override 改到 55432/56379，连接串不跟着改就连不上库 |
| `CORS_ORIGINS` | 留 `localhost` 会让线上前端被 CORS 拦掉 |

六、⚠️ 必须诚实说明的限制

```
· deploy.sh 语法已验：用 Git bash 跑 `bash -n deploy/deploy.sh` → 退出码 0
· ★ 但没有在真实服务器上跑过：我只有 Windows 环境、没有服务器凭据，
  起不了 systemd / 装不了 Nginx。**"逻辑正确"与"在你那台机器上一次跑通"是两回事**
· 因此脚本设计为【每步先校验再执行、且可重复执行】：某节失败直接重跑，不留半成品状态
· 最可能需要现场调整的是 UV_BIN（宝塔装的 Python 环境路径因机而异），
  脚本已支持 `UV_BIN=$(which uv) bash deploy/deploy.sh` 覆盖
```
