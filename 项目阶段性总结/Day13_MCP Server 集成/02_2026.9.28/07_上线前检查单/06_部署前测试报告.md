### 2.2 第 2 段：写链路 + 权限过滤真对照（13 OK / 0 FAIL）

**这一段是整个测试里最有价值的部分**，因为它造了"全库从来没有过"的数据形态（带权限标签的文档）：

```
上传       text/markdown 小文件 + permission_tags=['smoke_secret'] → 成功
Celery     status=uploading → ready，台账 status=success progress=1/1
★权限对照  admin 列表 total=22 可见 / alice 列表 total=21 不可见
           alice 取详情 → 404（不区分"不存在"与"无权"，与 REST 设计一致）
           alice 取切片 → 404
           alice 访问 /api/users、/api/roles → 403
           放宽标签为公开后 → alice 的 404 变 200（反向验证）
统计对账   与原始 SQL 逐一对齐：documents 22/21、chunks 339/332
清理      临时文档已删除、标签已复原
```

> 📌 **"反向验证"这一条很重要**：只验"看不见"有可能是过滤太狠（把该看的也挡了）；
> 放宽后立刻可见，才证明过滤是**按标签精确生效**的，而不是一刀切。

### 2.4 第 4 段：追查三条疑点（全部证伪）

| 疑点 | 追查结论 |
| --- | --- |
| SSE 事件名是 `citations`，脚本找的是 `citation` | **脚本错**：前端 `chatStream.ts:36` 期望的正是 `{type:'citations', citations: CitationRead[]}`，与后端一致 |
| citations 载荷"缺 8 个字段" | **脚本错**：载荷是信封结构 `{citations:[...]}`，我取错了层级 |
| 语义缓存不写入（Redis 52→52） | **预期不对**：`chat_service.py:703-705` 要求 `semantic_cache_enabled and not refused`，而那几次问句全被拒答。换一个能答上来的问题后，缓存立即命中（0.4s） |

**复盘**：三条里两条是断言写错、一条是测试数据选错。
**测试脚本的错误和产品 bug 一样会误导结论** —— 所以每条都追到源码/前端契约才下判断。

## 三、⚠️ 本轮我犯的错（测试侧的，逐条留档）

| # | 错误 | 怎么发现的 | 教训 |
| --- | --- | --- | --- |
| 1 | 断言事件名写成 `citation`（实际 `citations`）、citations 载荷少取一层 | 追到 `frontend/src/api/chatStream.ts:36` 才确认前端期望的形状 | **断言要对着契约写，不能凭印象** |
| 2 | 用"拒答型问题"去测语义缓存 | 读 `chat_service.py` 的缓存写入条件 | 测试数据要先确认能走进被测分支 |
| 3 | 第 1 段顺手创建了 `smoke_probe` 用户（污染数据，已删） | 第 2 段开始时核对用户表 | 冒烟脚本要自带清理，或至少把副作用写进 README |
| 4 | 第 5 段脚本分 3 次 `asyncio.run()` → 撞 `Event loop is closed` | 报错堆栈显示 Redis 客户端绑定在已关闭的循环上 | 限流器是 lru_cache 单例、Redis 客户端绑事件循环 → **全部异步步骤放同一个循环** |
| 5 | 生产 compose 第一版用 `${POSTGRES_PASSWORD:?...}` 强制口令，**实测无效** | `docker compose config` 能渲染通过 → 查出 compose 会自动读项目根 `.env`（里面是 `rag`） | compose 变量插值永远先看自动加载的 `.env`，**拦不住"存在的弱值"**；换 `--env-file` 才是有效隔离 |
| 6 | 文档里写"移到归档后 parents[2] 仍是项目根" | 实测 `parents[2]` 只到 `02_2026.9.28`，正确是 `parents[5]` | 移动文件后**路径层级必须实测**，不能推算 |
| 7 | 编辑 compose 时手滑把镜像名打成 `leikikko` | 立刻回看 diff 发现 | 改配置后要复查关键标识 |

> 这 7 条里，第 5 条最有价值 —— 它推翻了我原本写进"生产文件"的第一版防护，
> 属于"看起来做了安全加固、实际没有"的假安全，比不做更危险。
