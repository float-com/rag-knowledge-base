## 一、P0 项（不做就可能被打穿）

### ✅ P0-1 数据库与 Redis 不暴露到宿主机

**背景**：本地开发的 `docker-compose.yml` 把 5432/6379 发布到了 `0.0.0.0`，
公网机器上等于把数据库直接开放（弱口令 + 端口扫描 = 数据被拖走）。
改造方式：**新增生产专用编排** `docker-compose.prod.yml`，其中 postgres / redis
只 `expose` 不 `ports`，api / worker 进容器并用服务名互连。

**验证**：

```powershell
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d
docker ps --format "{{.Names}} {{.Ports}}"
# 预期：rag-kb-postgres / rag-kb-redis 的 Ports 列为空（只有容器内端口）
#      只有 rag-kb-api 出现 0.0.0.0:8000->8000

# 再确认从宿主机连不上（应连接失败/超时，不是密码错）
Test-NetConnection 127.0.0.1 -Port 5432
```

**⚠️ 已有数据卷时改口令**（`POSTGRES_PASSWORD` 只在**初始化空卷**时生效，改 `.env.prod` 不够）：

```powershell
docker exec rag-kb-postgres psql -U rag -d postgres -c "ALTER USER rag WITH PASSWORD '<新强口令>';"
# 改完同步 .env.prod 的 POSTGRES_PASSWORD，再重建 api / worker
```

### ✅ P0-2 JWT 密钥缺失/过短拒绝启动（`ENVIRONMENT=production`）

**背景**：原实现"密钥为空只打 ERROR 告警、照样启动"——等于门没锁却一切显示正常。
第 13 期改为按环境区分：`production` 下抛 `ConfigurationError` 拒绝启动，且要求
`len(JWT_SECRET) >= 32`；`development` 保持原行为（告警放行），本地不受影响。

**验证**（三种情况都必须符合）：

```powershell
cd backend
# ① 生产 + 空密钥 → 必须拒绝启动
uv run python -c "from app.core.config import Settings; Settings(environment='production', jwt_secret='').warn_if_jwt_unconfigured()"
# 预期：抛 ConfigurationError

# ② 生产 + 弱密钥（6 字符）→ 必须拒绝启动
uv run python -c "from app.core.config import Settings; Settings(environment='production', jwt_secret='123456').warn_if_jwt_unconfigured()"
# 预期：抛 ConfigurationError（提示 >= 32）

# ③ 生产 + 合规密钥（32+）→ 通过
uv run python -c "from app.core.config import Settings; Settings(environment='production', jwt_secret='x'*32).warn_if_jwt_unconfigured()"
# 预期：无异常
```

**生成密钥**：`openssl rand -hex 32`（或 `python -c "import secrets;print(secrets.token_hex(32))"`）

### ✅ P0-3 管理员口令不再是 `admin`

**背景**：`.env.example` 原来直接写 `DEFAULT_ADMIN_PASSWORD=admin`，
照抄部署 = 上线即存在人人皆知的管理员。已改为占位符 `CHANGE_ME_BEFORE_FIRST_START`，
并在生产环境对弱口令打 ERROR 告警。

**验证**：

```powershell
Select-String -Path .env.prod -Pattern "DEFAULT_ADMIN_PASSWORD"
# 预期：不是 admin / password / 123456

# 启动日志里不应出现这两行
#   "⚠️ 生产环境仍在使用默认/弱管理员口令"
```

**⚠️ 本项只在"库内无用户"时生效**。库已建号时改配置无效，必须重置：

```powershell
# 用后端自己的哈希函数生成 bcrypt 串，再写回数据库
cd backend
$h = uv run python -c "from app.core.security import hash_password; print(hash_password('<新口令>'))"
docker exec rag-kb-postgres psql -U rag -d rag_kb -c "update users set password_hash='$($h.Trim())' where username='admin';"
```

> 📌 更好的做法（**未实现，建议列入上线后第一周**）：给 `users` 加 `must_change_password` 列，
> seed 时置 true，首登强制改密。本次只做了"不留弱默认值"这一层。

### ✅ P0-4 MCP 通道补限流

**背景**：MCP 是 `app.mount("/mcp", ...)` 挂进来的独立 ASGI 子应用，**不走 FastAPI 依赖链**，
所以第 12 期给 REST 挂的 `enforce_rate_limit` 对它完全无效 ——
而 `ask_knowledge_base` 烧 LLM、`upload_document` 烧 embedding 与 COS。
这是第 12 期"新加一条通路要重新打钩能力清单"那条约定的第三次复现。

**改造**：新增 `app/mcp_server/limits.py::enforce_tool_limit(user, scope=...)`，
在 **ask** 与 **upload** 两个工具里各调一次；三个只读工具**刻意不限**
（与 REST 侧只读接口不挂限流的结论一致；且避免 Agent 的"了解环境"动作被限死）。

**验证**：

```powershell
# 把阈值临时调到 3，连调 4 次 ask_knowledge_base，第 4 次应被拒
# .env.prod: RATE_LIMIT_PER_MINUTE=3  → 重启 api
# 用 MCP 客户端连 /mcp，连续调用 ask_knowledge_base 四次
# 预期第 4 次返回：请求过于频繁，每分钟最多 3 次，请稍后再试
```

**两个设计要点**（写进代码注释了，改动时别丢）：

```
① key 带 "mcp-" 前缀 → 与 REST 的额度互不侵占
   （否则 MCP 问一次，网页侧就少一次额度，用户会莫名 429）
② 按 scope 分桶 → 上传不会吃掉问答额度
```

## 二、P1 项（已知风险，处置方式是"知道并接受"）

### ⚠️ P1-1 每次 MCP 调用有一次 307 重定向

**现象**：`POST /mcp` → 307 → `POST /mcp/` → 200。
**成因**：内层子应用路径设为 `/`，Starlette 对 mount 根路径的规范形式是带尾斜杠。
**影响**：MCP 客户端（httpx / MCP SDK / Cursor / Inspector）都会自动跟随，**功能不受影响**。
**真正的风险点**：**反向代理不跟随重定向** → 表现为"连不上"却查不到原因。

**上线必须确认两件事**：

```
① Nginx / 网关：确认 /mcp 的 proxy_pass 不会把尾斜杠规范化掉
   建议直接放行原始路径，不要在 location 上做 rewrite
② 用真实客户端连一次（Inspector / Cursor / Claude Desktop 任选）
   本次已实测 MCP Inspector 可正常列出 5 个工具
```

**若要彻底消除**：去掉 `streamable_http_path="/"` 并重新推算 mount 前缀 ——
但会牵动第 9 节那套"两层路径"的推理，收益很小，**本项目选择保留并留档**。

### ⚠️ P1-2 依赖锁在旧世代（`mcp 1.30.0` + `fastmcp 2.14.7`）

**背景**：为了让教程的 `from mcp.server.fastmcp import ...` 可用，本项目把
`mcp>=2.2.0` 回落为 `mcp>=1.30.0,<2` 并补了 `fastmcp>=2.14.7,<3`。
官方 v2 已把 FastMCP 改名为 `MCPServer`，所以这条链属于**上一代**。

**当前状态**：两者都仍在维护，**不是 EOL**，短期可接受。

**升级是一次破坏性迁移**，影响面清单（供将来评估）：

```
from mcp.server.fastmcp import FastMCP        →  from mcp.server.mcpserver import MCPServer
FastMCP(...)                                   →  MCPServer(...)
mcp.server.fastmcp.exceptions.ToolError        →  新路径
FastMCP.streamable_http_app()                  →  MCPServer.http_app()（2.x 已无前者）
mount_path 从构造参数移到 run() / app 方法
```

**建议**：等教程第 13 期讲完再**单独做一次升级**，不要边写文档边升 ——
否则代码与教程截图会全面对不上（第 2 章为对齐教程已经返工过一轮）。

**定期动作**：每月跑一次依赖漏洞扫描（`uv pip list --outdated` / `pip-audit`）。

## 四、首次部署的完整命令序列

```powershell
# 0. 准备生产变量文件（务必逐项替换占位值）
cp .env.prod.example .env.prod
#   必改：POSTGRES_PASSWORD / JWT_SECRET / DEFAULT_ADMIN_PASSWORD / CORS_ORIGINS
#         COS_* / EMBEDDING_* / CHAT_*

# 1. 构建并启动（api 启动时会先跑 alembic upgrade head）
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build

# 2. ★ 预热 Docling 模型（不做的话 PDF 解析必失败 —— 第 12 期 BUG-05 那个坑）
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm api \
  python scripts/preheat_models.py

# 3. 健康检查
curl http://127.0.0.1:8000/api/health
curl http://127.0.0.1:8000/api/health/db
curl http://127.0.0.1:8000/api/health/cos

# 4. 契约回归（应为 paths 29 / operations 40）
curl -s http://127.0.0.1:8000/openapi.json | python -c "import json,sys; d=json.load(sys.stdin); print(len(d['paths']))"

# 5. MCP 连通性（用真实客户端，不要只 curl）
#    参考 backend/.smoke/ 里的脚本，或直接用 MCP Inspector 连 http://<域名>/mcp

# 6. 若库是【复用】的旧库：重置管理员口令（见 P0-3）
```
