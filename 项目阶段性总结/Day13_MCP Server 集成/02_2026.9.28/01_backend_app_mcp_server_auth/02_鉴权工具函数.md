## 〇、三分钟速览（先读这一节）

```
本章要解决的一件事：
        MCP 工具被调用时，怎么知道现在是谁在调？

本章的入口只有一个：
        resolve_current_user(ctx) -> User        ← 后面 5 个工具的第一行都是它

本章的核心链路（六步，与网页侧 api/deps.py 逐行对齐）：
        解析 Authorization → 取出 Bearer 令牌 → 验签拿到 subject
            → UUID 转型 → 查库 → 校验 status == ACTIVE → 返回 User

本章唯一的差异（只有出口不同）：
        网页侧 get_current_user  抛 UnauthorizedError → HTTP 401
        MCP 侧 resolve_current_user 抛 ToolError      → 协议层 isError 文本
        原因：MCP 协议里【没有 401 这个概念】，它讨论的是"工具调用失败"

本章最该记住的两句坑话：
        教程的 from mcp.server.fastmcp import ... 在本项目跑不起来（mcp 2.x 已删掉该模块）
        我抛的 ToolError 会被 fastmcp 再包一层 "Error executing tool xxx: "，不是原样返回
```

## 二、为什么不能直接 import 网页侧的 `get_current_user`

### 2.1 两者入参来源不同

| | 网页侧（RESTful） | 本章（MCP） |
| --- | --- | --- |
| 请求头来源 | FastAPI 注入的 `Authorization` 参数（`Header(alias=...)`） | `ctx.request_context.request.headers` |
| 失败出口 | `UnauthorizedError` → 全局异常处理器 → HTTP 401 | `ToolError` → 协议层以 isError 内容返回给 Agent |
| 取用户 | `UserRepository(session).get_by_id()` | 同一份（**故意保持一致**） |

网页侧靠的是 `Depends` + `Header` 这套**框架注入机制**；MCP 这一层没有依赖注入，
工具函数拿到的是 `Context`，真正的 HTTP 请求要自己从 `ctx.request_context.request` 里取。

> ⚠️ 上表最后一列写的是**本章对外的入口**（`resolve_current_user`）。
> 内部那个 `_parse_bearer_token` 并不抛 `ToolError`，它抛的是 `UnauthorizedError`
> —— 与网页侧同名函数行为一致，转译只发生在 `resolve_current_user` 的 `except` 处。

### 2.2 ★ 但链路必须逐行对齐（本章最重要的设计约束）

```
解析 Authorization → 取出 Bearer 令牌 → 验签拿到 subject
    → UUID 转型 → 查库 → 校验 status == ACTIVE → 返回 User
```

这六步与 `app/api/deps.py::get_current_user` **一步一步对齐**，只有"失败时抛哪个异常"不同。

**为什么必须对齐**：鉴权口径一旦有第二份实现，就会出现
「**网页登不进、Agent 却能进**」这类漏洞；将来加"令牌黑名单"之类的机制时，
只改一处是修不掉两边的。

实测对照过 `api/deps.py`，本章用到的全是项目现成接口，没有一处杜撰：

```
AsyncSessionLocal                                    app/db/session.py
UserRepository.get_by_id                             app/db/repositories/user_repo.py
UserStatus.ACTIVE                                    app/db/models.py
decode_access_token                                  app/core/security.py
permission_service.is_admin                          app/services/permission_service.py
```

## 三、代码逐段讲解（`auth.py`）

### 3.1 第一步：`_parse_bearer_token` —— 纯字符串的令牌提取

```python
def _parse_bearer_token(authorization: str | None) -> str:
    if not authorization:                                  # 步骤 1：根本没带请求头
        raise UnauthorizedError("请先登录")

    scheme, _, token = authorization.partition(" ")        # 步骤 2：拆前缀与令牌
    if scheme.lower() != "bearer" or not token:            # 步骤 3：前缀必须 Bearer 且令牌非空
        raise UnauthorizedError("无效的访问凭证")
    return token
```

几个容易忽略的点：

| 细节 | 为什么 |
| --- | --- |
| 用 `partition(" ")` 而不是 `split(" ")` | partition 恒定返回 3 个元素；`split` 遇到 `"Bearer"`（无空格）只产出 1 个元素，解包直接抛 `ValueError`，会把"客户端拼错请求头"变成 500 |
| `scheme.lower()` | HTTP 规范里认证方案名大小写不敏感，`bearer` / `BEARER` 都合法 |
| 两种失败给不同文案 | 没带请求头 = 用户没登录（提示"请先登录"）；带了但不是 Bearer = **请求构造错了**（提示"无效的访问凭证"，开发者能直接定位到客户端问题）。本章鉴权是 Bearer 令牌，工具链里**没有密码**，不存在"密码错"这种情形 |
| `_` 是哑变量 | 接收被切出来的那个空格，占位且后续不使用 |

### 3.2 第二步：`resolve_current_user` —— 从 Context 反查用户

```python
request = getattr(ctx.request_context, "request", None)     # 步骤 1
if request is None:
    raise ToolError("当前传输模式不支持基于 HTTP Header 的身份鉴权")

try:                                                        # 步骤 2
    token = _parse_bearer_token(request.headers.get("authorization"))
    subject = decode_access_token(token)
    user_id = UUID(subject)
except (AppException, ValueError) as exc:
    raise ToolError(_user_facing_message(exc, default="无效的访问凭证")) from exc

async with AsyncSessionLocal() as session:                  # 步骤 3：短生命周期会话
    user = await UserRepository(session).get_by_id(user_id)

if user is None:                                            # 步骤 4
    raise ToolError("用户不存在或已被删除")
if user.status != UserStatus.ACTIVE:                        # 步骤 5
    raise ToolError("账号已被停用")
return user
```

**① 为什么写成 `getattr(..., "request", None)` 而不是直接取属性**

本项目传输方式固定为 Streamable HTTP，`ctx.request_context` 上一定带 `request`。
写成 getattr + 默认值是**为了非 HTTP 传输（如 stdio）也能给出可读原因**，
而不是抛一个 `AttributeError` 让调用方去猜。

**② ★ `except (AppException, ValueError)` 里 `ValueError` 为什么必须并列**

```
_parse_bearer_token  → UnauthorizedError（AppException 子类，HTTP 401）
decode_access_token  → UnauthorizedError（过期 / 签名不对 / 算法不在白名单）
UUID(subject)        → ValueError      ★ 不是"凭证错"，而是 sub 不是合法 UUID
```

`ValueError` 属 Python 内置异常，**与 `AppException` 毫无继承关系**，
少写它，脏 `sub` 就会冒成工具内部错误而不是"无效的访问凭证"。

**③ 为什么统一模糊成"无效的访问凭证"**

不把"是过期还是签名伪造"告诉调用方，是对外的有意的收敛（避免给攻击者枚举线索）；
真实原因仍留在 `from exc` 的异常链里，服务端日志看得到。

**④ 为什么自己开 session：**

MCP 这里没有 FastAPI 的 `Depends` 可自动开合会话，所以自己开一个**短生命周期**会话，
查完立刻归还连接（"即查即关"）。

> ⚠️ 返回的 `user` 已脱离会话（Detached），但**不同属性的安全性不一样，别一概而论**：
> - `user.roles` 是安全的：`User.roles` 声明了 `lazy="selectin"`，
>   而 `UserRepository.get_by_id` 走 `session.get(User, id)` 会顺带把 roles 一起加载；
> - **不安全的是"没被预加载的关联属性"**：访问它会为已关闭的会话触发 IO，
>   在异步引擎下抛的是 **`MissingGreenlet`**（同步 `lazy="select"` 会撞的那个），
>   而不是 `DetachedInstanceError`。
>
> 结论：工具里若要读关联数据，**自己新开 session 用仓储查**，不要指望这个实例。

### 3.3 第三步：`require_admin` —— 工具级的管理员闸门

```python
def require_admin(user: User) -> None:
    if not is_admin(user):
        raise ToolError("仅管理员可调用此工具")
```

- 复用 `permission_service.is_admin`，与网页侧 `get_current_admin` 是**同一个函数**；
  将来新增一种管理员（如 audit_admin），只改 `is_admin` 一处，两边同时生效
- 差别同样只在出口：网页侧抛 `PermissionDeniedError`（HTTP 403），这里抛 `ToolError`

### 3.4 第四步：`_user_facing_message` —— 异常文案的统一翻译

```python
def _user_facing_message(exc: Exception, *, default: str) -> str:
    if isinstance(exc, AppException):
        return exc.message
    return default
```

- `AppException` 的子类自带写给人看的中文 message（"请先登录"/"账号已被停用"），
  这正是 Agent 最能利用的信息；`ValueError` 这类原生异常没有，其 `str()` 可能带实现细节，
  不适合透给外部调用方 → 统一换成兜底文案
- **`default` 的真实用途**：本章唯一调用点同时捕获了 `AppException` **与 `ValueError`**，
  后者没有 message，`default`（传 `"无效的访问凭证"`）就是给它的。
  少了它，脏 `sub` 会把 `badly formed hexadecimal UUID string` 直接暴露给 Agent
- **为什么用 `isinstance` 而不是 `getattr(exc, "message", default)`**：
  ① isinstance 后静态检查器知道 `exc` 就是 `AppException`，`exc.message` 取得到；
  ② 语义诚实 —— 本函数要表达的是"只把**业务异常**的文案透出去"，
  而不是"凡是碰巧带 message 属性的都放行"

## 四、★ MCP 侧的错误出口到底长什么样（实测）

协议层没有 HTTP 状态码，那 `ToolError` 最后变成了什么？实测（fastmcp 2.14.7 / mcp 1.30.0）：

```
我 raise ToolError("无效的访问凭证")
    ↓  mcp/server/fastmcp/tools/base.py:116-117
       except Exception as e: raise ToolError(f"Error executing tool {self.name}: {e}")
    ↓  mcp/server/lowlevel/server.py:589-590
       except Exception as e: return self._make_error_result(str(e))
    ↓  mcp/server/lowlevel/server.py:473-480
       CallToolResult(content=[TextContent(text=error_message)], isError=True)
```

**→ Agent 读到的文本是 `Error executing tool xxx: 无效的访问凭证`，不是原样一句。**
写验收用例时必须按这个形状断言。

同时确认的三条（都在 `app/core/security.py` 核过）：

```
过期        → jwt.ExpiredSignatureError → UnauthorizedError("登录已过期，请重新登录")
签名/格式错 → jwt.InvalidTokenError     → UnauthorizedError("无效的访问凭证")
算法白名单  → algorithms=[settings.jwt_algorithm]（防 None 算法 / 算法降级）
```

## 五、⚠️ 本章最花时间的一件事：教程的 import 在本项目跑不起来

### 5.1 现象

教程写 `from mcp.server.fastmcp import Context`，而本项目 `pyproject.toml` 是 `mcp>=2.2.0`，实测直接失败：

```
ModuleNotFoundError: No module named 'mcp.server.fastmcp'.
  This is mcp 2.x, where FastMCP was renamed to MCPServer ...
```

### 5.2 三种组合各自实测（临时探针 venv，验完即删）

| 组合 | 结果 |
| --- | --- |
| `mcp 2.2.0`（原状） | ❌ 失败 |
| `mcp 2.2.0` + `fastmcp 4.0.10` | ❌ **仍然失败** |
| **`fastmcp 2.14.7`（自带 `mcp 1.30.0`）** | ✅ 通过：`Context` / `ToolError` / `streamable_http_app` 全在 |

### 5.3 为什么"补装 fastmcp"也不行

把安装包源码 `mcp/server/fastmcp.py` 打开看过 —— 它**不是**"等 fastmcp 来点亮"的 shim，
而是一块**无条件 raise 的墓碑**，文件里的原话：

> This module has no API. Importing it, or anything below it, raises `ModuleNotFoundError`.

### 5.4 结论与改动

```toml
# backend/pyproject.toml
"fastmcp>=2.14.7,<3",     # 新增
"mcp>=1.30.0,<2",         # 原 mcp>=2.2.0 → 回落：教程的 import 属于 mcp 1.x 时代
```

**回归验证**：降级后 `app.main` 装配正常，OpenAPI 仍为 **paths 29 / operations 40**
（与第 1 章定的回归底线 R1 一致）。
