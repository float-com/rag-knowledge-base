三、★ 三条关键设计判断

· 判断一：不能直接 import 网页侧的 get_current_user，但链路必须逐字对齐
  · 网页侧的 get_current_user 是 FastAPI 依赖（Depends + Header 注入），MCP 侧拿到的是 Context，
    两者入参来源与错误出口都不同，无法复用同一个函数
  · 但六步链路（解析 → Bearer → 验签 → UUID → 查库 → 校验 ACTIVE）与 api/deps.py 一步一步对齐，
    只有"失败时抛哪个异常"不同：网页侧 UnauthorizedError（HTTP 401）、MCP 侧 ToolError
  · 理由：鉴权口径一旦有第二份实现，就会出现"网页登不进、Agent 却能进"这类漏洞；
    将来加令牌黑名单之类的机制，只改一处是修不掉两边的
  · 实测对照过 api/deps.py：AsyncSessionLocal / UserRepository.get_by_id / UserStatus.ACTIVE /
    permission_service.is_admin 全部是项目现成接口，没有杜撰

· 判断二：MCP 协议没有 HTTP 状态码这一层，所以失败要翻译成 ToolError
  · AppException 自带 code / message / http_status，是给 HTTP 响应用的
  · MCP 里 Agent 看到的是"工具调用失败 + 一段文本"，所以由 _user_facing_message 把业务异常降维成一句话，
    把 HTTP 细节收敛在这一层，不让它泄漏到协议层
  · ★ 实测错误出口的完整形状：我抛的 ToolError 会被 fastmcp 再包一层
    "Error executing tool xxx: "（fastmcp/server/server.py 与 tools/base.py），
    最后由 lowlevel server 的 _make_error_result 转成 CallToolResult(isError=True)
    → 写验收用例时要按这个断言，不能按"原样返回"断言

· 判断三：本模块只做"认证"，不做"鉴权"
  · 认证（你是谁）→ resolve_current_user；鉴权（你能不能）→ require_admin + 业务层按 permission_tags 过滤
  · permission_tags 的计算留给各工具去调 permission_service.compute_user_permission_tags(user)，
    本模块不缓存、不猜测用户可见范围 —— 这是第 1 章 §3.5 定下的头号风险对策（只传参、不判权）

五、⚠️ 本次最花时间的一件事：教程的 import 在本项目跑不起来（依赖版本错配）

· 现象：教程写 from mcp.server.fastmcp import Context，但本项目 pyproject 里是 mcp>=2.2.0，实测直接失败
    ModuleNotFoundError: No module named 'mcp.server.fastmcp'.
      This is mcp 2.x, where FastMCP was renamed to MCPServer ...
· ★ 排查过程（三种组合各自实测，用一个临时探针 venv 验证，验完即删）
    ① mcp 2.2.0（原状）                     → 失败
    ② mcp 2.2.0 + fastmcp 4.0.10            → 仍然失败
    ③ fastmcp 2.14.7（自带 mcp 1.30.0）     → ★ 通过，Context / ToolError / streamable_http_app 全都在
· ②为什么也不行：把安装包源码 mcp/server/fastmcp.py 打开看过 ——
    它不是"等 fastmcp 来点亮"的 shim，而是一块【无条件 raise】的墓碑，注释原文写着
    "This module has no API. Importing it, or anything below it, raises ModuleNotFoundError"
· 结论与改动（pyproject.toml）：
    · 新增 fastmcp>=2.14.7,<3
    · 把 mcp>=2.2.0 回落为 mcp>=1.30.0,<2   ← 教程的 import 属于 mcp 1.x 时代
    · 用户当时的诉求是"保留教程 import 不动"，这个组合是唯一能兑现它的方案
· ★ 回归验证：降级后 app.main 装配正常，OpenAPI 仍为 paths 29 / operations 40
    （与第 1 章定的回归底线 R1 一致，挂载/降级都没有波及 /api/*）
