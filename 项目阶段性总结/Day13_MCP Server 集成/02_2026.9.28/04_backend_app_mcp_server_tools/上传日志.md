四、★ 三条关键设计判断

· 判断一：register_tools(mcp) 把实例"从外面传进来"，不在模块级建实例
    · 好处：挂载它的地方决定叫什么名字、挂到哪个路径；本模块只负责"有哪些工具"
      要用时一行：from app.mcp_server.tools import register_tools; register_tools(mcp)
    · 工具函数定义在函数体内部（闭包）：必须捕获外层的 mcp 才能写 @mcp.tool(...)；
      定义在模块级再手动 mcp.tool()(fn) 也可以，但那样工具函数会变成模块级公开 API
      （容易被别处误调用），且装饰器的 name / description 离函数更远、改契约时更易漏

· 判断二：全模块唯一的错误出口 _to_tool_error
    · AppException → 直接透出 exc.message（中文人话，如"文件为空"），Agent 能转述给用户
    · 其它异常      → 只给 default 兜底文案，同时 logger.exception 打完整堆栈
    · 这是"对外收敛、对内透明"：ValueError / KeyError 的 str() 可能是实现细节，
      透给外部既不安全也帮不上模型；排查时必须看得到，所以进日志
    · 它与第 2 章 auth.py 的 _user_facing_message 同构（都只认业务异常的 message），
      区别是出口不同：auth 那侧是鉴权链路早期错误，这里是各工具的业务错误

· 判断三：★ 出参【显式逐字段构造】，绝不用 model_validate
    · 服务层 citation 是 dict，里面带着 chunk_id / score / retrieval_meta 等内部调试字段
      （第 4 章 _serialize_citation 产出的）
    · 显式取字段 = 白名单脱敏
    · 若改成 MCPCitation.model_validate(c)，内部字段会不会漏出去，
      就取决于"Pydantic 的 extra 策略 + 名字是否恰好撞上"—— 那是靠运气，不是靠设计
    · 这是第 3 章"独立 schema"的意义在代码里的兑现

五、★ upload_document：为什么要把 bytes 包装成 UploadFile

· 问题：DocumentService.upload 的签名要求 UploadFile（实测确认），
  因为它姓"UploadFile"、是给 FastAPI 路由写的（路由收到 multipart，框架直接注入）；
  而 MCP 协议【没有 multipart 概念】，文件内容只能作为字符串塞进 JSON 参数

· 两条路，选了后者：
    · 改 DocumentService.upload 让它接受 bytes / 两种类型
      → ❌ 会波及网页侧上传链路（第 12 期刚改过的文件），风险面大
    · ★ 在 MCP 层适配：base64 还原成 bytes，再包一个"兼容 UploadFile 接口"的轻量对象
      → ✅ 服务层完全不知情

· _Base64UploadFile 的鸭子类型思路：
    · 实测 service 只用到三个属性：filename / content_type / read()
    · 那就只提供这三样，不去造真的 UploadFile（那需要 starlette 的文件对象 + SpooledTemporaryFile）
    · ⚠️ 它与真 UploadFile 的差异，将来改 service 时必须知道：
        read() 每次返回全量字节、不推进游标（真货有游标语义）
        没有 seek / size / file / headers —— service 一旦开始用就会 AttributeError
      即：本类只适合"当前这个" service.upload，是有边界的适配器，不是通用替身

· 上传工具的四道关（顺序不能反）：
    ① resolve_current_user(ctx)      认人
    ② require_admin(admin)           鉴权：写操作要 admin（第 1 章 §3.7 定的边界）
    ③ if not filename.strip()        挡参数
    ④ base64.b64decode(..., validate=True)   解码 + 格式校验
    → 之后全交给服务层（幂等 sha256 秒传、大小限制、MIME 检测一行都没重写）

六、★ 本次写进代码的 6 处步骤/语法注释

· 模块 docstring   三步说明：为什么要 register_tools / 每个工具的五步 / 错误出口统一走 _to_tool_error
· register_tools   为什么工具函数要定义在函数体内部（闭包捕获 mcp；避免模块级公开 API）
· ask_knowledge_base 步骤 1~5 全部编号：认人 → 挡参数 → 短会话调服务 → 翻译错误 → 出参显式构造
· 出参构造处       为什么不用 model_validate（白名单脱敏 vs 靠运气）
· upload_document  四道关 + base64 为什么必须 validate=True
                  （不加会"尽力猜测、静默丢字节"，写出内容被悄悄截断的文档，比报错难查）
· _status_value    只 strip() 不兜底：库里出现契约未声明的状态时应让校验失败并报出来，
                  静默改成 "ready" 尤其危险（Agent 会以为文档已可检索）；
                  # type: ignore[return-value] 的来历也写清了
· 语法点           from __future__ import annotations 的真实作用，并澄清一个常见误解：
                  它【不负责类型转换】—— status 的字符串→Literal 收敛仍需 _status_value 显式处理
