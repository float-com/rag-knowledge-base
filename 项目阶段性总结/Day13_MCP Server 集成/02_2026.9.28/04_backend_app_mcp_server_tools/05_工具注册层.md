## 〇、三分钟速览（先读这一节）

```
本章要解决的一件事：
        把协议层接到业务层 —— 外部 Agent 调用的名字，怎么变成 service 层能接住的那次调用。

本章的产物：
        app/mcp_server/tools.py
            register_tools(mcp)          5 个工具的统一注册入口
            工具 1  ask_knowledge_base   向知识库提问（本节的完整实现）
            工具 2  upload_document      上传文档（仅管理员，base64 传文件）
            _to_tool_error()             业务异常 → 协议层 ToolError 的唯一出口
            _Base64UploadFile            bytes → 兼容 UploadFile 的轻量对象
            _status_value()              ORM 字符串状态 → 契约 Literal

每个工具都是同一套五步：
        resolve_current_user(ctx)    认人
            → require_admin(user)    需要管理员的工具再上一道闸门
            → 参数校验                外部传进来的参数必须自己挡
            → 调 service 方法         业务逻辑一律在 app/services
            → 翻成 MCP schema         出参显式构造，不用 model_validate

本章最该记住的三句：
        ① 本模块【不写业务逻辑】：不判权限、不拼 SQL、不算向量
        ② 错误出口只有一个：_to_tool_error，业务异常的中文 message 直接透给 Agent
        ③ 两个同名异常别混：服务层 AppException 与 协议层 mcp...exceptions.ToolError
```

## 二、★ 步骤 1：为什么是 `register_tools(mcp)`，而不是模块级建实例

```python
def register_tools(mcp: FastMCP) -> None:
    @mcp.tool(name="ask_knowledge_base", title="知识库问答", description="...")
    async def ask_knowledge_base(question: str, ctx: Context) -> MCPAnswer:
        ...
```

| 设计点 | 说明 |
| --- | --- |
| 实例**从外面传进来** | 挂载它的地方决定叫什么名字、挂到哪个路径；本模块只负责"有哪些工具"。要用时一行：`register_tools(mcp)` |
| 工具函数定义在**函数体内部**（闭包） | 它们必须捕获外层的 `mcp` 才能写 `@mcp.tool(...)`。定义在模块级再手动 `mcp.tool()(fn)` 也可以，但那样工具函数会变成模块级公开 API（容易被别处误调用），且装饰器的 name / description 会离函数更远、改契约时更容易漏 |

> ⚠️ 这也解释了为什么本模块**没有**顶层 `mcp = FastMCP(...)`：
> 那样会在 import 时创建实例，挂载顺序与命名就失控了。

## 三、★ 步骤 2：`ask_knowledge_base` 五步逐段讲解

### 3.1 步骤 2a：认人

```python
user = await resolve_current_user(ctx)
```

MCP 侧没有 FastAPI 的依赖注入，必须显式解析当前用户（第 2 章的实现：
`Context → ctx.request_context.request.headers → Bearer 令牌 → 查库 → 活跃用户`）。

### 3.2 步骤 2b：挡参数

```python
question = question.strip()
if not question:
    raise ToolError("问题不能为空")
```

**为什么必须自己挡**：MCP 的参数来自外部 Agent，空字符串**能通过协议层的类型校验**（它确实是 `str`），
所以类型系统挡不住它，必须在语义层拦一次。

### 3.3 步骤 2c：短会话调服务

```python
async with AsyncSessionLocal() as session:
    service = ChatService(session)
    try:
        result = await service.answer_for_mcp(question, current_user=user)
    except Exception as exc:
        raise _to_tool_error(exc, default="问答处理失败") from exc
```

三件事同时发生：

| 动作 | 为什么要这么做 |
| --- | --- |
| 自己开 session | MCP 侧没有 `Depends` 自动开合会话，要自己开、自己关（第 2 章定下的"即查即关"） |
| 调 `answer_for_mcp` | 第 4 章的入口：真实用户权限过滤、跑同一张 RAG 图、异常一路冒出 |
| `except Exception` + `_to_tool_error` | ★ **翻译点就在这一行** —— 第 4 章"服务层不翻译、工具层翻译"的结论在此落地 |

### 3.4 步骤 2d：出参显式构造（**不是** `model_validate`）

```python
citations = [
    MCPCitation(
        ordinal=int(c["ordinal"]),
        document_id=c["document_id"],
        document_name=c["document_name"],
        page_no=c.get("page_no"),
        section_path=c.get("section_path"),
        quote=c.get("quote", ""),
    )
    for c in result.citations
]
return MCPAnswer(answer=result.answer, refused=result.refused,
                 citations=citations, trace_id=result.trace_id)
```

**为什么不用 `model_validate`**：服务层返回的 citation 是 dict，里面带着
`chunk_id` / `score` / `retrieval_meta` 等**内部调试字段**（第 4 章的 `_serialize_citation` 产出的）。
显式逐字段取 = **白名单脱敏**；

> 若改成 `MCPCitation.model_validate(c)`，`retrieval_meta` 这些内部字段会不会漏出去，
> 就取决于"Pydantic 的 extra 策略 + 名字是否恰好撞上"—— 那是靠运气，不是靠设计。
> **这是第 3 章"独立 schema"的意义在代码里的兑现。**

## 四、★ 步骤 3：`_to_tool_error` —— 全模块唯一的错误出口

```python
def _to_tool_error(exc: Exception, *, default: str) -> ToolError:
    if isinstance(exc, AppException):
        return ToolError(exc.message)
    logger.exception("MCP tool unexpected error")
    return ToolError(default)
```

| 分支 | 对外 | 对内 |
| --- | --- | --- |
| `AppException` | 直接透出 `exc.message`（中文人话，如"文件为空"） | —— |
| 其它异常 | 只给 `default` 兜底文案 | `logger.exception` 打**完整堆栈** |

这是"**对外收敛、对内透明**"的标准做法：`ValueError` / `KeyError` 的 `str()` 可能是实现细节，
透给外部调用方既不安全也帮不上模型；但排查时必须看得到，所以进日志。

> 它与第 2 章 `auth.py` 的 `_user_facing_message` **同构**（都只认业务异常的 message），
> 区别是出口不同：auth 那侧是鉴权链路早期错误，这里是各工具的业务错误。

## 五、★ `upload_document`：为什么要把 bytes 包装成 UploadFile

### 5.1 问题

```
DocumentService.upload 的签名（实测）：
    async def upload(self, file: UploadFile, *, created_by=None, permission_tags=None) -> Document

它姓"UploadFile"，是因为它是给 FastAPI 路由写的：
路由收到 multipart，框架直接把 UploadFile 注进来。

而 MCP 协议【没有 multipart 概念】—— 文件内容只能作为一个字符串塞进 JSON 参数。
```

有两条路：

| 方案 | 取舍 |
| --- | --- |
| 改 `DocumentService.upload`，让它接受 bytes / 两种类型 | ❌ 会波及**网页侧上传链路**（第 12 期刚改过的文件），风险面大 |
| ★ 在 MCP 这一层适配：把 base64 还原成 bytes，再包一个"兼容 UploadFile 接口"的轻量对象 | ✅ **服务层完全不知情** |

教程选了后者，本项目照做。

### 5.2 `_Base64UploadFile` 的鸭子类型思路

```python
class _Base64UploadFile:
    def __init__(self, *, filename, content, content_type) -> None:
        self.filename = filename
        self.content_type = content_type or ""
        self._content = content

    async def read(self) -> bytes:
        return self._content
```

**服务层真正用到什么，就只提供什么**：

```
实测 DocumentService.upload 只用到三个属性：filename / content_type / read()
→ 那就不必去造一个真的 UploadFile（那需要 starlette 的文件对象 + 底层 SpooledTemporaryFile）
→ 面向接口而非实现：给一个"鸭子"，不是造一个"孪生兄弟"
```

> ⚠️ **它与真 `UploadFile` 的差异，将来改 service 时必须知道**：
> - `read()` 每次返回**全量字节、不推进游标**（真 UploadFile 有游标语义）；
> - **没有** `seek` / `size` / `file` / `headers` 等属性 —— 一旦 service 开始用它们，
>   这里会直接 `AttributeError`。
>
> 也就是说：本类只适合"当前这个" `service.upload`，它是一个**有边界的适配器**，不是通用替身。

### 5.3 base64 解码：`validate=True` 是刻意的

```python
try:
    content = base64.b64decode(content_base64, validate=True)
except (binascii.Error, ValueError) as exc:
    raise ToolError("content_base64 不是合法的 base64 编码") from exc
```

`validate=True` 让"字母表之外的字符"（换行、空格、URL-safe 的 `-_`）**直接报错**，
而不是"尽力猜测、静默丢字节" —— 后者会写出一个**内容被悄悄截断**的文档，
比当场报错难查得多。

### 5.4 上传工具的四道关（按顺序）

```python
admin = await resolve_current_user(ctx)     # ① 认人
require_admin(admin)                        # ② 鉴权：写操作要 admin（第 1 章 §3.7 定的边界）
if not filename.strip(): raise ToolError(...)   # ③ 挡参数
content = base64.b64decode(..., validate=True)  # ④ 解码（含格式校验）
→ 包装成 UploadFile 兼容对象 → service.upload(...)  # ⑤ 之后全交给服务层
```

**为什么顺序不能反**：先 `resolve_current_user`（拿到人）再 `require_admin`（判资格）。
反过来的话，`require_admin` 没有 user 可判。

**幂等、大小限制、MIME 检测**全部走 service 层既有逻辑（含 sha256 秒传），
工具层**一行都没重写** —— 这是"只做协议转换"的具体体现。

### 5.5 `_status_value`：只 `strip()`，不兜底

```python
def _status_value(raw: str) -> DocumentStatusValue:
    return raw.strip()  # type: ignore[return-value]
```

| 选择 | 理由 |
| --- | --- |
| 只做 `strip()` | "尾随空格"这种最常见的存储瑕疵，不值得让整条链路失败 |
| **不做兜底映射** | 库里若出现契约未声明的状态，正确行为是**让校验失败并报出来**。把未知状态静默改成 `"ready"` 尤其危险 —— Agent 会以为文档已可检索 |
| `# type: ignore[return-value]` | `str.strip()` 静态返回 `str`，检查器无法证明它落在 Literal 集合内；合法性由 Pydantic 构造时兜底校验，所以显式忽略而不是用 `cast()` 假装安全 |

## 六、★ 语法点：`from __future__ import annotations`

```python
from __future__ import annotations
```

它把本模块所有类型注解变成**字符串**、延后求值，两个实际好处：

```
① 注解里可以自由引用尚未定义的名字（前向引用不必加引号）
② 注解的求值成本从"导入时"推迟到"真的需要时"
```

> ⚠️ **一个常见误解要澄清**：它**不负责类型转换**。
> 即使加了它，`status=document.status` 这种"字符串 → Literal"的收敛
> **也不会**自动发生，仍要靠 `_status_value` 显式处理。

## 九、排错速查表

| 现象 | 最可能的原因 | 先查哪里 |
| --- | --- | --- |
| Agent 收到 `Error executing tool xxx: ...` | 正常现象：fastmcp 会给错误文案包一层 | 第 2 章的错误出口链 |
| 工具报错但看不到原因 | 异常不是 `AppException`，走了 `default` 兜底 | `_to_tool_error` 的 isinstance 分支 + 服务端日志（`logger.exception` 有完整堆栈） |
| 空问题被送进 RAG 图 | 少了 `if not question` 那道挡 | `ask_knowledge_base` 步骤 2 |
| base64 传错却生成了残缺文档 | 解码没用 `validate=True` | `base64.b64decode(..., validate=True)` |
| 非管理员也能上传 | `require_admin` 被删了或顺序反了 | `upload_document` 步骤 1 |
| `AttributeError: ... has no attribute 'seek'` | service 开始用 `_Base64UploadFile` 没提供的接口 | 第五节 5.2 的"差异清单" |
| `ValidationError` 说 status 不是合法取值 | 库里出现了契约未声明的状态 | `_status_value` 的设计取舍（**故意不兜底**） |
| 出参里冒出 `retrieval_meta` | 改成 `model_validate` 了 | 第三节 3.4：必须显式逐字段构造 |

### 10.2 ★ 出图规矩（第 4 章第九节定下，本章起统一执行）

```
规矩 1  节点标签只用一种 HTML 标签 <b>
        换行只用 <br/>，绝不用源码里的裸换行
        （第 4 章踩过：裸换行会生成 refused / true / false 这类孤儿节点）
规矩 2  任何一行都不以 [ ( ' = , 结尾
        方括号改文字表达（写 retrieved_chunks，不写 list[...]）
        参数序列用「与」/「·」连接
        （第 4 章踩过：未加引号的半角括号会被当成形状定界符，截断后生成孤儿节点）
规矩 3  每行不超过约 26 个字符，中英混排尤其要短
        （第 4 章踩过：长行 + HTML 标签，导出后文字被切）
规矩 4  节点定义与连线分两段写：前半段只定义节点，后半段只连边
        即使某行被误解析，也不会长进节点文字里
规矩 5  init 一律加 useMaxWidth: true 与 padding: 12
        宁可整体缩小，也不让边缘被切
```

### 10.3 出图后的 5 秒自检

```
① 搜 (c, / (). / verify( 三种形态：不在行首、也不在引号内的，就是下一个孤儿节点
```
