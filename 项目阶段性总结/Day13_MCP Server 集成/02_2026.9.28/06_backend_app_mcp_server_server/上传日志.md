三、★ 第 8 章：三个部署开关各自解决什么

| 开关 | 作用 | 为什么本项目要它 |
| --- | --- | --- |
| stateless_http=True | 每次工具调用独立处理，不维护跨请求 session | 与 RAG 一次性问答语义天然契合（第 4 章甚至强制 chat_history = []），方便横向扩容。代价：session 级能力（服务端推送 / 进度订阅）不可用 —— 本项目不需要 |
| json_response=True | 响应直接 JSON，不走 SSE | 5 个工具都是"一次调用一个结果"，流式只会给客户端增加解析成本 |
| streamable_http_path="/" | ★ 让内层端点挂在根路径 | 默认是 /mcp，而第 9 节要 mount 到 /mcp，两者一叠就是 /mcp/mcp。改成 "/" 后，外层 mount 前缀才是唯一决定路径的地方 |

· instructions 是【写给模型看的说明书】，所以写成动作指南而不是功能清单（先调谁、再调谁）
· 实例为什么建在 server.py 而不是 tools.py：
    tools.py 只管"有哪些工具"（register_tools 接收实例），对"挂在哪个实例"一无所知；
    server.py 是唯一创建实例的地方，并在模块级完成注册 ——
    于是 import 一次就拿到"工具已经挂好"的实例
· __init__.py 为什么只导出 knowledge_mcp：
    第 9 节要用它做两件事 —— session_manager.run() 与 streamable_http_app()；
    把实例作为唯一出口，这两件事都能做；额外导出包装函数只会鼓励别处"再包一层"
· 为什么这里不配 session_maker：工具各自 async with AsyncSessionLocal() 开短会话，
    FastMCP 不持有数据库连接。⚠️ 实测确认本项目装的 fastmcp 2.14.7 的 __init__ 里
    **根本没有** session_maker 参数（既是不需要，也是这一版没有）

四、★ 第 9 章：挂载的两处改动

· 改动一（lifespan）：
    async with knowledge_mcp.session_manager.run():
        yield
    · mcp session manager 是 streamable HTTP 必需的后台任务组；
      ⚠️ 少了它，任何工具调用都会因 ASGI scope 缺失抛 RuntimeError
    · 必须绑进 lifespan：它负责清理跨请求的超时连接，
      async with 让它与"应用启动 → 关闭"同生命周期
    · yield 从裸的挪进 with 内部 —— 整个服务运行期都在 manager 上下文里

· 改动二（装配）：
    app.mount("/mcp", knowledge_mcp.streamable_http_app(), name="mcp")
    · 为什么 mount 而不是 include_router：mount 挂的是完整 ASGI 子应用（自带路由表与
      生命周期），include_router 挂的是本应用内的路由表；MCP 子应用有自己的路径体系
    · 为什么最终路径是 /mcp：内层已被第 8 节设为 "/"，前缀只由这里的 /mcp 决定
      （两处要一起想，否则会出现 /mcp/mcp 这种"看起来能连、实际 404"）
    · 为什么挂在所有 /api 路由之后：第 1 章定的回归底线 R1 ——
      一眼就能看出"/api 一条没动，只是多挂了一个独立子应用"

五、★★ 两个"只有实测才知道"的细节（都值得留档）

· 细节 1：session_manager 是【懒创建】的
    在 streamable_http_app() 被调用之前访问 session_manager 会抛：
      RuntimeError: Session manager can only be accessed after calling
      streamable_http_app(). The session manager is created lazily ...
    本项目为什么不会踩到（顺序天然正确）：
      import app.main
        → from app.mcp_server import knowledge_mcp      （只导入实例）
        → create_app()
            → knowledge_mcp.streamable_http_app()       ← 这里才创建 session_manager
        → 服务启动 → lifespan 执行
            → knowledge_mcp.session_manager.run()       ← 此时早已就绪

· 细节 2：多次取子应用 = 多个 app，但只有一个 manager
    实测：streamable_http_app() 每次返回**不同的** Starlette 实例
          session_manager 是**同一个**缓存对象
    → 所以"装配处取 app、lifespan 处取 manager"这种分工是安全的，
      不会出现两个 manager 各管一半连接。
    ⚠️ 但这意味着一条隐含约束：若将来 manager 改成不缓存，本节这套写法立刻会崩

七、⚠️ 实测中发现的一处细节：307 重定向

客户端日志每次调用都有一次跳转：
    POST /mcp   → 307 Temporary Redirect
    POST /mcp/  → 200 OK

· 原因：内层子应用挂在 "/"，Starlette 的 mount 对根路径的规范形式是带尾斜杠（/mcp/），
  所以访问 /mcp 会先 307 到 /mcp/
· 影响：客户端（httpx / MCP SDK）会自动跟随，**功能不受影响**
· 要留意：若将来有网关 / 反向代理不跟随重定向，就会看到"连不上"却找不到原因。
  真要避免，可以把内层路径改成 /mcp 并重新算 mount 前缀 ——
  本项目按教程保留现状并在此留档
