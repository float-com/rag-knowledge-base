二、本章要解决的一件事

```
Web 侧的问答链路：创建会话 → 落 user message → 跑 RAG workflow → 边产 token 边推 SSE
                        → 落 assistant message + citations

MCP 侧要的：一次调用、一个结果
```

· 教程给了三条"MCP 调用语义下不合适"的理由，我逐条核过，都成立：
    ① MCP 调用方是外部 Agent，自己管多轮上下文，不该污染我们的 conversations / messages 表
    ② MCP 工具协议是「一次调用、一个结果」，不需要按 token 流式返回
    ③ Web 路径里有大量「写 user message → 等 token → 写 citations」的事务步骤，
       对 MCP 这种无状态调用是负担
· 结论：**复用同一张 RAG 图，不复用 Web 那套事务步骤**

三、为什么不复用现成的 answer_for_evaluation（实测后确认它不能用）

· 项目里现成的非流式入口只有一个：answer_for_evaluation（第 10 章为离线评测写的）
· 它的两个性质对 MCP 是【致命的】：
    · ★ 权限走 WILDCARD_PERMISSION_TAG（等价 admin 视角看全量）
      → 直接给外部 Agent 用，等于绕过第 11 期的权限体系，正好踩中第 1 章 §3.5 的头号风险
    · ★ 异常吞进 error_message 不向上抛
      → MCP 工具调用失败却返回空答案，Agent 会把它讲成"知识库里没有"，这是事故
· 所以教程选择【新写一个入口】，这正是第 1 章 §3.6 那条"待大纲确认"的答案：
  当时问的是"复用现成的非流式入口，还是新写一个？"，答案是新写 —— 于是本章动了 chat_service.py

五、★ 两个新成员的设计取舍

· MCPChatAnswer 为什么不复用 EvaluationAnswer：
    · 两者跑同一张图，但面向的调用方完全不同 ——
      评测模型给"分析报表"用（要 chunks 全量、路由轨迹、归因画像、耗时），
      MCP 模型给"模型"用（只要 answer / refused / citations / trace_id）
    · 一句话：**面向不同消费者，就应该有各自的门面** —— 与第 3 章独立建 schema 同一条思路
    · frozen=True 与 EvaluationAnswer 一致：结果快照不该被下游无意篡改

· ★ 一处自我纠正：异常类不该由我加
    · 教程本章关于异常只有一行注释：
        # 异常 + 直接 raise，由 tool 层翻译成 ToolError 给 Agent
      它定义了【职责】，但没有定义任何异常类
    · 我第一版往 core/exceptions.py 加了一个服务层 ToolError（code=tool_error / 400）。两条删除理由：
        ① 它是"没有调用方的代码"：本章 answer_for_mcp 走"异常一路冒出"，根本不会 raise 它；
           而我自己在第 3 章文档里刚写下"没有调用方的代码 = 未验证的代码"（Day12 的教训），转头就自相矛盾
        ② 教程那句话【不需要】它：except AppException + _user_facing_message 已完整实现"翻译"
    · 翻译点定在未来的工具层（本章不实现）：

            result = await ChatService(session).answer_for_mcp(question, current_user=user)
        except AppException as exc:
            raise MCPToolError(_user_facing_message(exc)) from exc

        mcp.server.fastmcp.exceptions.ToolError   协议层（FastMCP → CallToolResult(isError=True)），

        服务层                                    无对应类，也不该有 —— 服务层只管抛 AppException 子类
      好处：服务层不必知道 MCP 协议的存在
    · 已在正文 §3.2 与本章"刻意没做的事"里留档，避免下次又"顺手补一个"

六、★ 本次写进代码的 8 处步骤/语法注释

· 步骤 1  UUID(int=0) 是占位值不是空值：RAGState 强类型要求 UUID，
          而图里有节点（load_context）会拿它查历史 —— 查不到就退化成"没有上下文"，正是我们要的；
          只要不走落消息/落引用分支，就不会真的写出这条假会话
· 步骤 1  chat_history 为什么强制空：MCP 的多轮由 Agent 自己维护，我们保持无状态，
          既避免上文污染改写/检索，也让同一次调用可重放
· 步骤 2  # type: ignore[arg-type] 的来历：ainvoke() 静态返回 dict[str, Any]，
          而 RAGState 是 TypedDict，update() 期望同类型映射 → mypy 报错；
          与评测路径用的是同一条写法
· 步骤 3  parts: list[str] + join 为什么优于 answer += delta：
          字符串不可变，循环里 += 是 O(n²) 拷贝；列表收集再 join 是一次性分配
· 步骤 4  list(state.get("retrieved_chunks", [])) 的两层防御：
          .get(..., []) 防 KeyError；外层 list(...) 只复制列表容器防校验器增删；
          元素是 frozen dataclass，天然不可变、无需深拷贝
· 步骤 4  校验时机为什么与 Web 不同：校验器需要完整答案，边流边校验会出现
          "前半段已发出、后半段又被判定为幻觉"的尴尬
· 步骤 5  bool(state.get("refused")) 强转：state 里可能是 None，契约声明的是 bool
· 签名处  current_user 用 * 限定为关键字参数：两者都是对象/字符串，
          位置传错不会立刻报错，关键字限定把这类事故挡在调用处

九、★★ Mermaid 出图规范（本次配图三轮返工换来的，后续所有图一律照此执行）

【本次踩的三个坑，按发生顺序】

· 坑 1（第 1 版）：节点标签里用【裸换行】代替 <br/>
  → Mermaid 把每一行当作新语句：refused = bool(...) 那一行生成了一个叫 refused 的孤儿节点，
    true / false（Mermaid 关键字）也被当节点；图右上角凭空多出一簇空壳方块

· 坑 2（第 2 版）：节点标签里出现【未加引号的半角括号】
  → Mermaid 的 ( 是"形状定界符"（ID(文本) 表示圆角矩形），解析器在 ( 处截断，
    剩余片段变成新语句：_serialize_citation(c, ordinal=i) 生成了名叫 c. ordinal=i 的孤儿节点

· 坑 3（第 3 版）：标签里【HTML 标签 + 行尾符号】组合，导出后文字被切
  → 被切的每一行都断在行尾的 [ ( ' = , 上：
    state['answer' ← 少了收尾的 '；chat_history = [ ← 少了 ]
    这不是排版折行，是裁剪位置算偏；去掉行尾符号后即恢复

【定稿后接下来写图一律遵守的 5 条硬规矩】

· 规矩 1  节点标签只用一种 HTML 标签：<b>。不再用 <i>；换行只用 <br/>
· 规矩 2  任何一行都不以 [ ( ' = , 结尾；方括号用文字表达（retrieved_chunks 而非 list[...]），
          参数序列用「与」或 · 连接
· 规矩 3  每行不超过约 26 个字符，中英混排尤其要短
· 规矩 4  节点定义与连线分两段写：前半段只定义节点，后半段只连边
          —— 即使某行被误解析，也不会长进节点文字里
· 规矩 5  init 一律加 useMaxWidth: true 与 padding: 12，宁可整体缩小，也不让边缘被切

【出图后的 5 秒自检】

· 在源码里搜 (c, / (). / verify( 三种形态：只要它们不在行首、也不在引号内，就是下一个孤儿节点
· 数一遍节点数：应等于 <b> 出现的次数；多出来的就是裸换行或裸括号产生的空壳
· 看最长的一行：超过 26 字符就必须拆行
