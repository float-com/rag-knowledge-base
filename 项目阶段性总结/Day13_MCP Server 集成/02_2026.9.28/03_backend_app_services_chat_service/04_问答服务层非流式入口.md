## 二、★ 为什么必须新写一个入口，而不复用现成的两个

### 2.1 Web 侧的链路长什么样（为什么不适合 MCP）

```
创建会话 → 落 user message → 跑 RAG workflow → 边产 token 边推 SSE
    → 落 assistant message + citations
```

这套逻辑搬到 MCP 调用语义下有三处不合适：

| # | 不合适的地方 | 说明 |
| --- | --- | --- |
| 1 | **会污染历史表** | MCP 调用方是外部 Agent，它自己管多轮上下文，不该在 `conversations` / `messages` 里留下一堆没人看的会话 |
| 2 | **协议形状不匹配** | MCP 工具协议是「一次调用、一个结果」，不需要也不应该按 token 流式返回 |
| 3 | **无谓的事务负担** | Web 路径有大量「写 user message → 等 LLM → 写 citations」的事务步骤，对 MCP 这种无状态调用纯属负担 |

### 2.2 项目里现成的非流式入口为什么也不能直接用

实测 `chat_service.py` 里的两个入口：

```
async def stream_answer(...)               → SSE 流式，产出事件序列，不是返回值
async def answer_for_evaluation(question)  → 非流式，返回 EvaluationAnswer
```

`answer_for_evaluation` 是第 10 期为**离线评测**写的，它的两个性质对 MCP 反而是问题：

| 性质 | 对 MCP 是好事还是坏事 |
| --- | --- |
| 面向"单轮、无会话历史" | ✅ 正好符合工具调用 |
| 返回结构化结果 | ✅ 正好符合 MCP 需要返回结构化数据 |
| 权限走 `WILDCARD_PERMISSION_TAG`（等于 admin 视角看全量） | ❌ **绝不能给外部 Agent**：那等于绕过第 11 期的权限体系 |
| 异常吞进 `error_message` 不抛出 | ❌ **绝不能给外部 Agent**：返回空答案会被模型讲成"知识库里没有" |

**→ 结论：复用图，不复用入口。** 这正是第 1 章 §3.6 那条补丁的落地。

> ⚠️ 这里有一条与第 1 章 §3.6"🔴 待大纲确认"的呼应：当时的问题是
> "教程是复用某个现成的非流式入口，还是新写一个？"
> 教程的答案是**新写一个** —— 所以本章动了 `chat_service.py`（第 12 期刚改过的文件）。

## 三、★ 两个新成员，与既有成员的关系

### 3.1 `MCPChatAnswer`（dataclass，与 `EvaluationAnswer` 放一起）

```python
@dataclass(frozen=True)
class MCPChatAnswer:
    """MCP `ask_knowledge_base` 工具的非流式问答结果。

    与评测路径不同的是：MCP 调用方是真实用户（持 JWT），需要按其权限标签过滤检索结果；
    与 stream_answer 不同的是：不创建 conversation、不写 user / assistant 消息，
    外部 Agent 自己管多轮上下文。
    """

    answer: str
    refused: bool
    citations: list[dict]
    trace_id: str | None
```

**为什么不复用 `EvaluationAnswer`**：两者都跑同一张图，但面向的调用方完全不同 ——

| | `EvaluationAnswer`（第 10 章） | `MCPChatAnswer`（本章） |
| --- | --- | --- |
| 面向谁 | 离线评测跑批 | 外部 Agent 的一次工具调用 |
| 字段 | 要 chunks 全量、路由轨迹、归因画像、耗时 | 只要答案 + 拒答标志 + 引用 + trace |
| 异常策略 | 不许抛出（防止批次熔断） | 必须抛出（工具失败要能看见） |

一句话：**评测模型的字段是给"分析报表"用的，MCP 模型的字段是给"模型"用的。**
这与第 3 章独立建 schema 是同一条思路。

`frozen=True` 与 `EvaluationAnswer` 一致：结果快照不该被下游无意篡改。

### 3.2 ★ 本章只新增了一个成员：**没有**新增异常类（一处自我纠正）

教程在这一章只写了一行注释：

```python
# 异常 + 直接 raise，由 tool 层翻译成 ToolError 给 Agent
```

它**定义了职责（异常冒出来 → 工具层翻译），但没有定义任何异常类**。
我在第一版实现里自作主张往 `app/core/exceptions.py` 加了一个服务层的 `ToolError`，
**后来删掉了**，理由有两条：

| # | 理由 |
| --- | --- |
| 1 | **它是"没有调用方的代码"**。本章 `answer_for_mcp` 走的是"异常一路冒出"，根本不会 `raise` 它；而第 3 章文档里刚写下"没有调用方的代码 = 未验证的代码"（Day12 的教训），转头加一个没人用的类属于自相矛盾 |
| 2 | **教程那句话不需要它**。`except AppException` + `_user_facing_message` 已经完整实现了"翻译"—— 在**工具层**捕获现有基类即可，不必新造类 |

于是翻译点明确落在工具层（各工具实现时）：

```python
# app/mcp_server/tools/*.py 未来的写法（本章不实现）
try:
    result = await ChatService(session).answer_for_mcp(question, current_user=user)
except AppException as exc:                     # ← 直接复用现有基类，不新增异常类型
    raise MCPToolError(_user_facing_message(exc)) from exc   # ← 协议层的 ToolError
```

> ⚠️ **两个 `ToolError` 不是同一层的东西**，但只有后者存在：
> - `mcp.server.fastmcp.exceptions.ToolError` 是**协议层**的（FastMCP 负责转成 `CallToolResult(isError=True)`），第 2 章的 `auth.py` 直接 `raise` 的就是它；
> - 服务层**不需要**也有**没有**对应的类 —— 服务层只管抛自己的 `AppException` 子类，
>   由工具层用 `_user_facing_message` 取出中文 message 再包成协议层的 `ToolError`。
>
> 这条界线的好处是：**服务层不必知道 MCP 协议的存在**。

## 四、`answer_for_mcp` 代码逐段讲解

```python
@traceable(name="ChatService.answer_for_mcp", run_type="chain")
async def answer_for_mcp(self, question: str, *, current_user: User) -> MCPChatAnswer:
```

`current_user` 用 `*` 限定为**关键字参数**：调用处必须写
`answer_for_mcp(question, current_user=user)`，避免"把用户和问题位置搞反"这类事故
（两者都是对象/字符串，位置传错不会立刻报错）。

### 4.1 步骤 1：取权限标签与 trace，装配图状态

```python
permissions = compute_user_permission_tags(current_user)
trace_id = get_current_trace_id()

state: RAGState = {
    "conversation_id": UUID(int=0),
    "question": question,
    "chat_history": [],
    "permissions": permissions,
    "trace_id": trace_id,
}
```

| 字段 | 为什么这么填 |
| --- | --- |
| `conversation_id: UUID(int=0)` | RAGState 强类型要求必须是 UUID、不能传 None；MCP 不落会话，用全 0 占位。图里有节点（`load_context`）会拿它去查历史 —— 查不到就退化成"没有上下文"，正是我们要的 |
| `chat_history: []` | **强制置空**：MCP 的"多轮"由 Agent 自己维护（它可以把上文并进 question），我们保持无状态，既避免上文污染改写/检索，也让同一次调用可重放 |
| `permissions` | ★ **本方法唯一的权限来源**，与网页侧同一函数、同一口径。第 1 章 §3.5 的头号风险就压在这一行 |

> ⚠️ 与评测路径对照：那里写的是 `"permissions": [WILDCARD_PERMISSION_TAG]`（看全量），
> 这里写的是真实用户的标签。**这一行就是"评测视角"与"真实用户视角"的分水岭。**

### 4.2 步骤 2：驱动 RAG 图

```python
final_state = await get_rag_graph().ainvoke(state)
state.update(final_state)  # type: ignore[arg-type]
```

`# type: ignore[arg-type]` 不是随手加的：`ainvoke()` 的静态返回类型是 `dict[str, Any]`，
而 `RAGState` 是 TypedDict，`update()` 期望同类型映射 → mypy 报 `arg-type`。
这是 LangGraph 的既有类型缝隙，评测路径用的是同一条写法。

### 4.3 步骤 3：生成答案（拒答快速通道 / 流式聚合）

```python
if state.get("refused"):
    answer = state["answer"]                    # 前置拒答：复用规划节点写好的文案
else:
    parts: list[str] = []
    async for delta in stream_generate(state):  # 逐个 yield 文本增量
        parts.append(delta)
    answer = "".join(parts)
    state["answer"] = answer
```

**为什么用列表缓冲再 join，而不是 `answer += delta`**：
字符串不可变，循环里 `+=` 会反复申请新对象（O(n²) 拷贝）；收集到列表再 join 是一次性分配，
长回答下差距明显。

**为什么这里可以把流"聚合掉"**：Web 侧要逐字下发所以不能缓冲，评测侧要完整文本所以必须缓冲 ——
MCP 属于后者，多花一次 join 换来的是"一次调用一个结果"的协议语义。

### 4.4 步骤 4：后置事实校验

```python
if settings.verify_answer_enabled:
    verify_result = await get_answer_verifier().verify(
        question,
        answer,
        chunks=list(state.get("retrieved_chunks", [])),
    )
    if not verify_result.verified:
        answer = REFUSAL_ANSWER
        state["answer"] = answer
        state["refused"] = True
```

三个要点：

| 要点 | 说明 |
| --- | --- |
| `list(state.get(..., []))` 的两层防御 | `.get(..., [])` 防 KeyError；外层 `list(...)` 只复制**列表容器**，防校验器增删影响 state。元素仍是同一批 `RetrievedChunk` 引用 —— 它是 frozen dataclass，天然不可变，无需深拷贝 |
| **校验时机与 Web 不同** | 这里是"聚合完之后"一次性校验，**不是**边流边校验：校验器需要完整答案才能判断事实是否被支撑；边流边校验会出现"前半段已发出、后半段又被判定为幻觉"的尴尬 |
| 三件事与 Web 完全对齐 | 换文案 `REFUSAL_ANSWER` → 回写 `state["answer"]` → 置 `state["refused"] = True` |

### 4.5 步骤 5：装配返回值

```python
refused = bool(state.get("refused"))

citations = (
    []
    if refused
    else [
        _serialize_citation(c, ordinal=i)
        for i, c in enumerate(state.get("retrieved_chunks", []), 1)
    ]
)

return MCPChatAnswer(answer=answer, refused=refused, citations=citations, trace_id=trace_id)
```

- `bool(...)` 归一化：state 里这个键可能是 `None`，而契约声明的是 `bool`
- `enumerate(..., 1)`：角标从 1 开始，与 prompt 里的「片段 N」严格一致 ——
  这个 `ordinal` 会一路带到第 3 章 `MCPCitation.ordinal`
- **拒答时清空引用**：避免"拒绝回答却附了参考资料"的自相矛盾
- ★ **复用 `_serialize_citation`**（第 8 期就在用的序列化函数），所以 citations 的形状与 SSE 链路
  逐字段一致 —— Agent 侧看到的引用结构与网页侧同源，不需要第二套序列化逻辑

### 4.6 ★ 步骤 5b：异常策略（与评测路径最关键的差异）

```python
# 本方法【没有】except Exception
```

| 路径 | 异常策略 | 为什么 |
| --- | --- | --- |
| `answer_for_evaluation` | `except Exception` → 塞进 `error_message` 返回 | 一个 case 崩溃不能熔断整批评测 |
| `answer_for_mcp` | **不捕获，一路冒出** | 工具调用失败却返回空答案，Agent 会把它当成"知识库里没有"讲给用户 —— 这是事故 |

冒出的异常由工具层兜成协议层的 `ToolError`（第 2 章的错误出口链），
Agent 能看到明确的失败原因。

## 五、与两条既有链路的完整对照

| 维度 | `stream_answer`（Web） | `answer_for_evaluation`（评测） | `answer_for_mcp`（本章） |
| --- | --- | --- | --- |
| 返回值 | SSE 事件序列 | `EvaluationAnswer` | `MCPChatAnswer` |
| 建会话 / 写消息 | ✅ 都做 | ❌ 都不做 | ❌ 都不做 |

| 引用序列化 | `_serialize_citation` | 同左（存进 chunks） | `_serialize_citation`（同一函数） |

## 七、⚠️ 本次刻意没做的事（留档，避免下次误以为漏了）

| 没做的事 | 原因 |
| --- | --- |
| **没接语义缓存** | 教程本章的实现范围内没有缓存接入。**但要注意第 1 章 §7.2 的预警仍然成立**：一旦后续接入，缓存命中会跳过整张图，`trace_id` 会是空的 → 第 3 章的 `MCPAnswer.trace_id` 已经按"可空"设计，形状不会因此变 |

| **没有新增任何异常类** | ★ 见 §3.2：教程只定义职责（"异常直接 raise，由 tool 层翻译成 ToolError"），没定义类。翻译点落在未来的工具层：`except AppException` + `_user_facing_message`。我第一版加过一个服务层 `ToolError`，已删 —— 它当时没有调用方，属"未验证的代码" |
| **`chat_service.py` 里没有 import 任何 ToolError** | 本章方法走"异常一路冒出"，翻译在工具层做；服务层连协议层异常的名字都不该出现 |

## 八、排错速查表

| 现象 | 最可能的原因 | 先查哪里 |
| --- | --- | --- |
| 普通用户通过 MCP 看到了无权限文档 | `permissions` 被写成了通配（复制了评测路径的写法） | 步骤 1 的那一行 `compute_user_permission_tags(current_user)` |
| Agent 收到空答案却说"知识库里没有" | 异常被吞掉了（照抄了评测路径的 `except`） | 本方法应**没有** `except Exception` |
| 多轮提问互相污染 | `chat_history` 被透传了 | 步骤 1 的 `"chat_history": []` |
| 引用角标与回答里的 `[N]` 对不上 | `enumerate` 起始值不是 1 | 步骤 5 的 `enumerate(..., 1)` |
| 拒答了却带着引用 | 拒答分支没清空 citations | 步骤 5 的 `[] if refused else [...]` |
| `MyPy` 报 `arg-type` | `state.update(final_state)` 少了 `# type: ignore[arg-type]` | 步骤 2 |
| 调用处报参数错误 | `current_user` 是关键字限定参数 | 必须写 `current_user=` |
| 想让服务层抛"工具异常" | 服务层不该知道 MCP 协议 | 翻译在工具层做，见 §3.2 |

### 9.2 ★ 为什么返工了三轮（每个坑都值得记住）

| 版本 | 现象 | 真正的原因 |
| --- | --- | --- |
| 第 1 版 | 渲染图右上角凭空多出一簇空壳方块（`refused` / `true` / `false` / `否`） | 节点标签里用了**裸换行**代替 `<br/>`：Mermaid 把每一行当作新语句，`refused = bool(...)` 那一行就生成了一个叫 `refused` 的孤儿节点；`true` / `false` 是 Mermaid 关键字，也被当节点 |
| 第 2 版 | 又冒出一个叫 `c. ordinal=i` 的孤儿节点 | 标签里出现**未加引号的半角括号**：`_serialize_citation(c, ordinal=i)` —— Mermaid 的 `(` 是形状定界符（`ID(文本)` 表示圆角矩形），解析器在 `(` 处截断，剩余片段变成新语句 |
| 第 3 版 | 图能画对，但导出后文字被切：`state['answer'` 少了收尾的 `'`、`chat_history = [` 少了 `]` | 标签里是 **HTML 标签 + 行尾符号** 的组合：被切的每一行都断在行尾的 `[` `(` `'` `=` `,` 上。这不是排版折行，是**裁剪位置算偏** |

> ⚠️ 第 1、2 版的坑**肉眼在源码里看不出来**（语法都不报错），只有在渲染结果里才会暴露；
> 第 3 版更隐蔽 —— 图结构完全正确，纯粹是导出时被切。

### 9.3 硬规矩（后续所有 Mermaid 图一律遵守）

```
规矩 1  节点标签只用一种 HTML 标签：<b>
        不再用 <i>；换行只用 <br/>，绝不用源码里的裸换行
规矩 2  任何一行都不以 [ ( ' = , 结尾
        方括号改用文字表达（写 retrieved_chunks，不写 list[...]）
        参数序列用「与」或 · 连接（写 question 与 answer，不写 question, answer）
规矩 3  每行不超过约 26 个字符；中英混排尤其要短
规矩 4  节点定义与连线分两段写：前半段只定义节点，后半段只连边
        —— 即使某行被误解析，也不会长进节点文字里
规矩 5  init 一律加 useMaxWidth: true 与 padding: 12
        宁可整体缩小，也不让边缘被切
```

### 9.4 出图后的 5 秒自检

```
① 搜 (c, / (). / verify( 三种形态：不在行首、也不在引号内的，就是下一个孤儿节点
② 数节点数：应等于 <b> 出现次数；多出来的就是裸换行或裸括号产生的空壳
③ 看最长的一行：超过 26 字符就拆行
④ 看每行行尾：出现 [ ( ' = , 就改掉
```
