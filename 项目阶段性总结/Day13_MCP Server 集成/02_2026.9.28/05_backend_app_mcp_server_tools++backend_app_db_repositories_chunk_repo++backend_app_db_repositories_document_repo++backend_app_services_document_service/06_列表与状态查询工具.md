## 二、★ `_viewer_tags`：全模块唯一的权限来源

```python
def _viewer_tags(user: User) -> list[str] | None:
    """admin → None；普通用户 → 合并后的有效标签。与 REST 同口径。"""
    return None if is_admin(user) else compute_user_permission_tags(user)
```

| 设计点 | 说明 |
| --- | --- |
| admin 传 **None** 而不是 `["*"]` | 服务层约定 `None = 不做权限过滤`。`["*"]` 语义上也等于全可见，但它要多走一遍"数组重叠"的 SQL 运算 —— 既然 admin 本来就不需要过滤，传 None 让 SQL 少一个条件 |
| **必须与 REST 侧同口径** | 网页侧路由也是这么算的（admin → None）。★ 一旦 MCP 侧自己判一套可见范围，就会出现"网页看不到、Agent 却能看到"的双口径漏洞 —— 第 1 章 §3.5 的头号风险 |
| 在**调用服务时现算**，不在认人时算 | 让"权限"与"这次查询"贴在一起，一眼能看出这次是否按权限过滤了 |

> 注意 `permission_tags` 与 `_viewer_tags` 的**语义分界**：
> 工具 2（上传）的入参 `permission_tags` 是"**我要给这份文档挂什么标签**"（写），
> 而 `_viewer_tags(user)` 是"**我能看到哪些标签**"（读）。两者恰好同名，别搞混。

## 三、工具 3：`list_documents` 逐段讲解

```python
@mcp.tool(name="list_documents", title="列出文档",
          description="按更新时间倒序分页列出当前用户可见的文档。")
async def list_documents(
    ctx: Context,
    page: int = 1,
    page_size: int = 20,
    status: DocumentStatusValue | None = None,
) -> MCPDocumentList:
    user = await resolve_current_user(ctx)                    # 步骤 1：认人

    if page < 1:                                              # 步骤 2：挡参数
        raise ToolError("page 必须 >= 1")
    if page_size < 1 or page_size > 100:
        raise ToolError("page_size 必须在 1-100 之间")

    async with AsyncSessionLocal() as session:                # 步骤 3：调服务
        service = DocumentService(session)
        try:
            items, total = await service.list_documents(
                page, page_size,
                status=DocumentStatus(status) if status else None,
                permission_tags=_viewer_tags(user),
            )
        except Exception as exc:
            raise _to_tool_error(exc, default="文档列表查询失败") from exc

    return MCPDocumentList(                                   # 步骤 4：出参翻译
        items=[MCPDocumentItem.model_validate(d) for d in items],
        total=total, page=page, page_size=page_size,
    )
```

### 3.1 为什么服务层有校验、这里还要再挡一次

MCP 的参数由**外部 Agent**填，模型很容易给出 `page=0` 或 `page_size=1000`。
若只依赖服务层兜底，Agent 拿到的会是一句模糊的失败原因；
在最外层给出**明确的边界提示**（"page 必须 >= 1"），模型才知道该怎么改参数重试。

### 3.2 `status` 为什么要 `DocumentStatus(status)` 显式转一次

```
MCP 参数：DocumentStatusValue（Literal 的五个字符串取值，供 Agent 填）
服务层要：DocumentStatus 枚举成员（见 list_documents 的签名）
```

这不是多余的一次转换，而是"契约层与服务层各自合理"的**真实例子**：
契约层要对模型友好（能填的取值写进 JSON Schema），服务层要对类型严格（枚举）。

### 3.3 ★ 为什么这里用 `model_validate`，而工具 1/2 用显式构造

```
MCPDocumentItem 声明了 model_config = ConfigDict(from_attributes=True)   ← 第 3 章
且它的字段集合与 ORM Document 刻意对齐（id/name/status/mime_type/size/
version/permission_tags/created_at/updated_at），没有内部字段需要拦
→ 可以直接 model_validate(orm_obj)

工具 1 的 MCPCitation、工具 2 的 MCPUploadResult 没开 from_attributes
→ 必须显式逐字段构造（顺带完成白名单脱敏）
```

**所以两条路径的差别不是"随意"**，而是取决于模型是否开了 `from_attributes`。
这也是第 3 章那句"本模块只有 `MCPDocumentItem` 需要它"在代码里的兑现。

## 四、工具 4：`get_document_status` 逐段讲解

```python
async def get_document_status(document_id: str, ctx: Context) -> MCPDocumentStatus:
    user = await resolve_current_user(ctx)                     # 步骤 1：认人
    document_uuid = _parse_uuid(document_id, field="document_id")   # 步骤 2：解析 id

    async with AsyncSessionLocal() as session:
        service = DocumentService(session)
        try:
            document = await service.get(document_uuid,
                                         permission_tags=_viewer_tags(user))  # 步骤 3
            latest = await service.get_latest_task(document.id)               # 步骤 4
        except Exception as exc:
            raise _to_tool_error(exc, default="文档状态查询失败") from exc

    return MCPDocumentStatus(...)                              # 步骤 5：出参翻译
```

### 4.1 ★ 为什么 `document_id` 声明成 `str` 而不是 `UUID`

```
MCP 的 JSON 里它就是字符串。
若声明成 UUID，格式不合法会变成【协议层的参数校验错误】——
模型看到的是一段 schema 报错；
而声明成 str 再由 _parse_uuid 显式解析，就能给出
"document_id 不是合法的 UUID" 这句可操作的话，模型立刻知道要重新取一个 id。
```

### 4.2 权限过滤也作用在"单文档查询"上

`service.get(..., permission_tags=...)` 在无权时抛 `NotFoundError` ——
**与网页侧口径一致：不区分"不存在"与"无权"**，避免向外泄露"这份文档存在"。

### 4.3 `latest` 可以为 None，所以六个 `latest_task_*` 全部可空

文档可能从未入过库（刚上传、任务还没落库），也可能任务早已被清理。
这在第 3 章设计 schema 时就按"可空"处理了，这里只是如实传递。

### 4.4 三个"翻译小函数"的分工

| 函数 | 转换 | 为什么需要 |
| --- | --- | --- |
| `_status_value` | `str → DocumentStatusValue` | ORM 上是**普通字符串列**，可能带尾随空格 → 只 `strip()`，不兜底 |
| `_task_type_value` | `str → Literal["ingest","reindex"]` | 任务类型在 ORM 上是 **Enum** → 直接 `.value`，不需要 strip |
| `_task_status_value` | `str → IngestionTaskStatusValue` | 同上，`.value` |

**三者共同的原则：只做类型收敛，不做业务兜底。**
库里若出现契约未声明的取值，正确行为是让 Pydantic 校验失败并报出来 ——
静默改成某个合法值（尤其改成 `"ready"`）会让 Agent 误以为文档可检索。

> ⚠️ `_status_value` 与另两个的差别是刻意的：
> 文档状态来自普通字符串列（所以要 `strip()`），任务状态来自 Enum（所以不用）。

> ⚠️ **`count_chunks` 的落点我改过一次，值得记下来**：
> 我第一版把它放在 `DocumentChunkRepository`（理由：切片数天然属于切片仓储，
> 而且那里已有一个 `get_stats(document_id)` 怕混淆粒度）；

### 5.3 ★ `_permission_where` 为什么只是转发一层

教程第 7 节里统计 SQL 用的是 `_permission_where(permission_tags)`。
本项目**已有** `build_permission_filter`（`document_repo` 模块级），所以：

```
_permission_where(...)  = 一行转发 → build_permission_filter(...)
```

**它不是第二份权限实现。** 真正的口径（标签重叠 OR 空标签即公开、通配短路）
仍然全项目只有 `build_permission_filter` 一处定义。
（`chunk_repo` 里我一度也留了一个同名转发，但那边的统计方法按教程挪走后
它就没有调用方了，已一并撤掉 —— 不留无人使用的私有函数。）

### 5.4 三个方法的关键取舍

**`count`：为什么不复用 `list_paginated`**

`list_paginated` 会连带把当前页的 ORM 实体全查出来，而概览只关心一个数字 ——
为了 count 去加载整页文档，在知识库变大之后是纯浪费。
（套一层 `int(...)` 的理由与 `UserRepository.count_all` 相同：`func.count()` 的静态
返回类型是宽泛的 `int | None`。）

**`count_chunks`：为什么必须 join documents，还要带 `status == "ready"`**

```
权限标签挂在【父文档】上（切片没有自己的标签），不 join 就拼不出权限条件；
status == "ready" 是"可被检索"的守卫，与 vector_search / keyword_search
的第一条 WHERE 完全一致。
```

少了 `ready` 守卫，概览会把正在解析、甚至解析失败的文档切片也算进"知识库规模"，
Agent 据此判断"值不值得检索"就会失真。

**`get_last_indexed_at`：为什么用 `updated_at` 不用 `created_at`、也不 join `ingestion_tasks`**

```
updated_at   文档转入 ready 且 reindex 成功后会被刷新 → 正是"入库完成"的落点
created_at   只反映"上传时间"，两者差着整条解析/切分/向量化流水线
ingestion_tasks.finished_at
             会引入"任务被清理后时间就丢了"的依赖；用文档自身状态时间更稳，
             也与第 3 章该字段的 description（"最近一次进入 ready 状态的文档时间"）一致
```

**为什么用 `max(updated_at)` 而不是 `order_by + limit 1`**：两者都能拿到结果，
但聚合写法少一次排序开销，语义也更直白。注意这里是标量聚合而非 count，
所以用 `scalar_one_or_none()` —— 没有任何行时 `max()` 返回 NULL，得到 `None` 而不是 0。

### 5.5 `get_stats` 为什么放在 Service，以及为什么返回 dataclass

第 1 章定的纪律：**MCP 工具层只做协议转换，不碰数据访问。**
三个 count/max 查询属于"业务口径"（哪些文档算可见、ready 才算可检索），
放 Service 才能与网页侧将来可能的复用共享同一口径。

**三项共用同一个 `permission_tags` 入参**，这也是把它们收进**同一个方法**的理由 ——
拆开调用就有漏传一个的风险，而"泄露一个数字"同样属于越权。

**返回 `KnowledgeBaseStats`（`@dataclass(frozen=True)`）而不是 dict**：

| | dict | dataclass（采用） |
| --- | --- | --- |
| 键名拼错 | 只能等运行时 `KeyError` | **调用处**就能被静态检查抓到 |
| 契约 | 靠约定 | 与第 3 章 `MCPStats` 强类型对齐 |
| 可变性 | 可被下游改写 | `frozen=True` 冻结，与既有 `ChunkStats` 同手法 |

**调度关系**（注意两个仓储都会用到）：

```
document_count  → DocumentRepository.count              （documents 表）
chunk_count     → DocumentChunkRepository.count_chunks   （chunks join documents）
last_indexed_at → DocumentRepository.get_last_indexed_at （documents 表，max(updated_at)）
```

> ⚠️ 一处必须说明的**命名偏离**：教程把这三个方法（含 chunk 那个）都写在
> `document_repo.py` 里，且 chunk 计数也叫 `count`。本项目**没有照抄**，原因是
> `chunk_repo` 里已经有一个 `get_stats(document_id)`（单文档切片统计，Day3 就在用），
> 再放一个 `count` 会让"统计"这个词在同一文件里指向两种粒度；
> 而"切片数天然属于切片仓储"。所以 chunk 的计数落在 `chunk_repo.count_chunks`，
> service 里表现为 `self.repo.count` 与 `self.chunk_repo.count_chunks` 两处调用。
> **行为与权限口径与教程完全一致，只是落点不同。**

### 6.2 ★ SQL 可编译性验证（新增的两条聚合查询未跑真库，至少确认 SQL 合法）

用 PostgreSQL 方言把新方法的拼装逻辑编译出来看：

```
permission=None / ['*']（通配即不过滤，两条等价）
  count               SELECT count(*) AS count_1 FROM documents
  get_last_indexed_at SELECT max(documents.updated_at) FROM documents
                          WHERE documents.status = %(status_1)s
  count_chunks        SELECT count(*) FROM document_chunks
                          JOIN documents ON documents.id = document_chunks.document_id
                          WHERE documents.status = %(status_1)s

permission=['public']（普通用户：权限条件正确拼上）
  count               ... FROM documents
                          WHERE (documents.permission_tags && %(permission_tags_1)s::VARCHAR[])
                             OR documents.permission_tags = %(permission_tags_1)s::VARCHAR[]
  get_last_indexed_at ... WHERE documents.status = %s
                          AND ((documents.permission_tags && ...) OR ...)
  count_chunks        ... JOIN documents ... WHERE documents.status = %s
                          AND ((documents.permission_tags && ...) OR ...)
```

> ⚠️ 两个要点：
> ① `count(['*'])` 与 `count(None)` 编译结果**完全相同、都没有 WHERE** —— 这是对的：
>    `build_permission_filter` 对通配标签返回 None（等价于"不过滤"），
>    与 `_viewer_tags` 给 admin 传 None 是同一条路径的两种入口。
> ② `get_last_indexed_at` 编译出来是**只查 documents 表**（无 join）——
>    这是按教程第 7 节校正后的形状：最近入库时间属于"文档"属性，
>    第一版我把它挂在 chunk_repo 上、走了 join，改对了。

必须靠"实际调用/属性核对"这一步。
