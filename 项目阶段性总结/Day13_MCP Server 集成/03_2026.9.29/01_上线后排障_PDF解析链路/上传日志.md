二、结论（先说结论）

```
功能层面：没发现代码 bug —— 3 类问题分别是【系统依赖缺失】【资源预算超支】【缺少兜底与自愈】
体验层面：修完不是"能用了"，而是"快了一个数量级"（第二次解析 5 秒，模型常驻内存免冷启动）
```

· 六个坑的归类：
    依赖缺失   libGL.so.1（docling → opencv-python 非 headless 版需要系统图形库）
    资源超支   一个解析任务拖死整机；API 进程白背 561 MB 推理栈
    兜底缺失   Docling 超时【不抛异常】而是静默返回残缺结果；硬重启后僵尸任务无自愈
    配置模板   EMBEDDING_BATCH_SIZE=16 撞上百炼 text-embedding-v3 上限 10

三、★ 本次最有价值的一条：API 进程白背一整套推理栈

· 导入链（问题的根源）：
    document_service → ingestion.tasks（只为拿 .delay() 投递）
                     → ingestion.pipeline → parser → docling/torch/transformers
· tasks.py 顶层导入 pipeline 的旧理由只回答了「会不会循环导入」，
  漏掉了「会不会把无关进程一起拖下水」——FastAPI 根本不需要解析文档的能力
· 本机 A/B 实测（同一进程内）：
    只导入 app.main + app.ingestion.tasks     253.4 MB   重型模块：无
    再导入 app.ingestion.pipeline（旧行为）   485.6 MB   docling/torch/transformers
· 线上效果：uvicorn 844 MB → 283 MB（−561 MB）
· 改法：把 pipeline 导入从模块顶层下沉到两个任务函数体内；任务注册不受影响
· 一句话教训：**模块级 import 是一次全局广播**，判断该不该放顶层，
  除了"有没有循环依赖"，还要问"谁会顺路被拖累"

五、实测数据（本机基准，2 页纯文字 PDF）

| 配置 | 耗时 | 峰值内存 |
| --- | --- | --- |
| 默认（OCR + 表格识别开） | 31.1 s | 1087.5 MB |
| 精简（两项关） | 24.1 s | 828.4 MB（解析结果【完全一致】） |
| 超时拦截验证 | 17.1 s 中断 | 498.9 MB → 正确抛出 DocumentParseError |

· 注意：24% 是"文字型 PDF"的差距；扫描件要逐页跑 OCR，差距会大得多
· 另一个实测：解析成本 ≈ 3.5 秒/页 + 约 17 秒模型冷启动 → 这决定了超时阈值该设多少（300 秒）

七、遗留问题（诚实清单）

· P1 僵尸任务自愈：目前强杀/强重启后 documents=parsing、ingestion_tasks=running 会永久卡住，
     只能手工 SQL 清理（本次已踩两次）→ 应加"启动时/定时收敛超时任务"
· P1 deploy.sh 自检：把今天的坑变成部署前检查（libGL、可用内存、BATCH_SIZE>10、超时是否设置）
· P2 扫描件型 PDF：当前关 OCR，图片型 PDF 会解析为空；方案是本地转 Markdown 再上传 .md
· P2 解析资源上限：目前靠 Nice + 低并发软限流，可补 systemd MemoryMax
· P2 uv lock --torch-backend cpu：服务器 lock 仍锁着 CUDA 版 torch，uv sync 会拉 3 GB 无用包
· P3 HTTPS：宝塔面板 SSL 一键申请
