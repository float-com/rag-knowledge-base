三、教程给的方案要点（5 条，已完整归档）

· 1 MCP 是什么：Server 暴露能力、Client 调用能力、三类原语（Tools / Resources / Prompts），本期只用 Tools
· 2 为什么不让外部 Agent 直接调 RESTful：契约要靠文档传递 Agent 无法自动感知；每家 Agent 定义不一致；
     MCP 把契约做成了协议本身，客户端连上就能自动获取工具列表与参数说明
· 3 传输方式选 Streamable HTTP：stdio 只适合跟着客户端起停的本地工具；SSE 已被官方标记 legacy；
     Streamable HTTP 一次普通请求即可完成调用，且方便复用网关 / 反代 / 鉴权基建
     落点是 FastMCP 的 streamable_http_app() 拿到 ASGI 子应用，直接 app.mount("/mcp", …) 挂到现有 FastAPI
· 4 整体架构：六段链路（外部 Agent → FastAPI mcp 子挂载 → FastMCP 5 个 tool →
     mcp_server/auth.py → app/services 与 app/workflows → PostgreSQL + pgvector 权限过滤）
· 5 Schema 独立设计的取舍：MCP schema 直接展示给外部 Agent，不能随 ORM 变动联动，
     所以单独建 app/mcp_server/schemas.py，只保留 Agent 真正需要的字段

四、★ 我补的三条补丁（教程未展开）

· 补丁一：工具必须带权限标签过滤（对应教程架构图最后一格的「权限标签过滤」）
  · 教程画了这一格但没展开，而它是本期【头号风险】
  · MCP 客户端拿到的 token 属于某个具体用户 → 工具返回的数据必须按这个用户的可见范围过滤
  · 否则外部 Agent 会成为绕过第 11 期权限体系的一条捷径：用户在 Cursor 里问一句，
    就能看到他在网页上看不到的东西
  · 做法必须与网页侧口径完全一致：复用 permission_service，只传参不判权，不另造一套可见范围
  · 这条与第 12 期「缓存 schema 必须带 permission_tags」完全同构 ——
    每加一条新的读取路径，都要重新确认权限过滤还在

· 补丁二：问答类工具不能用现成的 SSE 流式入口（实测才发现）
  · MCP 工具的返回是【一个值】，而本项目问答主入口是流式的：
      chat_service.stream_answer(...)       → SSE 流式，产出事件序列
      chat_service.answer_for_evaluation(…) → 非流式，返回 EvaluationAnswer
  · 所以如果工具里有「向知识库提问」，它不可能直接包 stream_answer
  · 现成的非流式入口只有一个 answer_for_evaluation，但它是第 10 期为评测写的
  · 必须先定：复用它，还是新写一个非流式入口 —— 这决定要不要动第 12 期刚改过的 chat_service.py

· 补丁三：工具的「写操作」边界
  · 教程说「所有工具都是对已有 service / workflow 的一层包装」，但实测 service 层同时有读和写
      读：list_documents / get / list_chunks / get_chunk / 检索
      写：upload / delete / retry / reindex / update_permission_tags
      管理：users / roles 的全部操作
  · 建议 MCP 只暴露「读 + 问答」，不暴露删除 / 改权限 / 重试这类写操作。三个理由：
      ① 写操作后果不可撤，而 Agent 的判断不保证可靠
      ② Agent 的调用是自动的，用户往往没意识到自己授权了一次删除
      ③ 真要做写操作，应走单独的、需二次确认的工具，而不是混在查询工具里
  · 若教程确实包了写操作，那它至少应要求 admin（复用第 11 期的 CurrentAdmin 口径）
