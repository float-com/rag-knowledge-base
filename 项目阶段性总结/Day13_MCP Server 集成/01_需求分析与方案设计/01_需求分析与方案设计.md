## 一、本期要解决什么

### 1.1 一句话

```
前十二期一直在做"知识库自己好用"：
    能登录、能上传、能检索、能答准、有权限、可评测、扛得住并发、算得起钱。

这一期第一次把能力【朝外】开放：
    让 Cursor / Claude Desktop 这类外部 Agent 直接调用我们的知识库。
```

**注意这不是加功能，而是加一层"对外协议"。** 这一点很关键 —— 教程原文有一句话点得很准：

> RESTful 接口不是写给 Agent 用的。

### 1.2 为什么这一期"不引入新表"

教程原文（方案设计第 4 节）：

> **这一期不引入新表，所有工具都是对已有 service / workflow 的一层包装。**

这是本期最重要的定性判断：**它是一次"包装 + 暴露"，不是一次"造数据"**。
实测本项目现有的 service 能力（见 §3.7）确实已经够用，不需要新表。

### 1.3 与前十二期的关系

| 前面做过什么 | 本期怎么用上 |
| --- | --- |
| 第 11 期：JWT 鉴权 + `permission_tags` 权限体系 | **直接复用**：MCP 客户端先调 `/api/auth/login` 拿 token，再放进 `Authorization: Bearer`（教程明确要求） |
| 第 11 期：`resolve_current_user` 式的"每次请求都重查用户" | **直接复用**：`mcp_server/auth.py` 就是干这个的（教程架构图第 4 格） |
| 第 6～8 期：混合检索 / 精排 / 答案校验 | **被包进工具**：工具的返回值直接来自 `app/services/*` 与 `app/workflows/*` |
| 第 12 期：语义缓存 / 限流 / Celery | **本期不碰**，但见 §3.6 的一个交叉点（问答工具会走缓存） |
| 第 10 期：评测集与指标 | 可包装成工具（评测集有哪些），但见 §3.7 的边界讨论 |

> ⭐ **一句话总结关系**：**前面十二期把"能力"做完了，这一期把"门"装上。**
> 门后面是不是能打，取决于前面做得怎么样 —— 所以本期几乎没有新业务逻辑。

## 二、MCP 是什么（教程原文 + 本项目的理解）

### 2.1 三个角色

教程原文：

```
Server: 暴露能力的一方    ← 本项目要扮演的角色
Client: 调用能力的一方（Cursor / Claude Desktop / 自建 Agent）
工具集 / 资源 / 提示词（三类可被 Agent 调用的原语）
```

**核心机制（教程给的最重要一句）**：

> Server 只需要写一个普通的 Python 函数和类型注解，SDK 会自动注解读出 JSON Schema
> 通过协议告诉客户端「这个工具叫什么、要什么参数、返回什么类型」。

**这就是"不用为每家 Agent 各写一套适配器"的原因** —— 协议层把描述与调用统一了。

### 2.2 三个原语，本期只用 Tools

| 原语 | 是什么 | 教程的取舍 |
| --- | --- | --- |
| **Tools** | 可被 Agent 调用的**函数** | ✅ **本期只用这一类** |
| Resources | 只读数据（如一段文档） | ❌ 本期不用 |
| Prompts | 预设的 prompt 模板 | ❌ 本期不用 |

> 📌 **为什么只做 Tools 就够了**（我的理解）：
> 外部 Agent 对我们的真实需求是"**帮我查一下知识库里有什么**"，
> 这是**动作**而不是**素材**。Resources 更适合"把文档当附件喂给模型"，
> Prompts 更适合"我们希望别人按我们的模板提问"—— 两者都不是本期要解决的问题。
> **少做两类原语，等于少维护两套契约。**

### 2.3 依赖

教程明确：**Python SDK 仓库是 `modelcontextprotocol/python-sdk`，里面就有 FastMCP 和底层协议两层。**

**实测本项目现状：**

```
$ pip list | grep -i "mcp\|fastmcp"
（无输出）

→ ✅ 教程说的"本期新增依赖"成立，MCP SDK 一个都没装。
```

## 三、⚠️ 关键设计决策

### 3.1 为什么不让外部 Agent 直接调我们的 RESTful 接口

**教程给了三条理由**（原文）：

| # | 教程的理由 |
| --- | --- |
| 1 | **契约要靠文档传递，Agent 无法自动感知**：Agent 要调一个 RESTful 接口，得提前知道路径是什么、请求体结构怎样、错误码怎么处理。这些靠文档或手写 system prompt 传递，既容易过时也容易出错 |
| 2 | **每家的工具定义不一致**：Agent 平台各用各的"工具协议"，换一家就要重新写适配代码 |
| 3 | **MCP 把契约做成了协议本身**：工具的 name / description / 参数由 server 在协议层声明，客户端连上就能自动获取完整的工具列表和参数说明，**不依赖外部文档** |

**我补第四条（本项目的实测视角）：**

| # | 补充理由 | 实测依据 |
| --- | --- | --- |
| 4 | **REST 的 29 个端点不是 29 个"工具"** | 实测本项目有 29 条路径 / 40 个操作，其中 `/api/users`、`/api/roles`、`/api/evaluations/*` 这些**管理面**端点根本不是给外部 Agent 用的。若直接暴露 REST，Agent 面前会摆着一堆它不该碰的动作 |

教程还有一句总结得非常好，值得原文抄下来：

> **RESTful 接口不是「给 Agent 用的工具」的语义层。**
> 接口的路径、参数、错误结构是为开发者设计的，不是为模型设计的。
> MCP 的工具描述（name、description、参数注释）是专门给模型看的自然语言提示，
> 能让模型准确判断什么时候该调用哪个工具、参数填什么。

### 3.2 传输方式选 Streamable HTTP

**教程的三种对比**：

| 传输方式 | 教程的评价 | 本项目适用性 |
| --- | --- | --- |
| **stdio** | 本地进程标准输入输出，适合"跟着客户端启动 / 杀掉的本地工具" | ❌ 我们是**长驻服务**，不是每次跟着 Agent 起停的本地小工具 |
| **SSE（旧）** | 服务端推送，**已被官方标记为 legacy** | ❌ 官方都标 legacy 了，新项目不该用它起步 |
| **Streamable HTTP** | **新**：一次普通 HTTP 请求即可完成调用，可选升级为 SSE，方便复用网关 / 反代 / 鉴权基建 | ✅ **选它** |

**教程给的具体落点（很关键）**：

> 具体到部署形态就选这个：通过 FastMCP 的 `streamable_http_app()` 拿到一个 ASGI 子应用，
> 直接 `app.mount("/mcp", …)` 挂到现有 FastAPI 上，**这样不用再起一个独立服务**。

> ⭐ **为什么这一条对教学项目特别重要**：
> 不用新起端口、不用新配反向代理、不用新写鉴权中间件 ——
> **现有的 CORS、异常处理、JWT 全部自动继承**。
> 实测本项目 `app/main.py` 的装配顺序是
> `configure_logging → SQLAlchemy lifespan → CORS → 异常处理器 → include_router`，
> `app.mount()` 只要挂在这一串之后即可，**不需要改动任何一步**。
> （mount 与 include_router 的区别：前者挂的是完整 ASGI 子应用，后者挂的是本应用内的路由表。
> MCP 子应用有自己的路径体系 `/mcp`，所以必须用 mount。）

### 3.3 Schema 独立设计的取舍

**教程原文（方案设计第 5 节）**：

> RESTful API 的请求 / 响应模型本身就是对外契约，但它服务的是网页前端和自家程序，
> 所以字段命名往往直接从 ORM 映射过来。
> 而 MCP schema 是**直接展示给外部 Agent 的协议字段**，不能随 ORM 改动联动，
> 也不该让 Agent 看到不必要的内部细节。
> 所以这一期专门建一个 `app/mcp_server/schemas.py`，**只保留 Agent 真正需要的字段**。

> ⭐ **这条是本期最值得学的设计思路**（我的理解）：
> **同一个业务能力，面向不同消费者时应该有各自的门面。**
> 本项目已经有过一次同构的判断 —— 第 11 期 `api/schemas/auth.py` 的注释里写着
> `UserRead` 必须与前端 `types.gen.ts` 逐字段一致；
> 现在 MCP 也一样：**它的字段集合由 Agent 的需求决定，而不是由 Document ORM 的列决定。**
>
> 📌 好处很实在：**将来 `documents` 表加一列（第 12 期就加过 `version`），
> MCP 的契约不会被动跟着变** —— 否则每次迁移都得回头想"这列要不要给 Agent 看"。

### 3.4 鉴权：复用现有 JWT，不新造一套

**教程原文**：

> 为了降低开发成本，我们直接复用前面的鉴权逻辑，
> 客户端先调 `POST /api/auth/login` 拿 token，再把它放进 `Authorization: Bearer <token>` 头部带给 MCP server。

**实测本项目已具备的部分：**

| 组件 | 位置 | 本期是否需要改 |
| --- | --- | --- |
| 签发 token | `POST /api/auth/login` → `LoginResponse.access_token` | ❌ 不改，直接复用 |
| 校验 token | `app/api/deps.py` 的 `get_current_user` | ❌ 不改，**但要有一份能读原始 ASGI 请求头的等价实现**（见下） |
| 权限标签计算 | `app/services/permission_service.py` 的 `compute_user_permission_tags` / `is_admin` | ❌ 不改，直接用 |

> ⚠️ **一个必须提前想清楚的点（我的补充）**：
> `get_current_user` 是 **FastAPI 的依赖**，它依赖 `Depends` + `HTTPBearer` 那套注入机制。
> 而 `mcp_server/auth.py` 里的 `resolve_current_user` 拿到的是 **MCP 的请求上下文**，
> **不是 FastAPI 的 Request** —— 两者不通用。
>
> 所以 `mcp_server/auth.py` 不是"import 一下 `get_current_user` 就完事"，
> 而是要用**同一套 JWT 解码逻辑**（`app/core/security.py` 里的签发/验签工具）
> 重新写一个"MCP 版"的当前用户解析。
> **→ 这正好解释了教程架构图为什么把 `resolve_current_user` 单独画成一格。**
> 🔴 **待大纲确认**：教程是否把它抽成公共函数（让 FastAPI 侧与 MCP 侧共用一份），
> 还是 MCP 侧独立实现一份。这决定要不要动 `deps.py`。

### 3.5 ⚠️ 补丁：工具必须带权限标签过滤（教程架构图画了，但值得显式强调）

教程架构图的最后一格写的是：

> **PostgreSQL + pgvector（权限标签过滤）**

**它画出来了，但没展开说。而这是本期与第 11 期的头号交叉风险点。**

```
MCP 客户端拿到的 token 属于【某个具体用户】
    ↓
工具返回的数据必须按【这个用户的可见范围】过滤
    ↓
否则：外部 Agent 会成为绕过权限的一条捷径
      —— 用户在 Cursor 里问一句，就能看到他在网页上看不到的文档
```

**具体要做的（与网页侧口径完全一致，不另造一套）**：

| 事项 | 做法 |
| --- | --- |
| 计算当前用户有效标签 | 复用 `permission_service.compute_user_permission_tags(user)`；admin → `None`（不过滤） |
| 传给业务层 | 与网页侧一样传 `permission_tags=` 参数（第 11 期已经给 `list_documents` / `get` / 检索方法都加过这个参数） |
| **不要新造权限口径** | 若 MCP 侧自己判一套"能不能看"，就会出现两套可见范围 —— **这是最危险的做法** |

> 📌 这与第 12 期语义缓存那条"缓存 schema 必须带 `permission_tags` 过滤"是**完全同构**的风险：
> **每加一条新的读取路径，都要重新确认权限过滤还在。**
> 第 11 期踩过"只改 items 不改 count"，第 12 期踩过"只改旧链路的限流"——
> 本期要新增的是**一整条新的对外读取通道**，风险面比前两次都大。

### 3.6 ⚠️ 补丁：问答类工具**不能**用现成的 SSE 流式入口

**这是实测才能发现的一处落差。**

MCP 工具的返回是**一个值**（结构化结果），而本项目现有的问答主入口是**流式的**：

```
实测 app/services/chat_service.py 的入口：
    async def stream_answer(...)              ← SSE 流式，产出事件序列，不是返回值
    async def answer_for_evaluation(question) ← ★ 非流式，返回 EvaluationAnswer
```

**→ 所以如果教程的工具里有一个"向知识库提问"，它不可能直接包 `stream_answer`。**

现成的非流式入口只有一个：`answer_for_evaluation`。但它是**第 10 期为评测写的**，有两个需要注意的性质：

| 性质 | 对 MCP 是好事还是坏事 |
| --- | --- |
| 面向"单轮、无会话历史" | ✅ 正好符合工具调用（Agent 自己管上下文） |
| 返回结构化结果（含引用） | ✅ 正好符合 MCP 需要返回结构化数据 |
| 为评测设计，可能有"绕缓存"之类的评测专属行为 | ⚠️ 需要确认：MCP 工具该不该走语义缓存？ |

🔴 **待大纲确认**：教程是复用了某个现成的非流式入口，还是**新写一个**？
这个问题必须在动手前定，因为它决定要不要动 `chat_service.py`（第 12 期刚改过的文件）。

### 3.7 ⚠️ 补丁：工具的"写操作"边界（教程未展开）

教程说"所有工具都是对已有 service / workflow 的一层包装"。
但实测本项目的 service 层**同时包含读与写**：

```
读类：list_documents / get / list_chunks / get_chunk / list_conversations / list_messages
      vector_search / keyword_search / hybrid 检索
写类：upload / delete / retry / reindex / update_permission_tags
      create_conversation / delete_conversation
      create_run / delete_run / update_item_bad_case（评测）
管理类：users / roles 的全部操作
```

> ⭐ **我的建议（待大纲确认后调整）**：
> MCP 工具**只暴露"读 + 问答"这类能力**，不暴露删除 / 改权限 / 重试这类写操作。三个理由：
> 1. **写操作的后果不可撤**（删文档、改可见性），而 Agent 的判断不保证可靠；
> 2. **Agent 的调用是"自动"的**，用户往往没意识到自己授权了一次删除；
> 3. 真要做写操作，也应该走**单独的、需要二次确认的**工具，而不是混在查询工具里。
>
> 教程若把某个写操作也包成了工具（比如"上传文档"），
> 那它至少应当要求 **admin**（复用第 11 期的 `CurrentAdmin` 口径），而不是任意登录用户。

### 4.2 MCP 与 RESTful 是两条并行的通路，不互相替代

```
网页前端 ──RESTful /api/*──→ app/api/routes/*  ─┐
                                                 ├─→ app/services 与 app/workflows ─→ PostgreSQL
外部 Agent ──MCP /mcp────────→ app/mcp_server/*  ─┘
```

> ⭐ **教程原文有一句关键的定位**：
> 「**MCP 面向外部 Agent 生态，两者并不冲突**」。
>
> 所以本期**不动任何现有 REST 路由** —— 不删、不改、不迁移。
> 实测的 29 条路径 / 40 个操作在本期结束后应当**一条不多、一条不少**
> （这是验收标准里的一条回归底线，见 §8.3）。

## 七、⚠️ 风险预警

### 7.1 MCP × 权限 = 本期最大风险

```
新增的是一整条【对外读取通道】
    ↓
它必须与网页侧共用同一套权限判断（permission_service），而不是自己判
    ↓
否则外部 Agent 成为绕过第 11 期权限体系的捷径
```

**对策**：工具实现里**只传参、不判权** —— 把 `permission_tags` 传给已有 service，
让第 11 期验证过的过滤逻辑继续生效。详见 §3.5。

### 7.2 MCP × 语义缓存 = 交叉点（第 12 期的产物）

第 12 期上了语义缓存。如果问答类工具走 `chat_service`，它会**自动享用缓存**。

- ✅ **好处**：Agent 反复问同一句话，几乎零成本；
- ⚠️ **要注意**：缓存命中会**跳过整张图**（不检索、不调 LLM），
  所以工具返回的 `trace_id` 之类"检索轨迹"字段在缓存命中时是**不存在的**。
  MCP 的 schema 设计要让这些字段**可空**，不能让 Agent 以为一定有。

### 7.3 MCP × 上一轮刚踩过的两个坑

| 坑 | 本期会不会再遇到 |
| --- | --- |
| **HF 环境注入漏了 worker**（BUG-05） | ❌ 本期不新增进程，不会遇到。但**如果 MCP 那侧要跑检索/重排模型**，就要重新检查一遍——第 12 期的教训是"新进程入口都要设一次 HF 环境" |
| **直传链路漏改**（BUG-02 / 限流漏挂） | ⚠️ **同构风险仍然存在**：只改"显眼的那条路"而漏掉另一条。本期有两条通路（REST 与 MCP），**必须从"能力清单"逐个打钩，而不是按文件排查** |

### 7.4 协议层的东西，自测容易"看起来成功"

第 12 期最深的教训是：**接口返回成功 ≠ 事情真的做成了**。
MCP 更甚 —— 一个工具"能被调用"和"客户端能正确理解它"是两件事：

```
工具函数跑通了           ← 单元测试能覆盖
    ≠ 客户端能列出它      ← 需要 tools/list 真的能返回
    ≠ 参数 schema 正确    ← 需要保证描述足够让模型填对参数
    ≠ 端到端真的能用      ← 需要真实 MCP 客户端连一次
```

**对策**：验收标准里必须包含"用真实客户端连一次"（见 §8.2）。
