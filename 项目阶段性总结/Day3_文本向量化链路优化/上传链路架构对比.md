# 文档上传：新旧两条链路架构对比

本文对比项目中并存的两条上传链路，用于理解"预签名 URL 直传"重构的动机与代价。

- **旧链路（multipart 代理上传）**：仍在代码中，前端已不再调用，作为灰度回滚与旧客户端兼容保留。
- **新链路（预签名直传）**：当前前端实际使用的链路。

涉及文件：

| 层次 | 旧链路 | 新链路 |
| --- | --- | --- |
| 前端 | `frontend/src/client/sdk.gen.ts` → `uploadDocument()` | `frontend/src/api/directDocumentUpload.ts` |
| 路由 | `backend/app/api/routes/documents.py` → `POST /api/documents` | `backend/app/api/routes/document_uploads.py` |
| 服务 | `backend/app/services/document_service.py` → `upload()` | `backend/app/services/document_upload_service.py` |
| 存储 | `file_service.upload()` | `file_service.create_presigned_upload()` / `verify_uploaded_object()` / `hash_object()` |
| 数据 | 只有 `documents` 一张表 | 新增 `upload_sessions` 表（两个状态机） |

## 二、新链路：预签名 URL 直传

### 时序图

```
浏览器 / 前端                FastAPI (8000)                     腾讯云 COS
     |                            |                                  |
     |  POST /uploads/init        |                                  |
     |  {file_name,size,mime,     |                                  |
     |   permission_tags} ------->|                                  |
     |  ★ 只有元数据，没有文件     |                                  |
     |                            | 1. 大小上限校验                    |
     |                            | 2. _resolve_upload_type() 后缀白名单
     |                            | 3. 建 UploadSession(INITIATED)     |
     |                            |    object_key =                    |
     |                            |      document-uploads/{uuid}/{名}  |
     |                            | 4. create_presigned_upload()       |
     |                            |    Method=PUT, Expired=300,        |
     |                            |    签名绑定 key + Content-Type      |
     |                            |    commit()                        |
     |<---------------------------|                                  |
     |  {upload_id, object_key,   |                                  |
     |   presigned_url,           |                                  |
     |   status=initiated}        |                                  |
     |                            |                                  |
     |  ┌──────────────────────────────────────────────────────┐    |
     |  │ ★ 文件二进制直接 PUT 到 COS，完全不经过 8000 端口      │    |
     |  │   浏览器必须先发 OPTIONS 预检（跨域！）                │    |
     |  │   OPTIONS + Origin -------------------------------------->|  |
     |  │   <------------------------------------ 200 Allow-Origin  |  |
     |  │   PUT presigned_url + Content-Type --------------------->|  |
     |  │   <------------------------------------ 200 ETag         |  |
     |  └──────────────────────────────────────────────────────┘    |
     |                            |                                  |
     |  POST /uploads/{id}/complete                                  |
     |  (空请求体) -------------->|                                  |
     |                            | 5. 取会话 + _ensure_not_expired()  |
     |                            | 6. 状态机：FINALIZING/COMPLETED    |
     |                            |       → 幂等返回；其他 → 409        |
     |                            | 7. verify_uploaded_object()        |
     |                            |    head_object(object_key) ------>|  HEAD
     |                            |<---------------------------------|  Content-Length
     |                            |    ★ 比对实际 size 与 MIME         |  Content-Type
     |                            |      以 COS 为权威，不信请求体      |
     |                            | 8. status=FINALIZING → commit()    |
     |                            | 9. background_tasks.add_task(      |
     |                            |        finalize_upload, id)        |
     |<---------------------------|                                  |
     |  status=finalizing         |                                  |
     |  ★ 只是"已受理"，还没建档   |                                  |
     |                            |                                  |
     |                            | 10. [后台] finalize_upload()      |
     |                            |     ★ 用独立 AsyncSessionLocal     |
     |                            |     hash_object() ───────────────>|  流式读取
     |                            |<---------------------------------|  分块 1MB 算 SHA-256
     |                            |     repo.get_by_hash()             |
     |                            |     ├─ 命中 → 删临时对象 → COMPLETED |
     |                            |     │         ★ 去重：不建 Document |
     |                            |     └─ 未命中 ↓                    |
     |                            |     建 Document(status=UPLOADING)  |
     |                            |       cos_object_key = 临时路径     |
     |                            |     upload_session = COMPLETED     |
     |                            |     commit()                       |
     |                            |     最后才 ingest_document()       |
     |                            |     PARSING → INDEXING → READY     |
```

### 对象键规则

```
临时（上传中）：document-uploads/{upload_id}/{原始文件名}
                              ↑
                    按会话隔离，防并发同名覆盖

正式 Document 记录沿用它，不再搬到 documents/ 前缀下，
但 documents.file_hash 的唯一约束仍然保留（去重语义不变，物理路径换规则）
```

### 端点一览

| 端点 | operation_id | 作用 | 位置 |
| --- | --- | --- | --- |
| `POST /api/documents/uploads/init` | `initDocumentUpload` | 建会话 + 签发预签名 URL | `document_uploads.py:56` |
| `POST /api/documents/uploads/{id}/complete` | `completeDocumentUpload` | COS HEAD 校验 + 挂后台任务 | `document_uploads.py:84` |
| `DELETE /api/documents/uploads/{id}` | `abortDocumentUpload` | 幂等取消 + 清理云端垃圾 | `document_uploads.py:119` |

## 三、逐维度对比

| 维度 | 旧链路 | 新链路 |
| --- | --- | --- |
| **文件是否经过业务服务器** | ✅ 经过（进一次、出一次） | ❌ 完全不经过 |
| **网络传输量** | 2 倍文件大小 | 1 倍文件大小 |
| **服务端内存峰值** | 整个文件驻留内存 | 仅几百字节 JSON |
| **读文件内容的位置** | 上传接口内 | 后台 finalize 阶段（流式 1MB 分块） |
| **算哈希的时机** | 上传前（已拿到全量 bytes） | 上传后（流式读 COS 对象） |
| **大小/类型校验依据** | 服务端实际读到的 bytes | init 声明值 + complete 时 COS HEAD 复核 |
| **去重命中的代价** | 文件已传到服务器才发现重复 | 文件已传到 COS 才发现重复（多一次上云，但省了服务器带宽） |
| **预签名有效期** | 无（无签名） | 300 秒（`document_upload_service.py:42`） |
| **密钥是否下发前端** | — | 否，只下发签名结果 |
| **跨域要求** | 无（同源走 vite 代理） | **需要 COS 桶配置 CORS** |
| **数据库表** | `documents` | `documents` + `upload_sessions` |
| **状态机数量** | 1 个 | 2 个 |
| **上传中断后的可见状态** | 无记录 / 半途失败 | `INITIATED` / `ABORTED` / `EXPIRED` 可追踪 |
| **响应返回时机** | COS 上传完成后 | COS HEAD 校验后（更早） |
| **回滚方式** | — | 前端改回调 `uploadDocument()` 即可 |

## 四、两个状态机（新链路特有）

```
┌─ upload_sessions ──────────────────────────────────────────────┐
│                                                                │
│   INITIATED ──complete──> FINALIZING ──finalize成功──> COMPLETED│
│       │                        │                               │
│       │                        └──finalize异常──> FAILED        │
│       ├──DELETE /abort──> ABORTED                              │
│       └──超过 expires_at──> EXPIRED                            │
│                                                                │
│   作用：只管"文件有没有成功传上来"                                │
└────────────────────────────────────────────────────────────────┘

┌─ documents ────────────────────────────────────────────────────┐
│                                                                │
│   UPLOADING ──> PARSING ──> INDEXING ──> READY                 │
│       └──────────────任一环节异常──────────────> FAILED          │
│                                                                │
│   作用：只管"内容有没有处理完"                                    │
└────────────────────────────────────────────────────────────────┘
```

两个状态机的关系：

```
finalize_upload 成功建档 ──> documents 记录出现（此刻 upload_sessions 已 COMPLETED）
        │
        └─> 紧接着调用 ingest_document() ──> documents 状态开始推进

前端列表按 documents.status 轮询：非终态则每 3 秒刷新
```

## 五、为什么新链路值得这么改

1. **带宽与内存**：后端不再承载文件字节流，100MB 文件从"进出各一次"变为"完全不经过"。
2. **可追踪**：上传会话独立成表，网络中断 / 用户取消 / URL 过期都有明确状态，可被 `cleanup_expired` 回收。
3. **权限可扩展**：`UploadSession.permission_tags` 在 init 阶段就能暂存下来（当前 `Document` 模型尚未持久化该字段）。
4. **响应更快**：`complete` 只做一次 HEAD 校验就返回，把哈希与向量化全部丢给后台。

## 六、新链路引入的代价（架构取舍）

1. **必须配置 COS CORS**：浏览器直传是跨域请求，且 `Content-Type` 非简单头会触发 OPTIONS 预检。桶上没配规则就会静默失败（前端原生 fetch 不走统一错误拦截器）。
2. **签名头一致性**：`Content-Type` 参与签名计算，浏览器 PUT 时必须发送与 init 阶段完全相同的值，否则 COS 判定签名无效。
3. **多一次"上传后才发现重复"**：去重移到 finalize，重复文件仍会先传上 COS 再被删除。
4. **多一张表、多一个清理任务**：需要 `scripts/cleanup_upload_sessions.py` 兜底回收过期的临时对象。
5. **`complete` 不能只信前端**：必须以 COS HEAD 的结果为权威，否则可以跳过真实上传直接"造"出 Document 记录。
