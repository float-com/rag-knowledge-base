## 一、本节要解决的问题

非流式三件套（创建会话 / 查会话 / 拉消息）是**基础 CRUD**，几十毫秒结束。而 `stream_answer` 是完整的 RAG 问答，并且要满足一个硬约束：

> **答案要一个字一个字地"流"给用户，而不是等全部生成完再一次性返回。**

这个约束把原本简单的"调用链"变成了**三段式结构**：

```
① 流式开始之前   会话校验              → 仍可返回 404
② 流式进行中     装历史/落库/检索/生成  → HTTP 状态码已锁死 200，出错只能发事件
③ 流式结束之后   落库回复与引用         → 补上收尾数据
```

**理解这三段，就理解了代码为什么长这样。** 本节所有设计点都可以归到这三段的某一段里。

## 二、`stream_answer` 十步拆解

### 步骤 1：会话校验——为什么它用请求级 session

```python
await self.get_conversation(conversation_id)      # 请求级 session
async with AsyncSessionLocal() as session:        # 之后才开独立 session
```

**注意边界**：会话校验发生在**流式响应开始之前**。此时还是普通 HTTP 请求，抛 `NotFoundError` 能正常返回 **404**。

一旦开始 `yield`，响应头已经发出，状态码锁定 **200**——之后再也不可能改用 4xx/5xx 表达错误。

> **流式接口第一原则：能在流之前做完的事，尽量在流之前做。** 会话校验放这里，就是因为它需要一个明确的 404。

### 步骤 2：开独立 session

```python
async with AsyncSessionLocal() as session:
```

**为什么不能复用 `self.session`？** `self.session` 是请求级的，生命周期 = 一次 HTTP 请求。而 SSE 请求会持续**几十秒到几分钟**，这条连接会被一直占着。

```
连接池 pool_size=5
→ 5 个用户同时提问
→ 5 条连接全被占住
→ 第 6 个用户连"刷新会话列表"都要排队等连接
```

`async with` 保证正常结束或异常退出时连接都会归还。

### 步骤 3：装历史 + 标准化查询——顺序不能颠倒

```python
state.update(await load_context(state, session))    # 先读历史
state.update(await normalize_query(state))          # 再标准化查询
```

**真正的约束在步骤 4：**

```
必须先 load_context（读历史）  →  再落库用户提问（写数据库）
```

**如果写反了会怎样？** 用户提问已经 INSERT 进数据库，`load_context` 会把**本轮提问**当成"历史消息"读回来：

```
chat_history = [..., HumanMessage("这门课的课程目标是什么")]   ← 本轮提问混进来了
当前 question = "这门课的课程目标是什么"                      ← 又一次
```

模型看到"历史里问过 Q3 了，现在又问一次"，于是：

- 答非所问（以为你在追问）
- 说"这个问题你刚才已经问过了"
- 把两次提问当成两个不同问题分别回答

**⚠️ 这个错误不会抛任何异常，日志干干净净**，只表现为回答质量静默劣化。属于"你只会觉得最近回答变笨了"的那类难查 bug。

### 步骤 4：落库用户提问 + 单独 commit

```python
async def _persist_user_message(self, state, session):
    repo = ConversationRepository(session)
    user_msg = ConversationRepository.make_user_message(
        state["conversation_id"], content=state["question"]
    )
    await repo.add_messages([user_msg])
    await session.commit()          # 单独提交
    state["user_message_id"] = user_msg.id
```

**为什么不和助手回复合并成一次提交？**

```
若合并提交：
  用户提问 INSERT（未提交）
  → 检索失败 / LLM 超时 / 网络中断
  → 整个事务回滚
  → 用户提问也没了
  → 用户刷新页面，发现自己问的问题完全不见了
```

**单独提交的收益：**

1. **用户输入永不丢失**：LLM 挂了，问题还在数据库里
2. **前端可实现"重发"**：提问有 `id`，前端可基于它做重试按钮，不必让用户重新打字
3. **开发排查有现场**：数据库里能看到"用户问了什么但没得到回答"

这也解释了 `except` 分支里的注释：

```python
await session.rollback()
# 用户提问已在步骤 4 单独提交，回滚不会把它删掉。
# 这里回滚的是"助手回复 + 引用"这一批尚未提交的写入。
```

### 步骤 5：`message_start` 为什么在检索**之前**发

```python
yield {"event": "message_start", "data": {"user_message_id": str(...)}}   # 先发
state.update(await retrieve(state, session))                              # 再检索
```

**这是性价比很高的优化。** 检索要先调 DashScope 把问题转成查询向量——第 9 章实测**平均 1000ms**。

```
等检索完再发 message_start：
  前端这 1 秒内什么都做不了，用户盯着空白界面，不知道系统是不是卡了

提前发 message_start：
  前端立刻拿到 user_message_id
  → 马上渲染用户气泡（确认"我的问题发出去了"）
  → 显示"正在检索知识库…"过渡态
```

> **一句话：别让一次外部 API 的耗时拖延首屏反馈。**

### 步骤 6：引用回填 + 生成分支（本节核心）

```python
citations_payload = [
    _serialize_citation(chunk, ordinal=i)
    for i, chunk in enumerate(state.get("retrieved_chunks", []), start=1)
]
yield {"event": "citations", "data": {"citations": citations_payload}}

if state.get("refused"):
    yield {"event": "token", "data": {"delta": state["answer"]}}      # 拒答：只发 1 次
else:
    answer_parts = []
    async for delta in stream_generate(state):
        answer_parts.append(delta)
        yield {"event": "token", "data": {"delta": delta}}
    state["answer"] = "".join(answer_parts)                            # 编排层写回
```

**三个关键点：**

**① `if state.get("refused")` 是第 9 章埋下的坑。**
`retrieve` 在拒答时已把 `state["answer"]` 写成拒答文案。若这里忘判 `refused` 直接调 `stream_generate`，模型输出会**覆盖**拒答文案——**熔断白做**。
实测证实此坑已避开：拒答分支 `token` 只出现 1 次。

**② `answer_parts` 累积 + 回写 `state["answer"]` 是第 9 章第 4 题的答案。**
`stream_generate` 是异步生成器，只能 `yield` 碎片，**不能 `return` 完整 dict**。所以"累积拼接并回写 state"只能由编排层做。这三行就是"不知道"的落地。

**③ 拒答分支里没有任何指向 LLM 的调用。**
这是"机制上不给幻觉机会"的最终体现。

### 步骤 7：落库助手回复 + 引用——必须同一事务

```python
await conv_repo.add_messages([assistant_msg])       # flush
if not state.get("refused"):
    await citation_repo.bulk_add(citations)         # flush
await session.commit()                              # 一次提交，两者原子
```

**分开提交的恶果：**

```
助手消息已提交  →  引用写入失败  →  用户看到一条回答，点引用全空
                                 →  无法自动修复（不知道哪些回答缺引用）
```

**注意 `if not state.get("refused")`**：拒答路径**不写引用**。因为拒答意味着"没有找到可靠依据"，**没有可溯源的原文**，硬写引用就是假的。

### 步骤 8：异常必须转成 `error` 事件

```python
except Exception as exc:
    logger.exception("chat stream failed: conversation_id=%s", conversation_id)
    await session.rollback()
    yield {"event": "error", "data": {"code": "chat_stream_failed", "message": str(exc) or "问答处理失败"}}
```

**为什么不能直接 `raise` 交给上层中间件？**

```
流式响应一旦开始 yield：
  1. HTTP 响应头已经发出
  2. 状态码 200 已经写死在响应里
  3. 此时抛异常，上层中间件想返回 500
     → 但响应体已在流式传输中，状态码无法再改
     → 结果：连接异常中断，前端收到一个"既无 message_end 也无 error"的残缺流

前端无法判断：
  - 网络断了？
  - 后端崩了？
  - 还是回答本来就到这里为止？
```

> **"流式"与"请求-响应"最本质的差别**：请求-响应模式下，错误是**状态码**的事；流式模式下，错误只能是**协议内的事件**。

## 三、自测题与批改记录

### 题目与作答

| # | 题目 | 作答 | 判定 |
| --- | --- | --- | --- |
| 1 | 为什么 `load_context` 必须在落库提问之前？顺序反了模型会看到什么？会报错吗？ | "模型会看到用户的问题出现两次，严重影响资源" | ⚠️ 现象对，结局说错 |
| 2 | `message_start` 为什么放在检索之前发送？前端获得什么好处？ | "把能提前给前端的信息都给前端，否则流式开始后状态码 200 无法更改，可能造成阻塞" | ⚠️ 串题 |
| 3 | 用户提问为什么单独 `commit`，而非与助手回复合并提交？ | "兜底策略，后续流式异常时用户问题已落库，可以继续向前端发送" | ✅ |
| 4 | 流式接口为什么必须自己 `try/except`，不能抛给上层？ | "流式过程中无法中断，跟普通接口一样会严重影响用户体验" | ⚠️ 方向对，未到机制 |
| 5 | 拒答分支 `token` 为什么只发 1 次？根本目的（不止省 token）？ | "不知" | ❌ |

### 逐题批改

**第 1 题 —— 现象对，但结局不是"资源"问题**

"问题出现两次"的现象判断正确。但这不是资源问题，**是答案质量问题**，且**不会抛异常**：

```
正常:  chat_history = [Q1, A1, Q2, A2]   + 当前 Q3
写反:  chat_history = [Q1, A1, Q2, A2, Q3]  + 当前 Q3   ← Q3 混进历史了
```

模型看到"历史里已经问过 Q3 了"，会答非所问 / 说"你刚才问过了" / 把两次当两个问题分别答。**全是静默的质量劣化，日志干干净净。**

> **危险之处正是它不报错**——你只会觉得"最近回答怎么变笨了"，不会想到是两行代码顺序问题。

**第 2 题 —— 串题了**

作答里塞了两个理由，但其中之一是**第 4 题的答案**：

```
"把能提前给前端的信息都给前端"          ✅ 第 2 题的正确方向
"否则流式开始后状态码 200 无法更改"      ❌ 这是第 4 题的理由
```

第 2 题问的是"为什么放在**检索之前**"，答案是**时间成本**：检索调 embedding 实测约 1000ms，等它完成再发 `message_start`，前端这 1 秒只能面对空白界面。提前发则可立即渲染用户气泡 + 显示过渡态。

> **与状态码无关。**

**第 3 题 —— 正确**

"兜底 + 用户问题已落库"，方向正确。补充两点实际收益：

1. 前端可基于 `user_message_id` 实现"重发"
2. 数据库留下"问了什么但没得到回答"的排查现场

**第 4 题 —— 方向对，但没到机制层**

"无法中断、影响体验"感受正确，但技术原因要说清：

```
响应头已发出 → 状态码 200 已写死 → 抛异常也无法改为 500
→ 连接异常中断 → 前端收到"既无 message_end 也无 error"的残缺流
```

**这才是"流式"和"请求-响应"最本质的差别**：错误从"状态码的事"变成"协议内事件的事"。

**第 5 题 —— 本节设计含量最高的一处**

拒答分支 `token` 只发 1 次就结束，根本目的：

> **完全不调用大模型——从机制上不给模型编造答案的机会。**

| | 交给 LLM 判断 | 编排层熔断（本项目） |
| --- | --- | --- |
| 流程 | 检索 → 照常调 LLM → 让模型自己判断 | 检索 → 判定不够 → **根本不调 LLM** |
| 约束方式 | **靠 prompt 求模型"别编"** | **架构上不给它开口的机会** |
| 失败模式 | 模型面对"无资料但有满腹常识"时极易编造 | 不存在此失败模式 |

**省 token 只是副产品**（实测省掉一次完整 7 秒调用），真正值钱的是：**知识库答不了的问题，系统永远不会给出一个"看起来很像真的"的假答案。**

> **"机制上杜绝"永远强于"约束上祈祷"。**

## 四、三题串起来的共同主题

第 1、4、5 题表面在问三件不同的事，实际是同一个主题：**流式的本质约束——"流一旦开始，很多事情就回不去了"**。

```
历史读错了  → 回不去（质量已污染，且不报错）
状态码错误  → 改不了（只能发协议内事件）
LLM 调过了  → 就有幻觉风险（所以必须提前熔断）
```

**三条串起来，就是 `stream_answer` 的设计逻辑**：

> **凡是"不可逆"的动作，都要放到尽可能晚，并在前面把能做的检查都做完。**

## 五、实测验证记录

代码写入后跑了**两条分支**的真实链路：

```
① 正常问答分支    提问「这门课的课程目标是什么」
   事件序列: message_start -> citations -> token × 48 -> message_end
   citations: 5 条, [1] score=0.6883, [2] score=0.6446
   message_end: refused=false
   回答: 403 字 / 耗时 7.4s
   回答开头: "这门课的课程目标有以下几个方面：**课程目标 1（专业知识面）**…[1]"
   落库: user(11字) + assistant(403字, metadata={'refused': False}) + 5 条引用

② 拒答熔断分支    提问「红烧肉的做法和食材配比是什么」（与知识库无关）
   事件序列: message_start -> citations -> token × 1 -> message_end
   citations: 5 条但分数仅 0.426 / 0.4228 / 0.4207（远低于 0.6 阈值）
   message_end: refused=true
   回答: "抱歉，知识库中没有找到与该问题相关的可靠依据。"
   ★ token 事件仅 1 次 → 未调用大模型
   ★ 落库引用 0 条 → 拒答不写引用
   落库: assistant metadata={'refused': True}
```

**三条设计点被实测证实：**

1. **熔断真的在 LLM 之前生效**：拒答分支 `token` 只 1 次，`stream_generate` 未被调用
2. **`refused` 判断没有漏**：若编排层忘判，拒答文案会被模型输出覆盖
3. **引用序数三方对齐**：回答 `[1]` / citations `ordinal=1` / `answer_citations.ordinal=1` 指向同一切片

## 七、一句话总结

> `stream_answer` 把 RAG 全链路的**十个步骤**与**五个 SSE 事件**一一映射：会话校验放在流之前（保住 404）、独立 session 撑长连接、`load_context` 早于落库提问（否则历史污染）、用户提问单独 commit（保住用户输入）、`message_start` 早于检索（别让 1 秒 embedding 拖延首屏）、拒绝时根本不调 LLM、助手消息与引用单事务原子提交、异常转 `error` 事件（状态码已锁死）。
> **贯穿始终的一条原则：凡不可逆的动作放到最后，前面把检查做完。**
