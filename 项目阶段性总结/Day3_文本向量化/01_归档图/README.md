## 一、为什么按「原代码目录」分三级

本目录下的 `api/routes`、`api/schemas`、`services`、`ingestion` **不是随手建的分组**，
而是**严格对应图原先所在的代码目录**：

```
backend/app/api/routes/   →  01_归档图/api/routes/
backend/app/api/schemas/  →  01_归档图/api/schemas/
backend/app/services/     →  01_归档图/services/
backend/app/ingestion/    →  01_归档图/ingestion/
```

这样做的理由只有一个：**看到图就知道该去读哪份代码**。
如果把 13 张图拍平在一个目录里，文件名前缀（`01_API控制层_…`）虽然还能分辨层次，
但"它对应哪个模块"这层信息就丢了，复习时要靠猜。

## 三、两条搬迁时的核对结论（都实测过）

### 3.1 这些图没有被任何文档引用

搬之前全库检索过 `*.md` 里的这几组文件名（`API控制层_` / `API契约层_` / `文档服务层_` /
`文档核心服务_` / `文档摄取流水线`），**零命中**。

所以：

- 搬迁**不会**造成任何 Markdown 图片链接失效；
- 同时也说明这些图此前是**"有图无文"**的状态 —— 没有哪篇总结引用它们。

### 3.2 原目录只删了图，代码没动

```
backend/app/api/routes     文件数 9（只剩 .py）      目录仍在
backend/app/api/schemas    文件数 8（只剩 .py）      目录仍在
backend/app/services       文件数 10（只剩 .py）     目录仍在
backend/app/ingestion      文件数 5（只剩 .py）      目录仍在
```

⚠️ **一处必须知道的副作用**：原先这些图与代码同目录，
可能有渲染脚本 / 手工流程按"图在代码旁边"的假设工作。
若以后再生成这类图，**请直接输出到本目录对应子目录**，
不要再写回 `backend/app/` —— 否则又会散出去。
