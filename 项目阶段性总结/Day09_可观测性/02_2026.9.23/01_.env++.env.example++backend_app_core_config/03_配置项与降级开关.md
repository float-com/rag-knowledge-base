## 二、配置字段清单

```python
# ===== LangSmith 可观测性（第 9 期）=====
# 关掉后 @traceable / LangChain 自动 trace 全部降级为 no-op、trace_id 返回 None，
# 业务链路完全不受影响（见 app/core/observability.py 的实现）。
langsmith_tracing: bool = False
langsmith_api_key: str = ""
langsmith_project: str = "rag-knowledge-base"
langsmith_endpoint: str = "https://api.smith.langchain.com"
langsmith_run_url_prefix: str = ""
```

| 字段 | 默认值 | 作用 | 缺了会怎样 |
| --- | --- | --- | --- |
| `langsmith_tracing` | `False` | 追踪总开关 | 默认不追踪 |
| `langsmith_api_key` | `""` | 上报鉴权 | 只开开关也**不算启用** |
| `langsmith_project` | `"rag-knowledge-base"` | 上报到哪个项目 | 落到 SDK 默认项目 |
| `langsmith_endpoint` | `"https://api.smith.langchain.com"` | 官方服务地址 | — |
| `langsmith_run_url_prefix` | `""` | LangSmith UI **私有** URL 前缀 | 前端只显示"复制"，不给跳转链接 |

> **`langsmith_run_url_prefix` 为什么默认空**：它形如
> `https://smith.langchain.com/o/<org_id>/projects/p/<project_name>`，
> **包含 workspace / org 信息、属于各人私有**，所以教程把它做成"可选、配置了才下发"。

## 三、`observability_enabled` —— 把两个条件合成一个布尔

```python
@property
def observability_enabled(self) -> bool:
    """LangSmith 实际生效开关：开关打开 + key 已配置。任一缺失都视为关闭。"""
    return bool(self.langsmith_tracing and self.langsmith_api_key)
```

**教程原话**：这样下游逻辑**只需要看一个布尔值**，不用每次拼接两个字段。

### 为什么这个属性必须存在（不只是为了省事）

它是第 1 章 §4.3 那次实测的直接产物：

```
只开 TRACING、不填 KEY
    → SDK 照样在本地把 run 建起来（get_current_run_tree() 有值）
    → 于是代码会把 trace_id 发给前端
    → 但上报必然 401，LangSmith 上什么都查不到
    → 结果：前端一个点进去打不开的坏链接 + 每次请求打一行错误日志
```

**对策**：把"是否真的启用"收敛成**一个属性**。
若在每个调用点各自判断两个字段，**早晚会漏掉其中一个**，
从而在"key 没配"时下发一个点不开的坏链接。

## 四、环境变量

在 `.env` / `.env.example` 末尾追加：

```dotenv
# ==============================================================================
# LangSmith 可观测性（第 9 期）
# ==============================================================================
# 追踪开关：false = 整条链路降级；true 时必须同时填 LANGSMITH_API_KEY 才算启用
LANGSMITH_TRACING=false
# 在 https://smith.langchain.com 注册后，于 Settings → API Keys 创建
LANGSMITH_API_KEY=
LANGSMITH_PROJECT=rag-knowledge-base
LANGSMITH_ENDPOINT=https://api.smith.langchain.com
# 格式：https://smith.langchain.com/o/{org_id}/projects/p/{project_name}
# 留空则前端只显示"复制 trace_id"、不给跳转链接
LANGSMITH_RUN_URL_PREFIX=
```

**启用步骤**：把 `LANGSMITH_TRACING` 改成 `true` + 填上 `LANGSMITH_API_KEY`。
`LANGSMITH_RUN_URL_PREFIX` 是**可选的**，暂时拿不到可以先空着。

> ⚠️ 教程截图里写的是 `LANGSMITH_TRACING=False`（大写 F）。
> pydantic 解析 bool 不区分大小写，写法都对；本项目沿用 `.env` 里的小写惯例
> （与 `RERANK_ENABLED=true` 等既有项保持一致）。

## 五、⭐ 关键认识：为什么不能只写 `.env` 就完事

**这是本章最重要的一句话**：

> **LangSmith SDK 读的是 `os.environ`，不是我们的 `Settings` 对象。**

**证据（可直接在依赖源码里看到）**：`langsmith/utils.py` 里所有环境变量都走
`get_env_var(name)`，它按 `("LANGSMITH", "LANGCHAIN")` 两个前缀拼名字去读 `os.environ`：

```python
# langsmith/utils.py（依赖源码）
def get_env_var(name, default=None, *, namespaces=("LANGSMITH", "LANGCHAIN")):
    names = [f"{namespace}_{name}" for namespace in namespaces]
    for name in names:
        value = os.environ.get(name)
```

而 `config.py` 的 `model_config` 里设了 **`extra="ignore"`** ——
**没在本类显式声明的键会被静默丢弃**，根本不会被写回环境变量。

**所以两个条件同时成立**：

| # | 事实 | 后果 |
| --- | --- | --- |
| 1 | SDK 只读 `os.environ` | 光配 `Settings` 字段没用 |
| 2 | `extra="ignore"` 挡掉未声明键 | 光配 `.env` 也没用 |

→ **必须有一步显式的"把 Settings 搬运到 `os.environ`"**，这就是第 4 章的 `observability.py`。

> 🔁 **本项目第二次遇到同一类坑**：`HF_ENDPOINT` 当年也是"写进 `.env` 却不生效"，
> 原因完全一样（第三方库只在 import 阶段读 `os.environ`，而 pydantic 不写回环境）。
> 第 4 章的 `configure_observability` 与既有的 `hf_env.setup_hf_environment` 是**同一套路**。

## 六、`LANGSMITH_*` 与 `LANGCHAIN_*` 两套前缀

`get_env_var` 的 `namespaces=("LANGSMITH", "LANGCHAIN")` 说明：
SDK **同时认两套前缀**，且 **`LANGSMITH_` 优先**。

| 本项目的写法 | SDK 同样认的旧写法 |
| --- | --- |
| `LANGSMITH_TRACING` | `LANGCHAIN_TRACING_V2` / `LANGCHAIN_TRACING` |
| `LANGSMITH_API_KEY` | `LANGCHAIN_API_KEY` |
| `LANGSMITH_PROJECT` | `LANGCHAIN_PROJECT` |
| `LANGSMITH_ENDPOINT` | `LANGCHAIN_ENDPOINT` |

> 教程正文用的是新前缀，但开头出现过一次 `LANGCHAIN_TRACING`。
> **统一用 `LANGSMITH_*` 一套**，避免两套并存时优先级打架（新前缀优先）。

## 七、验证结果

| 场景 | `observability_enabled` | 函数体内 `trace_id` | 说明 |
| --- | --- | --- | --- |
| `TRACING=false` + 无 key | `False` | `None` | 完全降级 |
| **`TRACING=true` + 空 key** | **`False`** | **`None`** | ⭐ **用户最易犯的错，被属性拦下** |
| `TRACING=true` + 有 key | `True` | 有值 | 正常启用 |

**场景 2 是本次新增属性的核心价值**：教程那句"`TRACING=False` 或 `KEY=""` 都降级"，
在**只按 SDK 默认行为**时并不成立（§3 已说明）；本属性把它变成了真的成立。
