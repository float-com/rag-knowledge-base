## 三、第 6 章：五处装饰器

### 3.1 `chat_service.py` —— trace 树的**根 span**

```python
# 导入区（L39 / L48）
from langsmith import traceable
from app.core.observability import build_trace_url, get_current_trace_id


class ChatService:
    # 【第 9 期】trace 树的根 span：本方法是整个问答链路的入口，
    #   不装饰的话下面所有子 span 会变成互不相连的孤儿，看不到"一次问答"这个整体。
    @traceable(name="ChatService.stream_answer", run_type="chain")
    async def stream_answer(
        self, conversation_id: UUID, question: str
    ) -> AsyncIterator[dict]:
```

### 3.2 三个检索器

```python
# hybrid_retriever.py（L29 导入 / L62 装饰器）
# 【第 9 期】手动打点：本方法内部是裸 SQLAlchemy 查询，不是 LangChain 对象，
#   不装饰则 trace 树里"混合检索"这一层缺失，也看不到它耗了多久。
@traceable(name="HybridRetriever.search", run_type="retriever")
async def search(self, query: str, *, recall_top_k: int, final_top_k: int): ...


# vector_retriever.py（L22 导入 / L89 装饰器）
# 【第 9 期】手动打点：与混合检索同理，本方法走裸 SQLAlchemy。
#   它是 trace 树里 HybridRetriever 的子节点，两路并发召回因此可以分别看耗时。
@traceable(name="VectorRetriever.search", run_type="retriever")
async def search(self, query: str, top_k: int) -> list[RetrievedChunk]: ...


# keyword_retriever.py（L26 导入 / L48 装饰器）
# 【第 9 期】手动打点：与向量路对称，本方法走裸 SQLAlchemy 全文检索。
#   两路都打点后，才能对比"向量路慢还是关键词路慢"。
@traceable(name="KeywordRetriever.search", run_type="retriever")
async def search(self, query: str, top_k: int) -> list[RetrievedChunk]: ...
```

> 🎨 **树的形状**（这才是"两路都打点"的价值）：
> ```
> HybridRetriever.search
>   ├─ VectorRetriever.search    ← 含一次 embedding 网络调用，通常更慢
>   └─ KeywordRetriever.search   ← 纯数据库全文检索
> ```
> 两路是 `asyncio.gather` 并发跑的，**都打点才能看出"哪一路拖了后腿"**。

### 3.3 `reranker.py` —— 标成 `tool`

```python
# L29 导入 / L64 装饰器
# 【第 9 期】手动打点：本方法用裸 httpx 调 DashScope（qwen3-rerank 不走 OpenAI 兼容协议），
#   SDK 认不出它是模型调用，故标成 tool；不装饰则 trace 树里看不到精排耗时。
@traceable(name="Reranker.rerank", run_type="tool")
async def rerank(self, query: str, candidates: list[RetrievedChunk]): ...
```

**为什么不标 `llm`**：它虽然"用了模型"，但**调用方式是一次普通 HTTP 请求**，
不是 SDK 生态里的模型对象。标 `llm` 属于硬凑 —— 而 `run_type` **只影响 UI 图标、不影响 trace 数据**，
所以按"**它实际是什么**"如实标 `tool` 更准确。

### 3.4 `name` 参数为什么要写

教程原话：

> `name` 不写的话 SDK 会用**函数名** `stream_answer`，我们这里声明一下可读性更好。

**实际差别**：

| 写法 | LangSmith UI 上显示 |
| --- | --- |
| 不写 `name` | `stream_answer`（三个类都有 `search`，全叫 `search` 分不清） |
| 写 `name` | `ChatService.stream_answer` / `VectorRetriever.search`（带类名，一眼分清） |

> 本项目**三个检索器方法同名都叫 `search`** —— 不写 `name` 的话 UI 上会出现三个 `search`，
> 完全看不出谁是谁。**这就是 `name` 在本项目里的实际价值。**

## 四、第 7 章：`RAGState` 增加 `trace_id`

```python
    # --- 9. 可观测性 (第 9 期) ---
    # LangSmith trace_id：未启用观测 / 取不到 run tree 时为 None。
    # 【为什么必须声明在状态里】LangGraph 会静默丢弃状态模式中未声明的键 ——
    #   不写在这里，服务层塞进来的 trace_id 会在 ainvoke 之后凭空消失，且不报任何错。
    # 【为什么由服务层写、节点不写】它来自服务层 stream_answer 的运行上下文，
    #   图内节点既看不到也拿不到，全链路所有节点只是"随着状态往后传"。
    trace_id: str | None
```

| 项 | 变化 |
| --- | --- |
| 字段数 | **17 → 18** |
| 位置 | 文件末尾（L90-96），紧跟在 `user_message_id` / `assistant_message_id` 之后 |
| 文件行数 | 88 → 96 |

### ⚠️ 这一章的重点不是"加个字段"，而是"加完要**验证它没被丢掉**"

第 8 期已经实测过一条**反直觉行为**：

> **LangGraph 会静默丢弃状态模式中未声明的键** —— 不报错、不警告，数据凭空消失。

所以 `trace_id` 必须**先声明在 `RAGState` 里**，服务层塞进去的值才能在图执行后存活下来。
**否则第 8 章会撞上一个极难排查的"设了值但读出来没有"的问题。**

### 为什么由**服务层**写，而不是图内节点写

```
trace_id 的来源 = 服务层 stream_answer 的运行上下文（@traceable 的根 span）
                    ↓
        图内节点既看不到这个上下文，也不该关心它
                    ↓
        它只是"随着状态往后传"，最终由服务层取出来下发/落库
```

这与 `user_message_id` / `assistant_message_id` 是**同一类角色**：都由服务层在落库后回写，
图内节点不产出、只透传。

## 五、⭐ 一个必须先验证的风险：`@traceable` 能不能裹住**异步生成器**

### 风险是什么

`stream_answer` **不是普通协程** —— 它是 `async def` + `yield`，返回 `AsyncIterator`。
**如果装饰器把它按"协程"处理，`async for` 会直接失败** —— 那流式问答就全废了。

这是**加装饰器之前必须先排除**的风险，不能等写完再发现。

### 实测结果（专项验证）

| 验证项 | 结果 |
| --- | --- |
| 装饰后还能 `async for` 吗 | ✅ 能，分片一个不少、顺序正确 |
| 装饰后返回类型 | ✅ 仍是 `async_generator`（不是协程），有 `__aiter__` |
| 生成器**体内**能取到 `trace_id` 吗 | ✅ 能 |
| 生成器体内**抛异常**还能被捕获吗 | ✅ 正常向上抛（服务层 `except` 兜底仍有效） |
| 中途调用另一个被装饰函数，trace 还连着吗 | ✅ 同一个 trace_id |

**结论**：**可以直接用，不需要任何特殊处理。**

### 端到端真实验证（真库 + 真图 + 真模型）

装饰器全部就位后，跑一轮**真实问答**：

```
事件总数 = 9     首事件 = message_start     末事件 = message_end
message_start 载荷 = {'user_message_id': 'd8fb837c-...'}
message_end   载荷 = {'message_id': '4b9fb985-...', 'refused': False}
✅ 流式完好（首 = message_start 且末 = message_end）？ True
（临时会话已自动清理）
```

**SSE 流式的形状一点没变** —— 这是本档最关键的一条验收。

## 六、⚠️ 教程的一处自相矛盾：两个函数名混用

教程第 6 章截图里，**同一段代码出现了两个名字**：

```python
from app.core.observability import build_trace_url, get_current_trace_id   # ← 导入这个
...
build_trace_url(get_trace_id())                                            # ← 调用这个
```

**照抄会直接 `NameError`。** 因为导入的是 `get_current_trace_id`，调用的是 `get_trace_id`。

### 本项目的处理（以及一次**改名往返**，如实记录）

| 时间 | 动作 | 理由 |
| --- | --- | --- |
| 第 4 章 | 我把教程的 `get_current_trace_id` 改成 `get_trace_id` | 当时判断教程文案里的函数名是笔误 |
| **本档** | **改回 `get_current_trace_id`** | 教程正文用的是这个名字；且**此刻没有任何调用方**（第 8 章才接入），改名成本为零 |

**最终定为 `get_current_trace_id`**，与教程一致 —— 避免以后对照教程时再困惑一次。

> 📌 **教训**：跟教程对齐命名，比"我觉得哪个名字更好"更重要 ——
> 因为以后你是拿教程当参照物来读代码的。
