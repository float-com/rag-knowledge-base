## 二、对外只暴露三个符号

| 符号 | 签名 | 一句话 |
| --- | --- | --- |
| `configure_observability` | `() -> None` | 把 Settings 写进 `os.environ` |
| `get_trace_id` | `() -> str \| None` | 在函数体内取号 |
| `build_trace_url` | `(trace_id: str \| None) -> str \| None` | 拼 LangSmith 跳转链接 |

> **为什么"稳定符号"值得专门说**：
> 如果业务代码里到处写 `from langsmith import get_current_run_tree`、
> 到处 `os.environ["LANGSMITH_..."]`，那么将来 SDK 改名、换供应商、
> 或者只想加一条日志，都要改十几个文件。
> 收成一个模块后，**第三方 SDK 的细节只在一个地方出现**。
>
> 📌 **注意**：`@traceable` **不在**这个文件里 —— 它由业务代码直接从 `langsmith` 导入
> （第 6 章再加）。本模块只负责"搬运配置"和"取号"两件事。

**教程原话（三层收益）**：

```
① 记账透明：业务代码只看到 @traceable
② 隔离：langsmith 的 API 变动只影响这一个文件
③ 可测试：不开 LangSmith 时，整块逻辑可以整体替换/关闭
```

## 三、`configure_observability()` —— 把 Settings 搬进环境变量

```python
def configure_observability() -> None:
    """在应用启动时同步环境变量，单次调用即可。"""
    if settings.observability_enabled:
        os.environ["LANGSMITH_TRACING"] = "true"
        os.environ["LANGSMITH_API_KEY"] = settings.langsmith_api_key
        os.environ["LANGSMITH_PROJECT"] = settings.langsmith_project
        os.environ["LANGSMITH_ENDPOINT"] = settings.langsmith_endpoint
        logger.info(
            "LangSmith tracing enabled: project=%s endpoint=%s",
            settings.langsmith_project, settings.langsmith_endpoint,
        )
    else:
        os.environ["LANGSMITH_TRACING"] = "false"
        logger.info("LangSmith tracing disabled (no LANGSMITH_API_KEY or switch off)")
```

### ⭐ 两个非直觉的设计点

#### ① 判断依据是 `settings.observability_enabled`，而不是 SDK 自己的判定

```
若交给 SDK 自己判断（只看 TRACING）
    → "TRACING=true + key 为空" 时 SDK 认为【已启用】
    → 本地照样建 run，于是我们把 trace_id 发到前端
    → 但上报必然 401 → 前端拿到一个点不开的坏链接
```

**用我们自己的布尔值判定，就把这种"半启用"直接归为关闭。**

#### ② 关闭时**显式写 `"false"`**，而不是"什么都不写"

教程原话：这是为了**避免 SDK 默认开启时的静默上报**。

> 换个说法：**不写 = 把命运交给别人的默认值**；写了 = 我们自己说了算。

### ⏱ 时机为什么关键（lru_cache 的**缓存发生在第一次读取时**）

`langsmith/utils.py` 的 `get_env_var` 带 `lru_cache(maxsize=100)`：

```python
@functools.lru_cache(maxsize=100)
def get_env_var(name, default=None, *, namespaces=("LANGSMITH", "LANGCHAIN")):
    ...
```

> ⚠️ **一个容易读错的细节**：这个缓存**不是"模块导入时就一次性定死"**，
> 而是**某个变量名第一次被读取时**才写进缓存。
>
> 区别很关键：
> - 按"导入时缓存"理解 → 会以为只要 `import` 顺序对就行
> - 按"第一次读取时缓存"理解 → 才知道关键是 **"第一次读取"之前**必须写完

**结论**：一旦有业务代码先触发了一次 trace，这个变量就被固定为旧值，
之后再往 `os.environ` 里写也读不到了。

→ 这就是**第 5 章的位置约束**：`configure_observability()` 必须紧随日志初始化、
并且在**任何会触发 trace 的业务代码之前**执行
（注意不是"任何业务 import 之前" —— `main.py` 里的 import 本来就在 `create_app()` 之前）。

## 四、`get_trace_id()` —— 取号

```python
def get_trace_id() -> str | None:
    if not settings.observability_enabled:
        return None
    try:
        from langsmith.run_helpers import get_current_run_tree
        run = get_current_run_tree()
        if run is None:
            return None
        return str(run.trace_id)
    except Exception:
        logger.warning("get_trace_id 异常，返回 None", exc_info=True)
        return None
```

### ⭐ 三个实现细节，每个都有理由

| # | 写法 | 为什么 |
| --- | --- | --- |
| 1 | **先判 `observability_enabled`** | 未启用时连 langsmith 都不必加载，且返回值确定 |
| 2 | **延迟导入**（写在函数体内，不放模块顶部） | 未启用观测时，这个进程**根本不 import langsmith** |
| 3 | **`except Exception` + `exc_info=True`** | 见下方"fail soft" |

### 🔴 fail soft：故意吞掉所有异常

**这是与第 8 章 `AnswerVerifier` 同一条设计原则的又一次应用**：

> **可观测性是"加分项"，不是"硬依赖"。它坏了，问答必须照常返回答案。**

| 组件 | 失败方向 | 理由 |
| --- | --- | --- |
| `AnswerVerifier` | **fail-open**（异常 → 视为已校验） | 校验是加分项，不能因为它坏了就拒答 |
| **`get_trace_id`** | **返回 `None`**（异常 → 没有 trace_id） | 观测是加分项，不能因为它坏了就阻断问答 |
| `settings.observability_enabled` 配错 | 判为**关闭** | 配置错误也不抛异常，只是静默降级 |

> **共同点**：**判定"这东西坏了要不要中断主流程"时，先问它是"必需"还是"加分"。**

### ⚠️ `run.trace_id` 而不是 `run.id`

**这是我实测出来的坑**（教程给的是 `.id`）：

| 属性 | 根 span 上 | **嵌套 span 上** |
| --- | --- | --- |
| `run.id` | == trace_id | ❌ **返回那个子 span 自己的 id** |
| `run.trace_id` | == trace_id | ✅ **始终返回整棵树的 trace_id** |

**实测证据**（三个读法对比，同一个根 span 内）：

```
① 根函数体直接读        = 01a0ccc3-afc7-7401-bca0-b94643150012
② 体内经普通 helper 读  = 01a0ccc3-afc7-7401-bca0-b94643150012
③ 体经被装饰子 span 读  = 01a0ccc3-afc7-7401-bca0-b94643150012   ← 三者全一致
```

因为 `get_trace_id()` 用的是 `.trace_id`，所以在**任何嵌套层级**读都是同一个值。
**若用 `.id`，第 ③ 种情况会返回子 span 的 id** —— trace 树还是对的，
但从那个 id 在 LangSmith UI 里点进去会落在**子节点**上，不是整条链路。

> **结论**：`.trace_id` 是语义正确的那个。教程的 `.id` 在"只在根读"时恰好也对，
> 属于**歪打正着**，不要照抄。

### 函数体内 vs 函数体外（第 1 章 §3.6 的实测复核）

| 位置 | 结果 |
| --- | --- |
| `@traceable` 装饰的函数**体内** | ✅ 拿到 trace_id |
| 函数**返回之后**再调 | ❌ 返回 `None` |

**原因**：`get_current_run_tree()` 读的是"**当前执行上下文**"（contextvars），
函数返回后上下文即被清掉。

**并发下会不会串味**（实测三个请求真正交错）：

```
根 trace_id = ['01a0ccc3-b05a-...', '01a0ccc3-b05b-...', '01a0ccc3-b05b-...']
三个是否互不相同？ True
是否都不为 None？  True
```

→ **contextvars 按 asyncio 任务隔离，并发下各自拿各自的，不串味。**

## 五、`build_trace_url()` —— 拼跳转链接

```python
def build_trace_url(trace_id: str | None) -> str | None:
    if not trace_id or not settings.langsmith_run_url_prefix:
        return None
    return f"{settings.langsmith_run_url_prefix.rstrip('/')}/runs/{trace_id}"
```

| 细节 | 理由 |
| --- | --- |
| 两个条件都判（`trace_id` **和** 前缀） | 任一缺失都拼不出可用链接 |
| 返回 **`None`** 而不是空串 | 前端 `chatStream.ts` 用的是 `??`（只兜 `null`/`undefined`），**空串会原样透传**，反而让前端以为有链接 |
| `rstrip("/")` | 前缀末尾带不带斜杠都能拼对，避免 `//runs/` 双斜杠 |

**实测**（前缀末尾**故意带一个斜杠**）：

```
输入：https://smith.langchain.com/o/abc-123/projects/p/rag-knowledge-base/
输出：https://smith.langchain.com/o/abc-123/projects/p/rag-knowledge-base/runs/01a0ccc1-...
                                                              ↑ 没有双斜杠
```

## 六、第 5 章：启动时接入（`main.py`）

```python
# 导入可观测性初始化：把 Settings 里的 LangSmith 配置同步写入 os.environ
from app.core.observability import configure_observability


def create_app() -> FastAPI:
    # 第一步：初始化日志系统
    configure_logging()

    # 第一步之二：初始化可观测性（第 9 期）
    configure_observability()

    logger = get_logger(__name__)
```

**教程原话**：

> 顺序要在 `configure_logging` 之后、**其它任何业务模块 import 之前**，
> 确保 LangSmith SDK 一旦被业务代码触发就能读到正确的环境变量。

### 为什么放在 `create_app()` 里就够安全

`main.py` 的最后一行是 `app = create_app()` —— 它在**模块被 import 的那一刻**就执行。
而 Uvicorn 是 `from app.main import app` 才拿到 ASGI 实例，所以：

```
Uvicorn 启动 → import app.main → app = create_app() → configure_observability()
                                                      ↓
                                          之后才开始处理任何 HTTP 请求
```

**任何业务代码都在 `create_app()` 之后才被触发**，因此这个位置是安全的。

> 📌 **对照本项目既有做法**：`setup_hf_environment()` 被单独放在 **`main.py` 最顶部
> （所有业务 import 之前）**，因为 `huggingface_hub` 是**在 import 阶段**就读变量。
> LangSmith 的读取发生在**运行时**，所以放在 `create_app()` 里就足够 ——
> **同样是"搬运环境变量"，但两者的时间窗口不一样。**

### 这一步之后，什么已经自动生效了

教程原话：

> 到这一步，LangChain 的 `ChatOpenAI` 和 LangGraph 的 `StateGraph.ainvoke`
> 已经能自动出现在 trace 树里了。

也就是第 1 章图二里**蓝色的那几个框**（自动捕获层）：

| 自动捕获对象 | 本项目对应 |
| --- | --- |
| `ChatOpenAI` 调用 | `stream_generate` 内部的 `get_chat_model().astream(...)` |
| `ChatOpenAI` 调用 | `AnswerVerifier.verify` 内部、`AgentPlanner.plan` 内部 |
| `StateGraph.ainvoke` | `chat_service.stream_answer` 里的 `get_rag_graph().ainvoke(state)` |

**而这些还看不到**（需要第 6 章手动加 `@traceable`）：

| 需要手动打点 | 为什么 SDK 看不到 |
| --- | --- |
| `stream_answer` | 是普通 Python 方法，不是 LangChain 对象 |
| `load_context` | 内部是裸 SQLAlchemy 查库 |
| `HybridRetriever.search` / `VectorRetriever` / `KeywordRetriever` | 内部是裸 SQLAlchemy |
| `Reranker.rerank` | 内部是裸 `httpx`（`qwen3-rerank` 不走 OpenAI 兼容协议） |

## 七、把三章连起来：配置生效链

```
.env / 环境变量
    ↓ pydantic-settings 读取（extra="ignore" 只吸收已声明的键）
Settings 对象（config.py，L219-229）
    ↓ observability_enabled 把"开关 + key"合成一个布尔（config.py，L231-240）
    ↓ configure_observability() 显式搬运（observability.py，L28-58）
os.environ["LANGSMITH_*"]
    ↓ SDK 的 get_env_var() 读取（带 lru_cache，所以时机敏感）
LangSmith 开始真正上报
    ↓ get_trace_id() 在函数体内取号（observability.py，L59-87）
业务代码拿到 trace_id → 下发给前端 + 落库（第 6/7 章）
```

> **这张链里任何一环断掉，症状都是"配了但没生效"**：
> ① 只写 `.env` 不搬运 → SDK 完全不知情；
> ② 搬运了但时机太晚（业务先跑了） → lru_cache 已经缓存了旧值；
> ③ 开关开了但 key 空 → 本地有 run、上报 401、前端拿到坏链接。

## 九、教程之外的偏差说明

| # | 教程写法 | 本项目 | 原因 |
| --- | --- | --- | --- |
| 1 | 用 `run.id` | 改用 **`run.trace_id`** | `.id` 在嵌套 span 上会返回子节点 id（实测） |
| 2 | `logger.warning("get_current_trace_id 异常…")` | 改为 `"get_trace_id 异常…"` | 教程文案里的函数名与实际函数名不符（笔误） |
| 3 | `try/except ImportError` 包 import | 直接 `from langsmith.run_helpers import ...` | 实测 `langsmith.run_helpers` 与顶层 `langsmith` 暴露的是**同一个函数对象**，无需回退分支 |
| 4 | "模块导入时缓存环境变量" | 改为"**第一次读取时缓存**" | 缓存挂在 `get_env_var()` 上，语义与时机判断都不同 |
| 5 | "任何具体业务 import 之前" | 改为"**任何会触发 trace 的业务代码之前**" | `main.py` 里的业务 import 本来就在 `create_app()` 之前，按原文读自相矛盾 |

> 偏差 1 是**行为正确性**问题；2/3 是文案与冗余；4/5 是**注释精确性**（不改代码行为，但影响后人理解）。
