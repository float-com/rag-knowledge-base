## 二、`config.py` 的新增内容

### 2.1 Reranker 段（L181-204）

```python
    # ===== Reranker（DashScope qwen3-rerank，第 8 章）=====
    # 关掉后 rerank 节点直接透传，作为「有 / 无精排」的对比开关。
    #   与 agent_loop_enabled / query_route_enabled 同一思路：
    #   给一条"退化回上一期行为"的退路，才能量化"精排到底带来了多少提升"。
    rerank_enabled: bool = True                                            # L185
    # DashScope rerank 端点：不是标准 OpenAI API。
    #   【为什么端点路径不同】OpenAI 兼容协议里没有 rerank 这一类接口，
    #   百炼为精排单独提供了 /api/v1/services/rerank/... 形态的端点，
    #   因此不能复用 embedding_base_url / chat_base_url 那两个 compatible-mode 地址。
    rerank_base_url: str = (                                               # L190
        "https://dashscope.aliyuncs.com/compatible-api/v1/reranks"         # L191
    )
    rerank_model: str = "qwen3-rerank"                                     # L193
    # 留空时复用 chat_api_key（同一份 DashScope key，避免重复配置）。
    #   实际取值请用下面的 effective_rerank_api_key 属性，不要直接用本字段。
    rerank_api_key: str = ""                                               # L196
    # rerank Top1 相关度阈值：低于此值视为"上下文不足"由 judge_context 触发拒答。
    #   【⚠️ 为什么必须与 retrieval_min_score 分开】：
    #   qwen3-rerank 输出的是 relevance_score ∈ [0, 1]（精排模型给出的成对相关性），
    #   而 retrieval_min_score 比较的是 embedding 余弦相似度 —— 两者【量纲不同、不可比】。
    #   0.3 是经验值：精排分整体偏高，若沿用 0.6 会导致拒答几乎不触发。
    rerank_min_score: float = 0.3                                          # L202
    # 请求超时（秒）：rerank 是同步调用主链路，超时短路比拖慢回答更好。
    rerank_timeout: float = 8.0                                            # L204

    # ===== 答案校验（第 8 章）=====
    # 关掉后跳过 verify_answer 调用，方便对比"有 / 无引用支撑校验"的效果。
    verify_answer_enabled: bool = True                                     # L208
```

**字段清单**：

| 字段 | 类型 | 默认值 | 作用 |
| --- | --- | --- | --- |
| `rerank_enabled` | `bool` | `True` | **对比开关**：关掉后 rerank 节点直接透传 |
| `rerank_base_url` | `str` | `.../compatible-api/v1/reranks` | 精排端点（**非 OpenAI 兼容协议**） |
| `rerank_model` | `str` | `qwen3-rerank` | 模型名 |
| `rerank_api_key` | `str` | `""` | 留空时**回落**到 `chat_api_key` |
| `rerank_min_score` | `float` | `0.3` | **精排分**拒答阈值 |
| `rerank_timeout` | `float` | `8.0` | 同步调用超时 |
| `verify_answer_enabled` | `bool` | `True` | 答案校验开关 |

### 2.2 `effective_rerank_api_key` 属性（L211-214）

```python
    @property
    def effective_rerank_api_key(self) -> str:                             # L212
        """rerank_api_key 留空时回落到 chat_api_key。二者本来就是同一份 DashScope key。"""
        return self.rerank_api_key or self.chat_api_key                     # L214
```

**与本文件既有两个属性同一风格**（`cos_configured` L69 / `cors_origin_list` L83）：

| 属性 | 作用 |
| --- | --- |
| `cos_configured` | 检测 COS 三要素凭据完整性 |
| `cors_origin_list` | 把逗号分隔的 CORS 字符串拆成标准源列表 |
| **`effective_rerank_api_key`** | **把"留空回落"逻辑收敛到一处** |

**⭐ 为什么用属性而不是在调用处写 `settings.rerank_api_key or settings.chat_api_key`**：

```
① 回落逻辑只写一遍 —— 若将来改成回落别的 key，只改这一处
② 调用方（reranker 客户端）不需要知道"回落"这件事存在
③ 【关键】若在字段上直接写默认值 = chat_api_key 会不行：
   pydantic 的字段默认值在类定义时求值，那时 chat_api_key 还没从 .env 读进来
   → 必须用【运行时属性】才能在读取 .env 之后计算
```

**实测两种情形**：

```
情形 A（未显式配置）：
  chat_api_key   = 已设置(116 位)
  rerank_api_key = 「空」
  → effective    = 已回落到 chat_api_key(116 位)   ✓

情形 B（显式配置）：
  Settings(rerank_api_key="sk-explicit-test")
  → effective    = sk-explicit-test                ✓ 优先用自己的
```

### ⚠️ 两个文件格式细节（追加时踩到的）

| 文件 | 编码 | 换行 | 结尾 |
| --- | --- | --- | --- |
| `.env` | UTF-8 **无 BOM** | **CRLF** | **末尾有空行** |
| `.env.example` | UTF-8 **无 BOM** | **CRLF** | **末尾无换行** |

**为什么要注意**：

```
① 用 PowerShell 的 Get-Content 读这两个文件会显示乱码 —— 那是【控制台解码问题】，
   不是文件问题。用 Python 以 utf-8 读就完全正常。
   （本批我一度以为文件是 GBK，实测 utf-8 解码成功、gbk 解码失败，才确认是 UTF-8）

② .env.example 末尾无换行，直接拼接会导致新段第一行与旧内容黏在同一行
   → 追加前必须先补一个换行

③ 两者用 CRLF，追加的内容也必须用 CRLF，否则一个文件里混两种换行
```

**`.env` 被 gitignore**（`.gitignore` 里有 `.env`、`.env.*`、但 `!.env.example` 例外）→ **只有 `.env.example` 会提交**。

2. **印证 `rerank_min_score = 0.3` 是合理经验值** —— **不相关的全部压在 0.3 以下**，阈值恰好切在空隙里

### 4.2 ⚠️ 载荷格式：**顶层扁平，不是嵌套**

**试错记录**（供第 2 章避免重复踩坑）：

| # | 端点 | 载荷 | 结果 |
| --- | --- | --- | --- |
| **A** | `compatible-api/v1/reranks` | **顶层扁平 `query` + `documents`** | ✅ **200** |
| B | `compatible-api/v1/reranks` | `input: {query, documents}` 嵌套 | ❌ 400 `Field required: input.query` |
| C | `compatible-mode/v1/reranks` | — | ❌ 404 |
| D | `services/aigc/text-rerank/text-rerank` | 任意 | ❌ 400 `url error` |
| E | `services/rerank/text-rerank/text-rerank` | `input` 嵌套 | ✅ 200（DashScope **原生**写法） |

**官方文档确认**（[重排序 Reranking API](https://help.aliyun.com/zh/model-studio/rerank)）：OpenAI 兼容端点的请求体就是**顶层扁平**：

```bash
curl --request POST \
  --url https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-api/v1/reranks \
  --data '{
    "model": "qwen3-rerank",
    "query": "什么是重排序模型",
    "documents": ["...", "...", "..."],
    "top_n": 2
}'
```

**⚠️ 注意**：`input: {query, documents}` 嵌套格式是给**多模态精排**（`qwen3-vl-rerank`）用的，**文本精排不要用嵌套**。

### 4.3 ⭐ 端点契约（第 2 章实现的依据）

```
【请求】POST {rerank_base_url}
Headers: Authorization: Bearer {effective_rerank_api_key}
         Content-Type: application/json
Body:    {"model": "qwen3-rerank",
          "query": "<用户问题>",
          "documents": ["<候选1>", "<候选2>", ...],
          "top_n": <可选，只返回前 N 条>}

【响应】200
{"object": "list",
 "results": [{"index": <原数组下标>, "relevance_score": <float 0-1>}, ...],
 "model": "qwen3-rerank",
 "usage": {"total_tokens": <int>}}
```

**⭐ 实现时最关键的一点**：

```
results 里的 index 是【原 documents 数组里的下标】
results 已按 relevance_score 【降序】返回

→ 客户端必须靠 index 把分数【写回原来的 RetrievedChunk】
   不能靠顺序对应！因为返回的是重排后的顺序

错误做法：for i, r in enumerate(results): chunks[i].rerank_score = r.score
          ↑ 这样会把"最相关的分数"赋给"原来的第一条"
正确做法：chunks[r["index"]].rerank_score = r["relevance_score"]
```

**其他可选参数**（本期不用，但记录）：

| 参数 | 作用 |
| --- | --- |
| `instruct` | 切换排序策略（**须用英文**）：默认"问答检索"，可改成 `"Retrieve semantically similar text."`（语义相似度，适合 FAQ 场景） |
| `top_n` | 只返回前 N 条；不设则返回全部 |

**模型限制**（`qwen3-rerank`）：最大文档数 **500**、单条最大 Token **4000**、单次请求最大 Token **120000**（本项目的 20 条候选远低于上限）。
