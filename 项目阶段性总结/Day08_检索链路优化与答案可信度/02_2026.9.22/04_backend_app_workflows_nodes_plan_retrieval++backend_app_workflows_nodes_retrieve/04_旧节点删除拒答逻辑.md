### 2.3 ⭐ 为什么要放大

```
改造前：retrieve 召回 20 → 融合后【按 RRF 分截断到 5】→ 交给后续
改造后：retrieve 召回 20 → 【不截断】→ 交给 rerank 精排 → 由精排裁到 5
```

**核心原因**（本章的核心设计思想）：

```
截断需要一个"相关性"判据
    召回阶段手里只有 RRF 融合分
        RRF 分 = Σ 1/(k + rank)，上限仅 2/(k+1) ≈ 0.033
        它只反映"在两条腿里都排前面"，【不反映真实相关性】
    精排阶段用成对打分给出【绝对相关性】
        → 这时候截断才站得住脚

若 retrieve 先裁到 5：
    精排只能在 5 条里排序
    → 召回阶段漏掉的，精排永远救不回来
    → 精排的价值被"上游的天花板"锁死
```

### 2.5 顺带一个「第 7 期修正」也随之失效

第 7 期曾发现一个**跨轮状态残留 bug**并修过：

```python

    #    【为什么"不拒答"时也要显式写空串】：
    #    Agentic 循环里本节点会被执行多轮，而 LangGraph 的状态是【跨轮累积】的 ——
    #    若第 1 轮熔断写了拒答文案、第 2 轮不熔断却不覆盖它，
    #    这段上一轮的文案就会残留在 state 里，最终出现

```

```
    → 不存在"上一轮的文案残留到下一轮"
```

**⭐ 这是一次"用重构消除 bug 成因"，而不仅是"修 bug"** —— 值得记下来。

### 3.2 改造后

```python

    #    文案由 refuse 节点统一输出（第 8 期收敛），本节点只声明"该走拒答出口了"。
    #    图的条件边 _after_plan 会读到 action == "refuse"，把控制权交给 refuse 节点。
    #    【为什么这样可以】服务层按 state["refused"] 分流，而文案由 refuse 节点写入，
    #    两者最终都会落到 state 上，不存在"标记了却没文案"的窗口。

    return update
```

### 3.3 ⭐ 为什么"只写标记"就够 —— 控制流与文案各归其位

**完整链路**：

```python
# ① plan_retrieval 只声明意图
    if decision.action == "refuse":
        update["refused"] = True

# ② 图的条件边读到意图 → 把控制权交给 refuse 节点
def _after_plan(state: RAGState) -> str:
    if state.get("agent_steps"):
        last_action = state["agent_steps"][-1].get("action")
        if last_action == "refuse":
            return "end"          # Δ 第 6 章要改成指向 "refuse" 节点

# ③ refuse 节点写文案
async def refuse(state: RAGState) -> RAGState:
    return {"refused": True, "answer": REFUSAL_ANSWER}
```

**⭐ 注意条件边读的是 `agent_steps[-1]["action"]`，而不是 `state["refused"]`**：

```
控制流依据：agent_steps 里的决策记录（plan_retrieval 刚追加的那条）
文案来源  ：refuse 节点的返回值

两条信息各归其位
→ plan_retrieval 不需要越权写文案
```

### 3.4 ⚠️ 那 `update["refused"] = True` 为什么保留

```
服务层是按 state["refused"] 分流的（chat_service）：
    if state.get("refused"):
        yield {"event": "token", "data": {"delta": state["answer"]}}   ← 直接下发预置文案
    else:
        async for delta in stream_generate(state): ...                 ← 调模型

所以 refused 标记必须有人写：
    plan_retrieval 先写（声明意图）
    refuse 节点再写一次（幂等，值相同）
```

**两处都写 `refused=True` 不冲突** —— 结果一致，且无论走哪条路径它都被置上。

## 六、问题解析（承接上一章的 Q4 / Q5）

### Q4　`retrieve` 口径放大遵循什么设计？

**参考答案**：

```
retrieve：宁滥勿缺 —— 让 rerank 有【足量】候选可挑
rerank  ：宁缺勿滥 —— 有了绝对相关性才敢裁
```

**核心原因**：

```
retrieve 融合后按【RRF 融合分】降序截断到 5
    RRF 分上限仅 2/(k+1) ≈ 0.033，只反映"在两条腿里都排前面"
    → 第 6 名之后可能有一条"真正回答了问题"的切片，因 RRF 排序被切掉
    → 而精排的成对打分本可以把它捞上来

若 retrieve 先裁到 5：召回阶段漏掉的，精排永远救不回来
```

| 作答 | 结果 |
| --- | --- |
| "放大遵循宁滥勿缺设计…不放大优质语义会被一刀切，精排优化很有限" | ✅ 正确 |

### Q5　`plan_retrieval` 的 `refuse` 分支为什么只写 `refused=True`、不写 `answer`？

**参考答案**：

```
图的条件边 _after_plan 读的是 agent_steps[-1]["action"] == "refuse"
    → 它据此把控制权交给 refuse 节点
    → refuse 节点写 answer

所以 plan_retrieval 只需要"声明意图" —— 控制流与文案各归其位
```

**⚠️ `update["refused"] = True` 保留**：服务层按 `state["refused"]` 分流。

> **⭐ 本章还有一个"意外收获"**：第 7 期曾修过一个"跨轮答案残留"bug（`retrieve` 第 1 轮写了拒答文案、第 2 轮不覆盖），
