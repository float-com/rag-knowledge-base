## 三、密码哈希：`hash_password` / `verify_password`

### 3.1 bcrypt 哈希串的解剖

```
$2b$ 12$ fHiy/y8NTvUYrM9RDgCen. eo04BOcDP8HGXg0RYa7pSTdwZECAdXK
 │    │  └────── 22 字符 ──────┘ └──────── 31 字符 ────────┘
 │    │        随机盐                 摘要
 │    └── cost（工作因子）= 12
 └── 算法版本标识
                      总计 60 字符
```

**关键：盐和 cost 都被写进了哈希串本身**，所以不需要单独的盐字段。
这也解释了为什么 `checkpw` 只需要两个参数（明文 + 哈希串）就能完成校验。

### 3.2 为什么要"故意算得慢"

| 哈希 | 单次耗时 | 攻击者每秒可试 | 用途 |
| --- | --- | --- | --- |
| MD5 / SHA256 | **微秒级** | **上亿次**（GPU） | ❌ 绝不能用来存密码 |
| **bcrypt cost=12** | **本机实测 267ms** | **约 3 次** | ✅ 登录接口 |

- **对登录接口完全无感**：人一次只登一次，267ms 察觉不到
- **对暴力枚举致命**：跑一万个常见密码约需 **45 分钟**（单线程）
- **cost 可随算力上涨而上调** —— 这是它比"固定轮数"算法强的地方

### 3.3 随机盐 vs 固定盐

```
❌ 固定盐：一锅出 —— 张三李四密码一样，密文就一样，破一个全玩完
✅ 随机盐：一人一配方 —— 密码相同、密文也完全不同，黑客只能挨个死磕
```

**盐写在串里不怕被看**：它不是密钥，只是让每人的密文独一无二，
并留着下次登录比对用。

实测已确认：**同一密码两次 `hash_password` 得到两个不同的串，但都能校验通过**。

### 3.4 `checkpw` 怎么做到的（实测验证）

```
1. 从 hashed 串里【读出当时保存的 salt 和 cost】
2. 用同一配方把 plain 重新算一次哈希
3. 与串尾的摘要比对
```

**第 1 步是实测证实的**（这点很容易被误解为"用固定 cost 再算一遍"）：

| 哈希串的 rounds | checkpw 耗时 |
| --- | --- |
| `$2b$12$`（cost=12） | **208 ms** |
| `$2b$10$`（cost=10） | **50 ms** |

相差约 **4 倍**（2²=4，正好对应 cost 每 +1 迭代翻倍），
证明它确实**读了串里记录的 cost**，而不是用固定值。

## 四、JWT：`create_access_token` / `decode_access_token`

### 4.1 三个标准声明（RFC 7519）

| 声明 | 含义 | 本项目 |
| --- | --- | --- |
| `sub` | subject：这个令牌代表谁 | `user_id` 的字符串形式 |
| `iat` | issued at：签发时刻 | 审计留痕用，**不参与有效性判断** |
| `exp` | expiration：过期时刻 | **JWT 唯一的自动失效机制** |

### 4.2 为什么必须强制带 `exp`

```
JWT 是【无状态】的 —— 服务端不保存"已签发了哪些令牌"
        ↓
因此在不引入 Redis 黑名单的前提下，服务端【在物理上无法主动吊销】单个令牌
        ↓
exp 是唯一的兜底防线 —— 宁可让用户每天重登一次，
也不能签发"永不过期"的令牌
```

### 4.3 三段式结构与底层做了什么

```
Header . Payload . Signature
   │         │          │
   │         │          └─ HMAC-SHA256(Header + "." + Payload, jwt_secret)
   │         └─ {"sub":"...","iat":...,"exp":...} 的 Base64URL
   └─ {"alg":"HS256","typ":"JWT"} 的 Base64URL
```

> ⚠️ **Payload 只做了 Base64URL 编码，没有加密** —— 任何人拿到令牌都能解出 `sub`。
> 签名保证的是**不可篡改**，不是**不可读**。这是 JWT 的常识，容易忘。

### 4.4 `decode_access_token` 做了四件事

| 步骤 | 内容 | 谁负责 |
| --- | --- | --- |
| 1 | **配置安全防线** | 本函数（`jwt_configured` 守卫） |
| 2 | **签名 / 时效 / 算法白名单** 三项核验 | PyJWT 的 `jwt.decode` 自动接管 |
| 3 | **异常转译**（区分过期与无效，`from exc` 保留异常链） | 本函数 |
| 4 | **载荷防御性核验**（`sub` 必须是非空字符串） | 本函数 |

**第 2 步是"免费"的**：`jwt.decode` 默认就校验 `exp`（实测确认，过期抛 `ExpiredSignatureError`），
因此**不需要手写时间比较** —— 手写反而容易漏掉时钟偏移等边界。

**第 4 步为什么必要**：`jwt.decode` 只证明"该令牌由本服务端合法签发且未被修改"，
**不保证业务字段齐全**。一个签名合法但没带 `sub` 的令牌，若不拦，
下游就会拿着 `None` 去查库。实测三种畸形 `sub` 都被拦住了（见 §六）。

### 4.5 异常映射表（8 种输入 → 结果）

| # | 输入 | PyJWT 抛什么 | 本项目转成 | 提示文案 |
| --- | --- | --- | --- | --- |
| 1 | 正常令牌 | — | 返回 `sub` | — |
| 2 | 已过期 | `ExpiredSignatureError` | `UnauthorizedError` | 登录已过期，请重新登录 |
| 3 | 签名被篡改 | `InvalidTokenError` | `UnauthorizedError` | 无效的访问凭证 |
| 4 | 乱码串 | `InvalidTokenError` | `UnauthorizedError` | 无效的访问凭证 |
| 5 | 空串 | `InvalidTokenError` | `UnauthorizedError` | 无效的访问凭证 |
| 6 | 别的密钥签的 | `InvalidTokenError` | `UnauthorizedError` | 无效的访问凭证 |
| 7 | 签名合法但**缺 `sub`** | 不抛（签名有效） | `UnauthorizedError` | 无效的访问凭证 |
| 8 | 签名合法但 `sub` 是**数字** | 不抛 | `UnauthorizedError` | 无效的访问凭证 |

> ⚠️ `ExpiredSignatureError` **是** `InvalidTokenError` 的子类，
> 所以只写一个 `except InvalidTokenError` 也能跑通。
> 拆开写的唯一目的是**让提示文案准确**（"该重登了" vs "这凭证有问题"），
> 不是为了技术上的必须。

## 五、异常契约：401 vs 403

本节新增 `UnauthorizedError`，与既有的 `PermissionDeniedError` 构成一对**最容易写错**的搭档。

| | `UnauthorizedError`（**本节新增**） | `PermissionDeniedError`（**早已存在**） |
| --- | --- | --- |
| 状态码 | **401** | **403** |
| `code` | `"unauthorized"` | `"permission_denied"` |
| 默认 `message` | `"请先登录"` | `"无权访问该资源"` |
| 语义 | **"你是谁"没证明成功** | **身份已证明，但权限不够** |
| 触发例 | 没带 token / 过期 / 签名不对 / 用户停用 | 普通用户访问 `/api/users` |
| 前端约定 | **清登录态 + 跳 `/login`** | **只提示"无权限"，不跳登录页**（重登也没用） |

> 🔴 **一句话**：**401 = "请先去登录"，403 = "登录了也没你的份"。**
> 两者必须是**不同的前端分支** —— 混在一起会让用户反复重登却依然无权限。

### 6.1 密码哈希（8/8 + 形态检查）

| 验证项 | 结果 |
| --- | --- |

### 7.2 ⚠️ 未处置：缺配置时返回 401，语义是错的

```python
if not settings.jwt_configured:
    raise UnauthorizedError("服务端未配置 JWT secret，无法签发 token")   # ← 401
```

**"服务端自己没配密钥"本质是服务端配置故障，本该是 503**（与既有 `ConfigurationError` 一致），
而 401 的语义是"**你**没证明成功"。

**副作用链**：

```
JWT_SECRET 没配 → 登录接口返回 401
        ↓
前端收到 401 → 清登录态 + 跳 /login（这是 401 的正确约定）
        ↓
用户重新登录 → 又是 401 → 再跳登录页 …… 【重登死循环】
        ↓
而真正的病因（服务端缺配置）一个字都不会提示出来
```

**当前选择**：**只记录、不改**（用户明确说"先不管"）。已在此处代码注释里标注为
「已知语义瑕疵，待收尾决定」。修法很简单：把这两处 `UnauthorizedError` 换成 `ConfigurationError`。
