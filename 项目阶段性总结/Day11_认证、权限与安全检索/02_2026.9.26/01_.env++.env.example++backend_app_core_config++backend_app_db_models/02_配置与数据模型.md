## 三、第 1 步：依赖与配置项

### 3.1 依赖：为什么是这两个

```
PyJWT 2.15.0     ← 只做 JWT 编解码，无多余抽象（Auth0 团队维护）
bcrypt 5.0.0     ← 直接用 bcrypt 库，【不引 passlib】
```

> ## ⚠️ 为什么不装 passlib
> `passlib` 1.7.4 会去读 `bcrypt.__about__.__version__`，而 **`bcrypt>=4.1` 已移除该属性**，
> 会抛 `AttributeError` 并降级成一条很难懂的 `TrappedError`。
> 本期只需要 `hashpw` / `checkpw` / `gensalt` 三个函数，直接用 `bcrypt` 少一层依赖。

### 3.2 配置项：6 个字段 × 3 处同步

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| `jwt_secret` | `""`（**故意留空**） | HMAC 签名密钥，生成示例 `openssl rand -hex 32` |
| `jwt_algorithm` | `"HS256"` | HMAC-SHA256，单服务自签自验足够 |
| `jwt_expire_minutes` | `1440` | 24 小时 |
| `default_admin_username` | `"admin"` | 首次启动的种子管理员 |
| `default_admin_password` | `"admin"` | 同上 |
| `default_admin_display_name` | `"管理员"` | 同上 |

**两个设计取舍**：

| 取舍 | 理由 |
| --- | --- |
| **密钥留空而不是给个默认串** | 给默认值最危险 —— 生产环境忘了改，等于用一个**人人皆知的值**签发令牌，任何人都能伪造 admin 的 JWT。留空 + 启动告警，把问题暴露在启动阶段 |
| **种子管理员可以长期留在配置里** | 它的逻辑是"库里已有用户时跳过"，所以无害。它的作用是打破死锁：**没有 admin 就无法创建用户，没有用户就无法创建 admin** |

**除了教程那 6 个字段，我多加了两个成员**（属教程留空）：

```python
@property
def jwt_configured(self) -> bool:
    """与 cos_configured / observability_enabled 同一思路：
    把'是否真的可用'收敛成一个布尔状态，避免散落书写 if settings.jwt_secret。"""
    return bool(self.jwt_secret)

def warn_if_jwt_unconfigured(self) -> None:
    """启动自检：密钥缺失时打 ERROR 告警，但【不抛异常、不阻断启动】。"""
```

> 教程只写了"为空时启动期打 ERROR 告警但不阻断"，**没写这个告警在哪打**。
> 为什么选告警而不是 `raise ConfigurationError`：本项目其它模块（COS / LangSmith）
> 缺配置是"降级"，但 JWT 缺配置**无法降级**（会让所有登录失败）。
> 若在这里 raise，学员在还没学到"配密钥"这一步时就完全起不来。

## 四、第 2 步：数据模型

### 4.1 三张新表

| 表 | 列 | 要点 |
| --- | --- | --- |
| `roles` | `id` PK、`name` **UK**、`description`、`permission_tags` **TEXT[]**、`created_at` | 角色名唯一 |
| `users` | `id` PK、`username` **UK**、`password_hash`、`display_name`、`status`、`created_at` | 登录名唯一 |
| `user_roles` | `user_id` PK+FK、`role_id` PK+FK | **复合主键、无业务字段**，纯关系 |

**三处实现细节值得记**：

| 细节 | 写法 | 为什么 |
| --- | --- | --- |
| `user_roles` 用 **Core `Table`** 而不是 ORM 类 | `Table("user_roles", Base.metadata, Column(...), Column(...))` | 它没有任何业务字段，纯关系。用 `Table` 让 SQLAlchemy 自动处理中间表，省掉一个空壳模型类 |
| 两边外键都是 `ondelete="CASCADE"` | `ForeignKey("users.id", ondelete="CASCADE")` | 用户或角色被硬删时，关**联行本身没有保留价值**，应当一并消失（对比 `documents.created_by` 用的是 `SET NULL`） |
| `permission_tags` 的双默认值 | `default=list, server_default="{}"` | `default` 管 **ORM 新建对象**；`server_default` 管 **DDL 默认值与已有行回填**。两者都要 |

### 4.2 两张已有表加列

```python
# Document（加在 error_message 之后）
permission_tags: Mapped[list[str]] = mapped_column(
    ARRAY(String()), nullable=False, default=list, server_default="{}")
created_by: Mapped[UUID | None] = mapped_column(
    PGUUID(as_uuid=True), ForeignKey("users.id", ondelete="SET NULL"), nullable=True)

# Conversation（替换掉那行"预留 user_id"的注释）
user_id: Mapped[UUID | None] = mapped_column(
    PGUUID(as_uuid=True), ForeignKey("users.id", ondelete="SET NULL"),
    nullable=True, index=True)
```

| 列 | 为什么这么设计 |
| --- | --- |
| `documents.permission_tags` + `server_default="{}"` | **空数组 = 公开**。前 10 期上传的存量文档没有标签，若把空数组当"谁都不能看"，这次升级会让所有历史文档**瞬间失联**。用 DDL 默认值把旧行一次性填成空数组，正好对应默认公开 |
| `documents.created_by` → **SET NULL** | 用户被硬删后置 NULL，但**文档本身保留**供管理员审计 —— 而不是把整份文档连同切片一起级联删掉。注意它与 `permission_tags` 职责完全不同：**前者管"谁传的"（审计），后者管"谁能看"（可见性）** |
| `conversations.user_id` → **SET NULL** + `index=True` | 会话列表是最高频查询之一，条件恒定带 `user_id = ?`，没索引就会全表扫描。存量会话加列后为 NULL，它们不会出现在任何普通用户的列表里 |
| 新增 `Document.creator` / `Conversation.user` 关系 | 教程只加列、不加关系。我加了单向关系（**User 侧不加反向属性**），供审计展示 |

> ⭐ **`Conversation.user_id` 其实是 Day04 就留好的口子**：
> 原代码在此处只有一行注释「预留 user_id 字段，后续引入用户体系时可平滑扩展」。
> 本期把它正式落地。

### 5.1 GIN 索引：为什么它必须同时写在模型里

教程的做法是**手工往迁移里插一句** `op.execute("CREATE INDEX ... USING GIN")`。
本项目的做法是**在 `Document.__table_args__` 里声明**，让 autogenerate 生成。

```
❌ 只在迁移里 CREATE INDEX，模型不声明：
   模型 metadata 里没有这个索引
        ↓
   Alembic 自动比对时把它当成"数据库里多出来的对象"
        ↓
   下一次 autogenerate 生成 DROP INDEX，把它误删
        ↓
   权限过滤从"毫秒级索引扫描"退化成"顺序扫描"
```

本模块头部本来就有这条既有约定（第 10 期给 `DocumentChunk` 补 GIN / HNSW 时踩过同一个坑）：

> 「索引显式声明：写在 `__table_args__` 里。**必须如此** —— 模型侧不声明时，
> Alembic 自动比对看不见这两类索引，每次 autogenerate 都会生成 `drop_index` 把它们误删。」

### 5.2 可逆迁移：两处手工加固

| 加固 | autogenerate 原样输出 | 本项目 | 不改会怎样 |
| --- | --- | --- | --- |
| **外键命名** | `op.create_foreign_key(None, ...)` | `'documents_created_by_fkey'` / `'conversations_user_id_fkey'` | 本项目 `alembic/env.py` **没有配置 `naming_convention`**，`None` 会让 downgrade 的 `drop_constraint(None, ...)` 直接报错 |
| **downgrade 顺序** | `drop_table('users')` 排在两个外键删除**之前** | `users` **最后**删 | 那两个外键正指向 `users`，PostgreSQL 因依赖拒绝 → downgrade 跑不通 |

> ✅ 已实测：修正后 `uv run alembic downgrade -1` **一次通过**，
> 库干净回到 9 张表 / `d454894ea042`。

## 六、⚠️ 本节最重要的一个发现

### 「空数组 = 公开」**不能靠 `&&` 实现**

教程原文：

> 「文档的 `permission_tags = '{}'`（空数组）**是公开**，任何登录用户都能看。」

第 2 步建完表后用真库验证时发现 —— `&&` 的语义是**双方都必须有元素可重叠**：

```sql
-- PostgreSQL 16 实测
SELECT ... WHERE permission_tags && '{}'::varchar[];   -- 返回 0 行！
```

**空数组与任何东西都不重叠，包括另一个空数组。** 所以如果只写成教程字面的
`WHERE permission_tags && :user_tags`，后果是：

| 用户 | 裸 `&&` 的后果 |
| --- | --- |
| 有 `hr` 标签 | 只看到 HR 文档，**公开文档看不到** |
| **无任何角色**（标签为空） | **一篇都看不到** —— 存量 10 篇全体失联 |

> 🔴 **正确口径必须显式加一个 OR 分支**：
> ```sql
> WHERE permission_tags && :user_tags
>    OR permission_tags = '{}'        -- 公开文档人人可见
> ```

### 实测证据（真库）

| 口径 | HR 用户 `&& ['hr']` | 销售用户 `&& ['sales']` | 无角色 `&& []` |
| --- | --- | --- | --- |
| **裸 `&&`** | 只命中 HR 系 | 只命中销售系 | **0 篇**（连公开都看不到） |
| **`&& ... OR = '{}'`** | HR 系 + 公开 ✅ | 销售系 + 公开 ✅ | **只命中公开** ✅ |

### 关键：加了 OR 分支**不会让 GIN 索引失效**

这是最容易担心的一点，实测 `EXPLAIN` 证明没问题：

```
Bitmap Heap Scan on documents
  Recheck Cond: ((permission_tags && '{hr,sales}'::varchar[]) OR (permission_tags = '{}'::varchar[]))
  ->  BitmapOr
        ->  Bitmap Index Scan on ix_documents_permission_tags   (permission_tags && '{hr,sales}')
        ->  Bitmap Index Scan on ix_documents_permission_tags   (permission_tags = '{}')
```

PostgreSQL 把它变成了 `BitmapOr`，**两个分支各自走索引**。

> ⚠️ 这点第 7 步写 `_permission_where()` 时必须照此落地。

关系改为默认惰性加载后，**异步场景下凡是要读关系的地方都必须显式预加载**：

| 访问方式 | 结果 |
| --- | --- |
| 不预加载直接 `user.roles` | ❌ **抛 `MissingGreenlet`**（多对多必须另外发一条 JOIN 查询） |
| `.options(selectinload(User.roles))` 后访问 | ✅ 正常 |
| 不预加载直接 `doc.creator` | ⚠️ **居然成功了** —— 多对一的外键值就在本行里，且该 User 恰好已被 session 缓存 |
| `.options(selectinload(Document.creator))` 后访问 | ✅ 正常（无上传者时返回 `None`） |

> 🔴 **第 4～5 步写 `UserRepo` 时必须带 `selectinload(User.roles)`** ——
> 登录、`/auth/me`、权限标签汇总三处都要读 `roles`，漏一处就在运行时炸。
> **不要因为"`doc.creator` 直接访问没事"就以为 `user.roles` 也没事** —— 两者机制不同。

### 9.2 第 3 步的坑：bcrypt 5.0 的行为变化

`bcrypt 4.x` 起**移除了对超长密码的静默截断** —— 密码超过 **72 字节**会**直接抛错**，
而不再像老版本那样悄悄截断。因此第 3 步写密码校验函数时**必须先做长度检查**，
否则用户输入一个超长密码会得到 500 而不是友好的 400。

### 9.3 权限尚未生效（正常）

新列与新表都建好了，但**过滤逻辑一行都还没写**（第 7 步）。所以现在：

```
文档可见性 = 所有人看到全部 10 篇     ← 权限标签目前"存着但没用"
```

这是本期"7 步依赖链"的设计：**先把地基铺好，过滤放最后**。

### 9.4 存量会话的归属问题

`conversations` 现有 **7 条会话的 `user_id` 全是 NULL**（加列时存量即为空）。
它们不会出现在任何普通用户的列表里 —— 第 6 步写会话列表过滤时需要考虑：
是让 admin 能看到全部（含无主的），还是给它们补一个归属。

│            conversations + user_id（SET NULL + index）

└── 迁移     e50484caedcc：命名外键 + downgrade 顺序调整

★ 本节最重要的发现：空数组的「公开」必须写 && OR = '{}'，且不影响 GIN 索引
```
