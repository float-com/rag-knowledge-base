## 三、三个关键设计决策

### 3.1 JWT（JSON Web Token）：为什么不用服务端 Session

```
服务端 Session：服务器存一份「已登录用户表」，客户端只拿一个 session_id
JWT：          服务器【不存任何状态】，签一个带 sub + exp 的字符串，客户端自己带着
```

| 方案 | 代价 |
| --- | --- |
| 服务端 Session | 要么占进程内存（重启即掉线）、要么额外引入 Redis |
| **JWT（选它）** | 服务端**无状态**，验签通过即认可；代价是**无法主动吊销**单个令牌（本期接受） |

使用 `PyJWT` 签发与验证：由 Auth0 团队维护，**API 精简，只做 JWT 的编解码，没有多余抽象**。

### 3.2 bcrypt：密码为什么不能明文、也不能用普通哈希

```
明文       → 库被拖走 = 用户密码全泄露
MD5/SHA    → 算得太快，GPU 每秒能试上亿次
bcrypt(选它) → 单次哈希【故意】耗时约 200ms（cost=12），暴力枚举基本没戏
```

关键在于 **cost 可调（算力涨了就调高）**。200ms 对登录接口完全无感（人一次只登一次），但对暴力破解是致命的。

> ## ⚠️ 依赖警告（本项目必须知道）
> `bcrypt` 与 `passlib` **当前都没装**。安装时注意：`passlib` 1.7.4 读取 `bcrypt.__about__.__version__`，
> 而 `bcrypt>=4.1` 已移除该属性，会抛 `AttributeError` 并降级成一条难懂的 `TrappedError`。
> 两条安全路径：① 直接用 `bcrypt` 库（不用 passlib）；② 固定 `bcrypt==4.0.1`。
> **建议走 ①** —— 少一层依赖，本期只需要 `hashpw` / `checkpw` / `gensalt` 三个函数。

### 3.3 RBAC：为什么是「角色」而不是直接给用户权限

```
❌ 用户 → 权限（100 个用户要改 100 次）
✅ 用户 → 角色 → 权限标签（改一次角色配置，全体生效）
```

教程明确说**做最小化实现**，这是本期的定位：

| 维度 | 本期的收敛 |
| --- | --- |
| 内置角色 | 只有 `admin` 和 `user` 两个，**不能改名也不能删**（防止把自己锁死） |
| 权限模型 | 只有一层「权限标签数组」，**不展开"资源-操作"矩阵** |
| 自定义角色 | `admin` 可以创建 `hr`、`sales` 这类业务角色 |
| 连接表 | `user_roles` 只有 `(user_id, role_id)` 复合主键，**无任何业务字段** |

### 3.4 `&&` 数组重叠匹配：本期最优雅的一处

```sql
-- documents.permission_tags && user_tags
-- 两个数组只要有任意一个元素相等，就算命中
```

配合 **GIN 索引**，百万行表也能毫秒返回。有三条必须记住的约定：

| 约定 | 含义 | 为什么这么设计 |
| --- | --- | --- |
| `permission_tags = '{}'`（空数组） | **公开**，任何登录用户都能看 | 兼容前几期上传的存量文档，不让这次升级把它们全部"失联" |
| admin 角色带特殊标签 `"*"` | **通配**，代码里识别到 `*` **直接跳过 WHERE 拼接**，不做数组过滤 | admin 视角等价于"不加任何权限条件"，**跑得最快**，也符合"admin 看全量"的预期 |
| `chunk` 不存自己的标签 | 靠 `JOIN documents` 继承 | 见下 |

### 3.5 chunk 为什么继承 document 的权限、而不自己存一份

```
document_chunks 数量是 documents 的几十倍（实测：10 文档 / 259 chunk）
若 chunk 自己存 permission_tags：
  → 改一次文档权限 = 批量 UPDATE 几百上千行
  → 数据冗余，极易不一致
所以：chunk 这种量级表不存标签，靠 JOIN documents 取
  顺带手加一个 permission_tags 过滤，零成本
```

## 四、关键取舍：权限过滤放在哪一层

这是本期方案设计里花最多篇幅论证的地方。

### 4.1 三个候选方案

| 方案 | 做法 |
| --- | --- |
| **1** | 在 Python 应用层 post-filter：retriever 拿回 Top-K 后，再按权限丢掉无权限的 chunk |
| **2** | 在 retriever 接口里做：每个 retriever 自己 import 权限判断 |
| **3（选它）** | 在 SQL 层下推：把权限标签作为 `WHERE` 条件之一交给数据库 |

### 4.2 方案 1 的两个致命问题

```
① 召回缩水：召回 Top-20 后丢掉 15 个无权限的，真正能进 rerank 的只剩 5 个
   → 直接影响最终答案质量（Day08 好不容易把 recall_top_k 调到 20）
② 敏感数据暴露：那 15 个 chunk 【已经在进程内存里被处理过】，
   可能进了日志与 LangSmith trace
   → 违反「敏感数据最小化暴露」原则（Day09 上了全链路 trace，这个风险是真实存在的）
```

### 4.3 方案 2 的问题：重构成本

要么每个 retriever 各写一遍权限逻辑（重复），要么让它们互相 import（成环）。而本项目的检索其实是**两条腿**：

```
workflows/nodes/retrieve.py
    └─ HybridRetriever.search()                     ← 两条腿的调度者（并发召回）
           ├─ VectorRetriever.search()  ──┐
           └─ KeywordRetriever.search() ──┤   各持一个独立 session（AsyncSession 不支持并发）
                                          ▼
                        ChunkRepository.vector_search()    ← 只有这两个函数发检索 SQL
                        ChunkRepository.keyword_search()
```

方案 2 意味着**两条腿都要改**，而方案 3 只需要在它们共同的落点 `ChunkRepository` 上改一处。

### 4.4 方案 3 的落地形态

```python
# chunk_repo 提供一个统一的 WHERE 表达式工厂
def _permission_where(permission_tags: list[str]) -> ColumnElement[bool]:
    # admin 的 "*" 短路：不加任何条件，跑得最快
    if "*" in permission_tags:
        return true()
    # 空标签 → 只能看公开文档；否则做数组重叠匹配
    return Document.permission_tags.op("&&")(permission_tags)
```

**所有读路径都要拼上这一段**：

| 读路径 | 位置 |
| --- | --- |
| 向量检索 | `ChunkRepository.vector_search` |
| 关键词检索 | `ChunkRepository.keyword_search` |
| 文档列表 | `DocumentRepository.list_page` |
| 文档详情 | `DocumentRepository.get` |
| chunk 列表 / 详情 | `ChunkRepository.list_paginated_by_document` / `get_for_document` |

### 4.5 身份怎么一路流到 SQL（本期最关键的一条链）

```
HTTP 请求（Authorization: Bearer ...）
  → FastAPI Depends 解析出 CurrentUser
  → Service 层把该用户所有角色的 permission_tags 求并集，得到 user_tags
  → ChatService.stream_answer 在【进图之前】把 user_tags 注入 RAGState
  → workflows/nodes/retrieve.py 从 state 取出，传给 HybridRetriever
  → ChunkRepository 拼成 WHERE 条件
  → 数据库只返回有权限的行
```

> 🔴 **`RAGState` 是 `TypedDict(total=False)`，新字段必须显式声明，否则 LangGraph 会【静默丢弃】。**
> 本期要给这个 18 字段的 state 加第 19 个字段 `permissions`。不声明就丢，而且不报错。

## 五、数据模型（3 张新表 + 2 张改表）

```
新建 3 张：roles / users / user_roles
改造 2 张：documents（+ permission_tags + created_by）
           conversations（+ user_id）
```

| 表 | 关键列 | 说明 |
| --- | --- | --- |
| `users` | `id` uuid PK、`username` varchar UK、`password_hash` varchar、`display_name` varchar、`status` varchar | 用户名唯一 |
| `roles` | `id` uuid PK、`name` varchar UK、`permission_tags` TEXT[] | 角色名唯一 |
| `user_roles` | `user_id` uuid PK+FK、`role_id` uuid PK+FK | **纯连接表**，复合主键，无业务字段 |
| `documents` | `+ permission_tags` TEXT[]、`+ created_by` uuid FK | 前者管**可见性**，后者管**审计** |
| `conversations` | `+ user_id` uuid FK | 会话**归属**，只能看自己的 |

**两条关系要分清**：

```
roles.permission_tags  ←→  documents.permission_tags     同一个词汇表，靠 && 匹配
                           ↑ 这是全期唯一的权限连接点

documents.created_by   →  users   记录【谁传的】（审计）
conversations.user_id  →  users   记录【谁的会话】（归属）
```

> ⚠️ **图中 `text_array` 是渲染妥协**：
> mermaid 的 ER 属性类型不允许 `[]`（会当语法字符截断），所以配图里把 `TEXT[]` 记作 `text_array`。
> **数据库实际列类型是 PostgreSQL 的 `TEXT[]`，不存在 `text_array` 这种类型。**
>
> ⚠️ `user_roles` 刻意**不加 `created_at`**，与教程保持一致的最小形态。
> 代价是失去"角色何时被授予"的审计信息；若后续要补，现在补最省事（迁移里一次加完）。

## 六、实现顺序（严格依赖链，跟着走不返工）

```
1. 装依赖与配置         → PyJWT + bcrypt；JWT_SECRET / 过期时间进 .env
                          三处同步：.env + .env.example + config.py
2. 建表迁移             → roles / users / user_roles 新建，documents / conversations 加列
3. 安全工具函数         → 签令牌 / 验令牌 / 密码哈希 / 密码校验
4. Repository + Service → UserRepo / RoleRepo + AuthService
5. 依赖注入             → CurrentUser / CurrentAdmin 两个 Depends（写进 app/api/deps.py）
6. 路由                 → /api/auth/login、/api/auth/me、/api/users、/api/roles
                          （必须对齐 2.3 节列出的 12 个 operationId）
7. 最后一步：权限过滤接入检索 SQL   ← 前六步全为这一步铺垫
```

**为什么"权限过滤"必须排最后**：它依赖 `CurrentUser` 拿到 `user_tags`，而 `CurrentUser` 依赖 1～6 全部就位。
**如果先做过滤，你会造出一个"拿不到用户身份"的过滤函数**，只能靠假数据测，最后还得整体返工。

## 七、⚠️ 风险预警：本期过滤会反噬 Day10 的评测链路

**这是本期最容易踩、且后果最严重的一个坑，必须在方案设计阶段就记下来。**

```
Day10 的评测入口 ChatService.answer_for_evaluation
        ↓ 走的是和线上问答【完全同一条】检索链路
    ChunkRepository.vector_search / keyword_search
        ↓ 第 7 步给这两个函数加上【权限 WHERE】之后
    评测跑批时如果没有"系统身份"，permission_tags 为空
        ↓
    命中条件变成「只匹配公开文档」→ 非公开文档全部检索不到
        ↓
    Day10 的各项指标（context_recall / citation_hit_rate / ...）【突然崩盘】
```

**必须在第 7 步一并处理**，两种方案：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A. 评测走系统身份 | `answer_for_evaluation` 显式注入 `["*"]`（等价 admin 视角） | 语义清晰，但要明确"评测是系统内部行为，不代表任何真实用户" |
| B. 评测按用户跑 | 给评测 run 加 `owner_id`，按某用户权限跑 | 更真实（能测出"某用户看不到某文档"这类 Bad Case），但本期工作量翻倍 |

**建议走 A**，并在评测的归档文档里同步说明 —— 否则 Day10 的指标会变成"测的是权限过滤，不是检索质量"。
